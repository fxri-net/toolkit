# 本地门禁提速与改动文件覆盖率

第 2 个（共 4 个）；前置：20261124-唐启云-修复性能预算测试在覆盖率下误红；后继：无

## 背景

本地全量门禁实测 265s：单元测试 + 覆盖率采集 194s、类型检查 32s、eslint 30s、仓库自检 7s，其余约 12s。
覆盖率让单测从 ~86s 涨到 194s（2.2 倍），主要开销在「200+ 文件的报告生成」，而不是测试执行本身。

不能简单把覆盖率全交给 CI：发布门禁也在本地 `pnpm verify`，若本地不采集且代码未推送，「功能写了、测试忘加」的代码可能直接发布。
所以本地要保留**改动行覆盖率信号**，只是把采集范围收窄到本次改动的文件——测试仍全量跑，信号不丢，开销下降。

## 采集率口径（本次不改判定公式，只改采集范围）

- 指标是**新增语句的命中比例**，不是文件数、不是全仓百分比：
  `改动行覆盖率 = 被测试执行到的新增语句数 / 新增语句总数`。
- 「新增语句」由 `git diff -U0` 的 `+` 行确定；语句起始行落在这些行里的才计入。
- 门槛：新增语句 ≥ 5 条时要求 ≥ 80%，不足 5 条直接放行。
  - 改 3 行已测函数内的逻辑：既有测试通常覆盖到，覆盖率高，不需要新增测试；
  - 新增一个 6 条语句的小功能：至少 5 条被执行即可，**只需一个测试触达，不要求成堆测试文件**；
  - 0/6 才失败——含义是「新代码一行都没跑过」，不是「测试文件不够多」。
- 覆盖率收窄只改变「报告里包含哪些文件」，因为全部测试照跑，改动文件的语句命中数依然准确。
- **补测不按任务新建文件**：门槛只要求「新增语句被执行到」，优先在既有同主题测试文件里追加用例；仅当被测模块没有对应测试文件时才新建（文件生命周期约定见后继任务）。

## 实施方案

1. **先实测开销**：对比 `--coverage`（全量 200+ 文件）与 `--coverage --coverage.include=src/<单文件>` 的耗时。
   若收窄后仍 ≥170s（说明开销在执行而非报告），回退为「本地不采集覆盖率 + 发布前必须 `--full`」，并在任务档记录实测数据。
2. **本地按改动文件采集**：`scripts/verify.mjs` 在本地（非流水线、非 `--full`）取改动/未跟踪的 `src/**/*.ts`，
   生成 `--coverage.include` 列表；无改动时不采集覆盖率并提示「无可采集文件，覆盖率交由流水线」。
3. **局部模式跳过全局下限**：`scripts/check-coverage.mjs` 增加 `--no-floors`（局部数据算不出全局），改动行判定照常；
   流水线与 `--full` 保持全量采集 + 全局下限。
4. **类型检查改增量**：类型检查步骤增加 `--incremental --tsBuildInfoFile .toolkit-verify/tsconfig.tsbuildinfo`；
   `.toolkit-verify` 已在 gitignore 内，CI 冷环境行为不变。
5. **覆盖率摘要写进 GitHub job summary**：`check-coverage.mjs` 结论后若存在 `GITHUB_STEP_SUMMARY`，追加 Markdown 摘要
   （全局四项百分比 + 改动行覆盖率 + 未覆盖 `文件:行`，最多 20 行）；本地与 GitLab 无该变量时不写。
6. `AGENTS.md` 同步：本地默认只对改动文件采集覆盖率并跳过全局下限，`--full` 与流水线全量；发布前必须 `--full` 或已推送由 CI 校验。

## 影响范围

- 触达：`scripts/verify.mjs`、`scripts/check-coverage.mjs`、`AGENTS.md`；`.gitignore` 已含 `.toolkit-verify`，无需改。
- 判定公式（改动行 80%、全局下限 78/65/82/81）不变；本地只是采集范围收窄、全局下限跳过。
- 测试与 eslint 仍全量，不裁剪。
- 变更集：无（内部门禁口径，无对外行为变化）。

## 验证方式

1. 实测对比：全量 `--coverage` 与单文件 `--coverage.include` 的耗时差，记录在任务档；据此确认方案或回退。
2. 本地裸 `pnpm verify`：只采集改动文件，输出改动行覆盖率；总耗时预期 100–120s（未达标则按第 1 步回退）。
3. 反向验证：在 `src/` 新增一个未被测试触达的函数 → 本地门禁报出 `文件:行`、退出 1；补一个触达测试后通过。
4. 小型改动（新增语句 <5 条）放行，不要求新增测试文件。
5. `pnpm verify --full` 与模拟流水线（`FX_TOOLKIT_PIPELINE=1`）：全量采集 + 全局下限 + job summary（后者设置临时 `GITHUB_STEP_SUMMARY` 验证）。
6. 归档后 `pnpm verify`。

## 回滚

单提交回退（恢复全量覆盖率与 `skipCoverage` 默认）。
