# 全端通用规范（common）

> 归属：common。跨面原则：改规则、改门禁、设计对外接口时适用。索引见 index.md。

## C-28. 规则落门禁

规则层新增或强化一条「可自动检出」的要求时，**或复核发现既有要求尚无检测入口时**，须在**同批变更**内补落检测入口（`toolkit task check` / `pnpm verify` 内步骤），且入口须置于不可逆动作**之前**；只写进规则文件或核对清单而无门禁覆盖的要求，一律视为纸面规则。

- **要求**：新增 / 强化可检出的要求、或复核发现既有要求无检测入口时，同步问三句——有检测入口吗？入口挂在哪个命令？它跑在不可逆动作之前吗？三问缺一即补齐；检测入口优先并入既有 `task check` 软告警清单，不自造新命令与新开关。
- **反例**：`skills/fxri-release-changelog/SKILL.md` 早已规定「变更描述一律以 `类型：` 前缀开头」，但 `pnpm verify` 与 `toolkit task check` 均不扫 `.changeset/`——缺前缀只在 `release bump` 时由 `warnUntypedEntries` 兜底告警，而那一刻 `changeset version` 已消费并删除变更集源文件，告警到达时已无从补写，规则在发版前实际从未生效。（历史注记：`skills/README.md` 与 `docs/guide.md` 的技能版本表曾是无门禁用例的手写投影、随真源升级而漂移；该缺口已由版本表一致性校验补齐，不再作为现存缺口示例。）「既有要求只停留纸面」与新增要求同等对待，复核发现即补落入口。
- **理由**：规则的效力不取决于写得多完整，而取决于违规能否被自动挡住；检测时点晚于不可逆动作（发版、消费删除源文件）时，告警只能事后追认，与无告警等价。
- **配套**：与索引 `C-7`「触达核对前置」配套——后者管「规则措辞的文档触达面」，本条管「规则的可执行落点」，两者同为规则生效的必备条件。

## C-29. 门禁与测试的环境无关性

`pnpm verify` 的每一步都须与**运行环境**无关（hermetic），尤以时区为要：凡涉「无时区的墙上时间字符串 ↔ `Date.now()`」比对的测试与步骤，本地与 CI 须在同一时区口径下运行；口径按**数据来源**分两轴——合成数据步骤（被测数据由测试当场构造、与运行环境时区无关）钉 `TZ=UTC`，读真实任务数据的步骤钉 `TZ=Asia/Shanghai`，在数据书写时区原地判定；具体步骤名、数量与各自时区以 `scripts/verify.mjs` 各步骤的 `env` 声明为准，本文不枚举。后续新增涉时间的测试 / 步骤须同样按来源选定并固定时区。

- **要求**：新增或修改门禁步骤 / 单测时，问一句「这一步的期望是否随运行环境（时区、locale、路径分隔符、换行符）变化？」——会变化的须显式固定该环境变量，使本地与全部 CI 同轴；时区取值按数据来源选：合成数据取 `TZ=UTC`，读真实任务数据取数据书写时区（本仓库为 `TZ=Asia/Shanghai`）。业务侧跨时区容差（如 `src/date.ts` 的 `MAX_UTC_OFFSET_MS`）只作补充，不能替代测试侧固定时区。
- **反例**：未来时间检测把「无时区的本地墙上时间」按运行环境时区解析后与 `Date.now()` 比对；归档时间戳按东八区墙上时间书写，本地（UTC+8）跑绿、CI（UTC）把 +8 墙上串当 UTC 解析而整体前移 8 小时被判为「未来」，同一份代码在 GitHub `check` / `windows` 两 job 全红、14 条误报——「本地自检通过、CI 才报错」正是非环境无关的征兆。
- **理由**：门禁的价值在于「本地跑绿 = CI 跑绿」；一旦某步依赖运行环境，本地通过即丧失对 CI 的预测力，缺陷只在远端暴露而本地门禁形同虚设。
- **配套**：与索引 `C-22`「门禁单源与时点」配套——后者管「步骤清单单源与关卡时点」，本条管「单步的环境无关性」。

## C-41. AI 优先的人机体验

本工具的主要使用者是 AI，其次是人；功能、输出、错误与文档须先保证 AI 可解析、可自动化、可复用，再兼顾人的可读性与操作便利。

- **要求**：对外契约优先结构化与确定性——机器可读输出走稳定字段（如 `--format json` / `schemaVersion`），stdout 只放数据、告警与诊断走 stderr；交互式能力须同时提供非交互入口（`--yes` 或等价参数），不得让 AI 必须模拟 TTY；错误须给出稳定标识与可执行的下一步；文档先写命令、参数、边界与可复制示例，再补解释。人的体验（可读性、可发现性、安全性）应兼顾，但不得以牺牲 AI 可自动化性为代价。
- **反例**：只做交互向导、没有 `--yes`；关键信息只存在于彩色终端文本或表格；失败只给自然语言、没有稳定字段与下一步；文档只有概念说明、没有可直接复制的命令。
- **理由**：AI 是主要执行者与消费者，AI 体验差会直接导致调用失败、误操作与上下文浪费；人仍负责确认与排障，因此两边都要覆盖，但优先级不能倒置。
- **配套**：与 `C-26`「降级不静默」、`C-40`「文档信息架构」配套——`C-26` 管失败可观测，`C-40` 管文档按任务组织。

## C-45. 命名与封装统一

同一类操作在不同模块换名字，会让调用方反复确认、也让检索失效；本仓库以本条文为命名唯一口径，新增代码立即遵守，存量按批次收敛。

- **要求**：
  - 动词族固定：`read` 纯读取 / `load` 读取并补默认值或缓存 / `resolve` 推导 / `get` 即时取值 / `list` 返回集合 / `find` 筛选集合 / `format` 文本化 / `print` 终端输出 / `run` 命令流程 / `write` 落盘 / `ensure`、`assert` 保证。
  - 谓词：返回 boolean 一律 `is` / `has` / `can` / `should` 开头，匹配类可用 `matches*`；禁止负向命名（`lacksX` 改为 `hasX` 并在调用处取反）。
  - 参数：配置对象用 `options`、已加载配置用 `config`、路径用 `dir` / `file` / `path`；不用 `opts`、`cfg` 一类简写。
  - 文件：kebab-case；角色后缀主体在前（`cli-main.ts`、`cli-guard.ts`），不新增 `-cmd` 一类后缀。
  - 前缀：当前源码不使用 `fx` 前缀；新增前缀须先立目录与白名单（如跨模块基础封装层），通用能力（文件、路径、时间、版本）与业务域（scope / skills / tasks / usage / changelog）一律不加前缀；包名 `@fxri/toolkit`、技能名 `fxri-*` 保持既有。
  - 全局命名空间：环境变量一律 `FX_TOOLKIT_<用途>`，不写 `FX_<用途>`（多产品并存会串）；文件与目录优先放进 `.toolkit/`、`~/.toolkit/`、`.toolkitrc*.json` 等产品目录，必须落在通用目录时文件名带 `toolkit`；生成文件的标记键同样带 `toolkit`（如 `toolkit-usage-hooks`）。例外：`.tasks/.archive.lock` 位于共享任务目录，改名会让新旧版本互斥失效，维持不改。
  - 封装优先：文件读写与主目录解析只走 `readTextFile` / `writeFileAtomic` / `getHomeDir`；终端样式等跨命令的展示能力收敛到单一模块（如 `src/term-style.ts`）并落 lint 门禁，禁止在各命令内联 ANSI 转义。
  - 存量策略：内部函数分批重命名；`src/index.ts` 公共导出改名保留旧名别名并标注弃用，或按 major 处理；环境变量等对外名称的兼容读取须写明移除版本与告警文案，不无限期保留。
- **反例**：同一读取动作在不同模块分别叫 `readX` / `loadX` / `getX`；布尔函数叫 `pathPresent` / `dirsEqual`；配置对象参数写 `cfg` / `opts`；环境变量只写 `FX_USAGE_DIR`，与同组其它产品撞名；改名后旧名静默失效，用户升级即断。
- **理由**：命名是检索面与调用面的共同契约；动词、谓词与命名空间不统一时，同一能力会出现多套入口，文档与测试也得各自记住，长期维护成本随模块数增长。
- **配套**：与 `C-7`「触达核对前置」配套（改名须过文档与门禁触达面）、`C-28`「规则落门禁」配套（可自动检出的命名约束优先落门禁）。

## C-47. 交互与入口统一

同一工具内多套交互写法会让用户与 AI 都要重新学习入口、取消语义与确认边界；新增命令一律按本条文接入既有基座与矩阵，不再自造第二套。

- **要求**：
  - 交互一律走 `src/cli-ui.ts`：有上级步骤时 ESC 返回上一级、顶层退出；Ctrl+C 以 `130` 结束；取消文案统一为「已取消，未修改任何文件」式；确认选「否」按成功 `0` 退出，不写任何文件。
  - 写操作统一「预览 → 确认 → 落盘 → 结果块」：`--yes` 跳过确认、`--dry-run` 只预览；非 TTY 的批量写须显式 `--yes`，否则报错并给出用法。
  - 裸命令入口按域类型固定：查询型给默认视图、配置 / 分发型给帮助、交互型给摘要 + 子命令提示；非 TTY 一律退出 `0`，
    需要强制交互时用 `--interactive`（无终端时退出 `2`），不再单列 `wizard` 子命令。
  - 开关类查询同时支持 `--format json`，文本与 JSON 由同一份摘要数据渲染；机器可读输出不带诊断与指引。
  - 入口矩阵、术语表与退出码以 `docs/cli.md` 为单一事实源；改入口行为须同批更新该页与 `cli-golden` 快照。
- **反例**：裸命令在不同域一会儿进菜单、一会儿报退出码 2；子页 ESC 直接取消整个命令；`--yes` 与 `--dry-run` 语义各域不同；`--format json` 里混入提示文案。
- **理由**：入口与取消语义是脚本与 AI 判断「能否继续」的依据，各域自造会在组合调用时产生不可预测的退出码与交互阻塞。
- **配套**：与 `C-41`「AI 优先」配套（非交互入口与纯净 JSON 通道是自动化的必要条件）、`C-28`「规则落门禁」配套（矩阵有 golden 快照与文档断言）。

## C-48. 单一真源与事实注册表

同一事实只允许一个 owner；其余位置一律 import 派生、指针引用或由生成块产出，不得各写一份。

- **事实四类**：A 代码事实（数值 / 枚举 / 清单）、B 契约事实（对外格式）、C 叙述事实（流程 / 措辞）、D 外部约束（`engines` / CI）。
- **手段四级**：派生 > 指针 > 生成 + `--check` > 一致性校验；同一事实不得同时存在生成器与校验器两份实现。
- **归属分层**：包内（`files` 白名单）/ 文档站（`docs/`）/ 本仓（`AGENTS.md`、`.trae/`、`.tasks/`、`scripts/`、`src/` 源码）。
  用户可见事实的 owner 必须落在包内或文档站；本仓只放维护纪律、自检与守卫，不承载只给使用者的正文或数值。
- **文档三层职责**：手册＝用户视图、skills＝细节真源、`ai.md` 与各规则页＝薄壳（纪律 + 模块自有细节 + `preferences` 偏好）；
  三层各写各的读者面，不得互相复述可变流程细节。
- **生成器输入契约**：脚本不得正则解析源码结构；优先读数据文件，必须解析时加「解析条数 == 结构出现次数」不变量并在 `--self-test` 覆盖。
- **生成物入库**：生成块与产物随仓库提交（包内文件直接分发，不在发布时补生成）。
- **数字书写**：清单型数量（模块数、技能数、脱敏类数、状态数）必须指向 `--help` 或单源页，不在正文写死；
  直接影响用户判断的阈值（如搁置天数、更新间隔）可保留具体数字，但须有引用代码常量的一致性测试（`thresholds.test.ts`）。
- **登记与维护**：新增事实先登记下表（`F-<n>` 不复用）；owner 变更同批改本表并写 `history.md`；`check-consistency` 校验本表结构与 ID 连续性。
- **配套**：`C-16`（提交规则单源）、`C-15`（锚点单源）、`C-22`（门禁单源）均为本条在具体领域的实例。

## C-49. 工具与技能离线自包含

工具与技能在没有网络、内网或私有大模型的环境下也要能完成正常执行与升级判断；远端页面只能作可选补充，不能承载规范正文、候选清单或迁移步骤。

- **要求**：规范正文、候选清单与升级步骤须随包分发，或由生成器写入包内文件；技能正文不出现承载规范内容的 `http(s)://` 链接（frontmatter `source` 与明确标注「可选」的链接除外）；技能内相对链接只能指向本技能目录或 `package.json` `files` 白名单内文件，跨技能 `../fxri-*` 引用须带「技能源 / 包内真源」兜底；工具运行时提示涉及升级 / 迁移时，须同时给出本地文件或本地命令。
- **反例**：把候选目录表写成文档站链接，离线时查不到；技能模板示例指向未随包分发的 `docs/` 路径；升级提示只给在线升级页，内网用户无从判断。
- **理由**：受限环境的用户占比不低，远端依赖会把「装完即用」变成「先能上网」；链接失效还会把规范正文变成死链，而 AI 在离线时会把死链当作可读内容继续引用。
- **配套**：与 `C-7`「触达核对前置」、`C-48`「单一真源与事实注册表」配套——后者要求生成物入库，本条要求正文与提示不依赖外网；门禁为 `scripts/check-consistency.mjs` 的离线自包含检查。

## C-50. 人读文案与机器键分离

CLI 的人读输出优先让人看懂，机器键只服务程序消费；同一概念、符号与提示语写法只认一处。

- **要求**：文本层只给中文，`policy:<id>` / `allowlist` / `gated` 等机器键只进 `--format json` 与调试输出；用户需要手写取值时写「中文（原值）」；称谓、状态符号、提示语与报告行结构以 `docs/cli.md` 的「术语表」「文案约定」为单一事实源，新增概念先入表再进代码；help 与文档引用实际输出，发现不一致同批修正。
  交互选项一律「名称 + 一行影响面说明」（说明只作展示、不参与判定），长路径按中段省略；选项值不变。
- **反例**：`scope status` 直接打印 `policy:legacy:...`；向导标题写「要做什么」；同一状态混用 `✔` / `✓`；选项只有名称，用户看不出选它会做什么。
- **理由**：机器键与实现术语对使用者无意义，还会在措辞调整后漂移；集中一处才能让代码、help、文档与技能保持同口径。
- **配套**：与 `C-48`「单一真源」、`C-41`「AI 优先」配套；门禁为 golden 快照与 `docs/cli.md` 的术语断言。

## C-51. 声明式写入即收敛

派生自配置的产物（安装形态、链接、入口壳等）必须由写命令自己收敛，不能留第二条命令让用户补跑。

- **要求**：写配置的命令须在一次调用内完成「写前预览派生变更 → 确认后先原子落配置 → 再收敛产物 → 逐项报告结果」；产物已是目标形态时不重写（幂等），
  收敛失败不得静默——退出码非 0 并给出可重跑入口，且失败态只能是「配置已生效、产物仍更宽」这类安全方向。
  低层写入口（`config set`、手工改配置文件）不自动收敛，但须提示漂移与收敛命令；收敛命令只对齐既有产物，不改选择集、不新增对象。
- **反例**：`scope list add` 只写配置，用户还得自己想起跑 `skill install`；收敛失败仍以 0 退出；预览只说「将写入配置」，不列哪个产物会变形。
- **理由**：配置是声明，产物是派生；留第二条命令等于把一致性责任推给用户，而静默失败会让配置与现场长期分叉、还查不出是哪一步漏的。
- **配套**：与 `C-26`「降级不静默」、`C-47`「交互与入口统一」配套；实现见 `src/scope/artifact-linkage.ts` 与 `src/skills/reconcile.ts`，
  门禁为联动单测与 golden 快照。

## C-52. 命令域归属：顶层编排、域内初始化

顶层命令只做跨域编排，某一个域的初始化与配置动作归该域，不在顶层重复提供。

- **要求**：跨多个域的一条龙流程放顶层（如 `toolkit setup` 做技能 / 规则 / 作用域的接入编排）；单域的构建动作挂在该域下
  （如任务区初始化是 `toolkit task init`）；顶层命令不复制域内能力，只调用它；域内命令保持可单独执行且幂等。
- **反例**：顶层命令既做任务区初始化又做全局接入（v1 的 `init`）；向导里复制一份 `task init` 的实现；把单域设置写成顶层命令、与域内入口并存。
- **理由**：能力归属单一，help 与文档才能按域收敛；顶层膨胀会让「一条命令」的边界越滚越大，同一动作也会出现两套参数与两套提示。
- **配套**：与 `C-47`「交互与入口统一」、`C-48`「单一真源」配套；编排层以独立 program 调用各域命令，不复制其内部逻辑。

## C-53. 规则模块独立可读

全局规则按模块组合后供用户单独复制，任一模块正文不得具名引用另一个模块。

- **要求**：跨模块说明改写为语义自述（「除非规则另有约定」而非「个人偏好可覆写」）；确需转发时只保留行为要求，不写「细节见《某规则》」；
  推荐预设包含的模块组合必须能独立读通，删掉任一模块不产生悬空指代；模块间语义冲突在条文层消解（如「提交是否执行由规则约定，未约定时需用户确认」），
  不靠读者自行排序。
- **反例**：`workflow` 写「个人偏好可覆写」而 `recommended` 预设不含该模块；`usage` 具名引用 `workflow` 的两条纪律；
  模块正文写「覆写本套规则」而单独复制时没有「本套」可言。
- **理由**：用户只复制自己需要的模块，具名引用在缺失时会变成悬空指令；同一问题连续三次只换措辞仍未消除，说明必须按语义自述判断，而不是替换名词。
- **配套**：与 `C-6`「细节只进 skills」、`C-48`「单一真源」配套；门禁为规则页组合一致性测试与预设断言。

## C-59. 规则文本的收件人与指代

全局规则的收件人是 AI 自身（`core` 首句「你是一个严谨的编程助手」），凡指向用户的授权、确认与选择必须写「用户」，不能写「你」。

- **要求**：规则模块正文与规则页可复制块内，`你` 只用于给 AI 定角色；授权、确认、选择、提供的对象一律写「用户」
  （如「须先获用户明确授权」「未约定时需用户确认」）。规则页围栏外的说明文字面向读者，可继续用「你」。
- **反例**：`preferences` 写「都须先获你的明确授权」——收件人是 AI，「你的授权」读成 AI 授权自己；
  `workflow` 写「未约定时需你确认」——无法判断是 AI 自行确认还是向用户确认。
- **理由**：规则直接喂给 AI，指示代词随收件人解释；同一段既给 AI 定角色、又用「你」指用户时，模型容易把授权对象读成自己。
  改写成「用户」后语义唯一，也便于按关键词检索与复核。
- **配套**：与 `C-53`「规则模块独立可读」、`C-50`「人读文案与机器键分离」配套；改规则模块须同步锚点与文档镜像（见 `C-15`）。

## C-55. 入口收敛优先

同一能力出现两条以上入口时，用户与 AI 都要记住「什么时候用哪条」；默认只保留一条，强制交互也不另开平行命令。

- **要求**：裸命令直接承担该域的默认行为（查询型给视图、配置 / 分发型给帮助、交互型给交互）；
  需要非终端强制交互时用 `--interactive`，不单列 `wizard` 之类平行入口；被替代的旧入口直接移除、不留隐藏别名，
  兼容只保留在 v1 argv 改写层（命中时提示迁移）；移除属破坏性变更，变更集用 `重大：` 标注。
- **反例**：`scope wizard` 与裸 `scope` 同时进向导；`skill plan` 与 `skill install --dry-run` 同义并存；删除入口后保留无提示的隐藏别名。
- **理由**：入口数量随功能增长线性膨胀，每个入口都要独立文档、测试与取消语义；收敛到一条后，帮助与文档才有唯一口径。
- **配套**：与 `C-47`「交互与入口统一」配套（入口矩阵以 `docs/cli.md` 为准）、`C-52`「命令域归属」配套。

## C-62. 极简入口与批量有界

对外只保留一条主入口，内部可自由拆分；批量 / 覆盖动作不能因为「入口只有一个」就默认全做。语义与变体以概念 `minimal-entry` 为单一真源，本条只做指针，不复述细节。

- **要求**：新增或改命令入口时，先问「用户是否只需记住这一条」；批量动作先预览影响范围，条目多时交互多选且默认不全选，脚本才用 `--all --yes` 显式全量。
- **反例**：同类动作并列多条等价命令；批量命令没有预览就直接全部执行；交互多选默认全勾选。
- **理由**：入口数量与批量默认值都会随能力增长膨胀；只收敛入口却不收窄默认动作，误伤面反而更大。
- **配套**：与 `C-55`「入口收敛优先」、`C-47`「交互与入口统一」配套。
