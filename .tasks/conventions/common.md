# 全端通用规范（common）

> 归属：common（所有端适用）。条文全文见本节，索引见 index.md。

## C-23. 测试假现场须与真实现场形态一致

测试中用于模拟现场（安装布局、目录结构、路径形态等）的假数据，必须与真实环境可能出现的形态一致；被测逻辑对现场形态存在分支判据时，每一种真实存在的形态都要有对应用例覆盖，不得只造一种。

- **反例**（本条的来源案例）：稳定入口解析的守卫只在「项目内 pnpm 布局」成立，而测试假现场清一色写成 `<home>/node_modules/.pnpm/…`——该形态属项目内布局，全局布局（`.pnpm` 与 `node_modules` 并列）无人覆盖，守卫在全局布局下恒假也拦截不到，缺陷直达用户真机；且判定层只比对 realpath，`status` 仍报「正常」，症状被二次掩盖。
- **要求**：造现场前先枚举被测逻辑会遇到的真实形态（如 pnpm 项目内 / pnpm 全局 / npm、yarn 的真实目录），逐种造现场并断言；形态判据本身也要有纯函数级用例，端到端用例则要跑通「形态变化 → 行为仍正确」。
- **与索引`C-17`「测试不复刻被测实现」配套**：后者管「逻辑同错复刻」，本条管「现场形态失真」；两者都会让实现缺陷原样漏过，互为补充。
- **理由**：假现场与真实现场形态不符时，测试通过只证明「该形态下正确」，对未覆盖形态零信息量，并给出虚假的安全感。

## C-25. 版本括注口径（本仓库治理）

文档中的 `（x.y.z 新增）` 类版本括注，只用于标注**命令 / 技能 / 配置项 / 单一能力点**的首次引入版本，且须紧邻该对象本身；描述**跨版本演进的产物清单**时不得在句末挂版本括注。

- **反例**（本条的来源案例）：`初始化项目任务区（生成 .tasks/ 骨架、conventions/ 规范载体与技能入口壳，1.7.0 新增）`——产物跨 1.7.0（`init` 与 `.tasks/` 骨架）、1.10.0（conventions 目录化）、1.11.0（v2 载体与入口壳）三代，`1.7.0 新增` 挂句末必然失真。
- **要求**：括注单一能力点时须点明对象（如「配置项 1.7.0 新增」）；后续扩展史一律由 `CHANGELOG.md` 承载，文档不复述「x.y.z 又扩展了什么」；与 `--help` 同源的命令清单以 `--help` 文本为准、不加版本括注。
- **理由**：把「首次引入版本」（稳定事实）与「跨版本演进清单」（易变事实）混在一处，任何一次能力演进都会让括注失同步，且读者无从判断该括注指向哪一代产物。

## C-28. 规则落门禁（本仓库治理）

规则层新增或强化一条「可自动检出」的要求时，**或复核发现既有要求尚无检测入口时**，须在**同批变更**内补落检测入口（`toolkit tasks check` / `pnpm verify` 内步骤），且入口须置于不可逆动作**之前**；只写进规则文件或核对清单而无门禁覆盖的要求，一律视为纸面规则。

- **反例**（本条的来源案例）：`skills/fxri-release-changelog/SKILL.md` 早已规定「变更描述一律以 `类型：` 前缀开头」，但 `pnpm verify` 与 `toolkit tasks check` 均不扫 `.changeset/`——缺前缀只在 `changelog version` 时由 `warnUntypedEntries` 兜底告警，而那一刻 `changeset version` 已消费并删除变更集源文件，告警到达时已无从补写，规则在发版前实际从未生效。
- **反例（存量补落）**：`skills/README.md` 与 `docs/guide.md` 的技能版本表是 SKILL.md 真源版本的手写投影，核对清单明列「表内版本须与真源一致」，却无用例读取两张表——投影随真源升级而漂移（`fxri-release-changelog` 双写位升 1.1.3、两表仍留 1.1.2）无人拦截；「既有要求只停留纸面」的缺口与新增要求同等对待，复核发现即补落入口。
- **要求**：新增 / 强化可检出的要求、或复核发现既有要求无检测入口时，同步问三句——有检测入口吗？入口挂在哪个命令？它跑在不可逆动作之前吗？三问缺一即补齐；检测入口优先并入既有 `tasks check` 软告警清单，不自造新命令与新开关。
- **与索引`C-7`「触达核对前置」配套**：后者管「规则措辞的文档触达面」，本条管「规则的可执行落点」，两者同为规则生效的必备条件。
- **理由**：规则的效力不取决于写得多完整，而取决于违规能否被自动挡住；检测时点晚于不可逆动作（发版、消费删除源文件）时，告警只能事后追认，与无告警等价。

## C-29. 门禁与测试的环境无关性（本仓库治理）

`pnpm verify` 的每一步都必须与**运行环境**无关（hermetic），尤以时区为要：凡涉「无时区的墙上时间字符串 ↔ `Date.now()`」比对的测试与步骤，本地与 CI 须在同一时区口径下运行；口径按**数据来源**分两轴——合成数据步骤（`scripts/verify.mjs` 的「单元测试」「覆盖率门槛」两步，被测数据由测试当场构造、与运行环境时区无关）钉 `TZ=UTC`，读真实任务数据的步骤（「本源仓库自检」「任务区体检（tasks check）」「归档块归一核验（tasks normalize）」）钉 `TZ=Asia/Shanghai`，在数据书写时区原地判定。后续新增涉时间的测试 / 步骤须同样按来源选定并固定时区。

- **反例**（本条的来源案例）：未来时间检测把「无时区的本地墙上时间」按运行环境时区解析后与 `Date.now()` 比对；归档时间戳按东八区墙上时间书写，本地（UTC+8）跑绿、CI（UTC）把 +8 墙上串当 UTC 解析而整体前移 8 小时被判为「未来」，同一份代码在 GitHub `check` / `windows` 两 job 全红、14 条误报——「本地自检通过、CI 才报错」正是非环境无关的征兆。
- **要求**（与索引`C-22`「门禁单源与时点」配套）：新增或修改门禁步骤 / 单测时，问一句「这一步的期望是否随运行环境（时区、locale、路径分隔符、换行符）变化？」——会变化的须显式固定该环境变量，使本地与全部 CI 同轴；时区取值按数据来源选：合成数据取 `TZ=UTC`，读真实任务数据取数据书写时区（本仓库为 `TZ=Asia/Shanghai`）。业务侧跨时区容差（如 `src/date.ts` 的 `MAX_UTC_OFFSET_MS`）只作补充，不能替代测试侧固定时区。
- **理由**：门禁的价值在于「本地跑绿 = CI 跑绿」；一旦某步依赖运行环境，本地通过即丧失对 CI 的预测力，缺陷只在远端暴露而本地门禁形同虚设。

## C-32. 现场路径形态须归一（本仓库治理）

生产代码对「**同一资源的不同路径书写形态**」做比对或归属判定时，须先取**磁盘真实形态**（`fs.realpathSync.native` 等）再比较——比对两侧、以及作为边界基准的值（如 home、仓库根）与其父链逐级目录，都要过归一函数；只做纯字符串归一不足以替代真实形态归一。

- **不归一的形态差异**（同一目录的多种书写形态）：Windows 8.3 短名 / 长名（`C:\Users\RUNNER~1\…` ↔ `C:\Users\runneradmin\…`）、软链 / 实链（macOS `/var` ↔ `/private/var`）、盘符与段大小写、分隔符。
- **纯字符串归一与真实形态归一的分工**：`normalizePathForCompare` 这类「分隔符转正斜杠 + 去尾斜杠 + 折叠大小写」只解决**书写层**差异，对短名 / 软链一律无能为力；两者须叠加使用，不可互相替代。真实形态归一在路径不存在时回退原串，保证「本就不可命中」的场景行为不变。
- **反例**（本条的来源案例）：`inspectLocalConfigIgnore` 以 `git rev-parse --show-toplevel` 返回的**长名**仓库根，与来自 `os.tmpdir()` 的 **8.3 短名**目标路径做前缀比对，`isInsideWorktree` 误归 `outside-repo`，「本地配置未被 gitignore 覆盖」告警被**静默吞掉**（连同违反 `C-26`）；`config.ts` 本地层 `stopAtHome` 的 home 边界同因失配，存在把 `~/.toolkitrc.local.json` 误当项目本地层命中的风险。两处本地自检全绿，仅在 CI 的 Windows runner（临时目录为短名）才暴露。
- **与索引`C-23`「测试假现场须与真实现场形态一致」、`C-29`「门禁与测试的环境无关性」配套**：`C-23` 管「测试的假现场形态失真」、`C-29` 管「门禁步骤依赖运行环境」，本条管「**被测实现**对现场形态差异的归一缺失」；三者同属「形态差异只在特定环境暴露」一族，互为补充。
- **理由**：形态差异是否出现取决于运行机器的用户名长度、临时目录设置与文件系统挂载方式，缺陷在作者机器上默认不可见且**静默降级**，直达用户真机。
