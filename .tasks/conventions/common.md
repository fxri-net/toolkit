# 全端通用规范（common）

> 归属：common。跨面原则：改规则、改门禁、设计对外接口时适用。索引见 index.md。

## C-28. 规则落门禁

规则层新增或强化一条「可自动检出」的要求时，**或复核发现既有要求尚无检测入口时**，须在**同批变更**内补落检测入口（`toolkit tasks check` / `pnpm verify` 内步骤），且入口须置于不可逆动作**之前**；只写进规则文件或核对清单而无门禁覆盖的要求，一律视为纸面规则。

- **要求**：新增 / 强化可检出的要求、或复核发现既有要求无检测入口时，同步问三句——有检测入口吗？入口挂在哪个命令？它跑在不可逆动作之前吗？三问缺一即补齐；检测入口优先并入既有 `tasks check` 软告警清单，不自造新命令与新开关。
- **反例**：`skills/fxri-release-changelog/SKILL.md` 早已规定「变更描述一律以 `类型：` 前缀开头」，但 `pnpm verify` 与 `toolkit tasks check` 均不扫 `.changeset/`——缺前缀只在 `changelog version` 时由 `warnUntypedEntries` 兜底告警，而那一刻 `changeset version` 已消费并删除变更集源文件，告警到达时已无从补写，规则在发版前实际从未生效。同类存量缺口：`skills/README.md` 与 `docs/guide.md` 的技能版本表是 SKILL.md 真源版本的手写投影，核对清单明列「表内版本须与真源一致」，却无用例读取两张表——投影随真源升级而漂移（`fxri-release-changelog` 双写位升 1.1.3、两表仍留 1.1.2）无人拦截；「既有要求只停留纸面」与新增要求同等对待，复核发现即补落入口。
- **理由**：规则的效力不取决于写得多完整，而取决于违规能否被自动挡住；检测时点晚于不可逆动作（发版、消费删除源文件）时，告警只能事后追认，与无告警等价。
- **配套**：与索引 `C-7`「触达核对前置」配套——后者管「规则措辞的文档触达面」，本条管「规则的可执行落点」，两者同为规则生效的必备条件。

## C-29. 门禁与测试的环境无关性

`pnpm verify` 的每一步都须与**运行环境**无关（hermetic），尤以时区为要：凡涉「无时区的墙上时间字符串 ↔ `Date.now()`」比对的测试与步骤，本地与 CI 须在同一时区口径下运行；口径按**数据来源**分两轴——合成数据步骤（`scripts/verify.mjs` 的「单元测试」「覆盖率门槛」两步，被测数据由测试当场构造、与运行环境时区无关）钉 `TZ=UTC`，读真实任务数据的步骤（「本源仓库自检」「任务区体检（tasks check）」「归档块归一核验（tasks normalize）」）钉 `TZ=Asia/Shanghai`，在数据书写时区原地判定。后续新增涉时间的测试 / 步骤须同样按来源选定并固定时区。

- **要求**：新增或修改门禁步骤 / 单测时，问一句「这一步的期望是否随运行环境（时区、locale、路径分隔符、换行符）变化？」——会变化的须显式固定该环境变量，使本地与全部 CI 同轴；时区取值按数据来源选：合成数据取 `TZ=UTC`，读真实任务数据取数据书写时区（本仓库为 `TZ=Asia/Shanghai`）。业务侧跨时区容差（如 `src/date.ts` 的 `MAX_UTC_OFFSET_MS`）只作补充，不能替代测试侧固定时区。
- **反例**：未来时间检测把「无时区的本地墙上时间」按运行环境时区解析后与 `Date.now()` 比对；归档时间戳按东八区墙上时间书写，本地（UTC+8）跑绿、CI（UTC）把 +8 墙上串当 UTC 解析而整体前移 8 小时被判为「未来」，同一份代码在 GitHub `check` / `windows` 两 job 全红、14 条误报——「本地自检通过、CI 才报错」正是非环境无关的征兆。
- **理由**：门禁的价值在于「本地跑绿 = CI 跑绿」；一旦某步依赖运行环境，本地通过即丧失对 CI 的预测力，缺陷只在远端暴露而本地门禁形同虚设。
- **配套**：与索引 `C-22`「门禁单源与时点」配套——后者管「步骤清单单源与关卡时点」，本条管「单步的环境无关性」。

## C-41. AI 优先的人机体验

本工具的主要使用者是 AI，其次是人；功能、输出、错误与文档须先保证 AI 可解析、可自动化、可复用，再兼顾人的可读性与操作便利。

- **要求**：对外契约优先结构化与确定性——机器可读输出走稳定字段（如 `--format json` / `schemaVersion`），stdout 只放数据、告警与诊断走 stderr；交互式能力须同时提供非交互入口（`--yes` 或等价参数），不得让 AI 必须模拟 TTY；错误须给出稳定标识与可执行的下一步；文档先写命令、参数、边界与可复制示例，再补解释。人的体验（可读性、可发现性、安全性）应兼顾，但不得以牺牲 AI 可自动化性为代价。
- **反例**：只做交互向导、没有 `--yes`；关键信息只存在于彩色终端文本或表格；失败只给自然语言、没有稳定字段与下一步；文档只有概念说明、没有可直接复制的命令。
- **理由**：AI 是主要执行者与消费者，AI 体验差会直接导致调用失败、误操作与上下文浪费；人仍负责确认与排障，因此两边都要覆盖，但优先级不能倒置。
- **配套**：与 `C-12`「机器可读输出与诊断提示分流」、`C-26`「降级不静默」、`C-40`「文档信息架构」配套——`C-12` 管输出通道，`C-26` 管失败可观测，`C-40` 管文档按任务组织。
