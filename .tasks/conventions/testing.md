# 测试规范（testing）

> 归属：testing。写或改测试时适用。索引见 index.md。

## C-23. 测试假现场须与真实现场形态一致

测试中用于模拟现场（安装布局、目录结构、路径形态等）的假数据，须与真实环境可能出现的形态一致；被测逻辑对现场形态存在分支判据时，每一种真实存在的形态都要有对应用例覆盖，不得只造一种。

- **要求**：造现场前先枚举被测逻辑会遇到的真实形态（如 pnpm 项目内 / pnpm 全局 / npm、yarn 的真实目录），逐种造现场并断言；形态判据本身也要有纯函数级用例，端到端用例则要跑通「形态变化 → 行为仍正确」。
- **反例**：稳定入口解析的守卫只在「项目内 pnpm 布局」成立，而测试假现场清一色写成 `<home>/node_modules/.pnpm/…`——该形态属项目内布局，全局布局（`.pnpm` 与 `node_modules` 并列）无人覆盖，守卫在全局布局下恒假也拦截不到，缺陷直达用户真机；且判定层只比对 realpath，`status` 仍报「正常」，症状被二次掩盖。
- **理由**：假现场与真实现场形态不符时，测试通过只证明「该形态下正确」，对未覆盖形态零信息量，并给出虚假的安全感。
- **配套**：与索引 `C-17`「测试不复刻被测实现」配套——后者管「逻辑同错复刻」，本条管「现场形态失真」，两者都会让实现缺陷原样漏过，互为补充。

## C-44. 仓库自检脚本的每次改动都要有假现场用例

仓库自检脚本（`scripts/check-*.mjs`）新增或修改校验逻辑时，须在对应测试文件里补假现场用例：一条断言「合规时退出码 0」，一条断言「违规时报出含具体目标的 error」。

- **要求**：沿用既有范式（临时目录搭假仓库 + `spawnSync` 跑脚本）；脚本为兼容裁剪场景而做的容错（缺失文件直接跳过等）也须有用例锁住，防止下次改动把容错改回抛异常。
- **反例**：`check-consistency.mjs` 加规则模块体量棘轮时未配用例，脚本在假现场缺 `templates/rules/` 时直接抛 `ENOENT`，把既有两例测试打破；同一文件上一次加「references 引用校验」也没补用例，同类问题第二次才被发现。
- **理由**：自检脚本本身不在被测面内，没有用例时它失效了也无人察觉；「临时改错再改回」的一次性手测不产生回归保护。
- **配套**：与索引 `C-23`「假现场形态须真实」配套——C-23 管现场是否真实，本条管有没有现场。
