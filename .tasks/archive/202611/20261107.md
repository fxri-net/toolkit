# 调整 usage 初始化向导默认值

## 背景

`toolkit usage init` 的交互向导存在三个默认值与其命令语义相悖的问题：

1. 首次运行的预设默认是「保持关闭」——用户主动执行 `init` 本身就是启用意图，一路回车却得到「什么都没配」，命令成了空操作。
2. 「统计 toolkit 分发的第三方技能」默认「否」——技能从自持仓库经 `toolkit skills install` 装入时属第三方来源，默认关闭会让统计恒为空，用户会误判为工具故障。
3. 末尾「确认写入配置」默认「否」——与上面同一问题，回车即取消。

另有一处现实与文档不符：`docs/usage/index.md` 写着「所有选项都有默认值，直接回车即可完成」，而当前一路回车的结果是保持关闭。

同时 `usage init --yes` 未给 `--preset` 时按「关闭」静默处理，与「用户显式非交互初始化 = 启用意图」同样冲突，按「降级不静默」改为报错。

## 实施方案

1. 在 `src/usage/wizard.ts` 抽出可导出的默认预设常量，交互向导的预设 `default` 改为「已配置 → 保持当前配置，未配置 → 本地 + 一方与第三方」。
2. 预设选项顺序调整为「保持当前配置（已配置时）→ 本地 + 一方与第三方 → 推荐 → 保持关闭 → 自定义 → 高级」，避免默认指针落在列表中部。
3. 末尾「确认写入配置」默认改为「是」。
4. `--yes` 未给 `--preset` 时报错退出（退出码 1）并提示合法取值，不再静默按关闭处理；`--preset off` 语义不变。
5. 单测：改写「未配置过」用例断言新默认；把默认预设常量纳入断言；新增 `--yes` 缺 `--preset` 报错用例。

## 背景

现版 `fxri-plan-to-task` 只在工作流第 1 步写「全部建档后再改第一处文件」，但没有把建档定义为「开始」授权的标准前置：模型可能只建当前任务档就开工；展示表明文「不落档」，长总计划缺少持久载体；任务档模板也未要求自包含，执行到后期依赖对话上下文，压缩或换会话后细节丢失。

## 方案

1. **「开始」= 建档 + 校验 + 开工**：方案已确认时，收到明确的推进授权（语义识别，不写死词汇——如开始、开工、按计划执行、照这个做、执行吧）即按展示表**一次性建完全部任务档**，跑 `tasks check` 通过后才改第一处文件；**单任务方案同样走这一前置**。授权后不再追问「要不要落档」；但**方案未确认时仍须先出方案、等确认**，两条同时写明，避免误读成可以跳过方案确认。
2. **触发词语义化**：技能中写明「授权」的判据是语义指向推进落地，给两组对照示例（授权：开始 / 按计划执行 / 照这个做；非授权：继续评估 / 方案可以 / 先落档 / 再看看），并强调示例非穷举；「先落档」只是任务档维护授权，不等于执行授权。
3. **任务档自包含**：每档写全背景、方案步骤、影响范围、验证方式，并标注「批次 / 计划位置 / 前置与后继」；禁止「详见对话」「见上文」这类指向对话上下文的指代（引用其他任务档或归档路径合法）。执行到第 N 个任务时只读该档即可恢复全部细节；总计划不单独落档，靠各档互链串联。
4. **失败模式新增**：「只建当前任务档就开工」「任务档写『详见对话』」「总计划细节只存在于对话」。判据写清：指向对话上下文的指代（详见对话 / 见上文 / 如上所述 / 前面说过）违规，引用其他任务档、归档路径或规范载体合法。
5. **授权边界**：一条推进授权覆盖当次展示表内全部任务的建档与逐任务交付，但**不覆盖不可逆动作**（发版、推送、打远端标签、全局安装）；中途新增任务需重新确认——**原任务范围内的细化拆分视为已授权，新增独立范围或扩大影响面须重新确认**。
6. **`fxri-plan-review` 复核清单加一条**：是否全部任务已建档、每档是否自包含；与「展示表不落档」的关系写明为「表不落档、档互链」；发现未建档只输出 `需要确认`，不越权写任务档。
7. **档间串联只用「批次 / 计划位置 / 前置与后继」**：串行先后不写 `depends_on`（只用于仍 active 的并行依赖），避免 `tasks check` 误报与恢复时读错顺序。
8. **方案演进**：执行中发现更优做法时更新当前任务档并在完成情况里记录调整；涉及范围扩大的，按第 5 条重新确认，不静默改用户已确认的范围。
9. **建档范围与校验口径**：不出展示表时（单任务）以方案里的实施步骤为建档依据；用户只确认部分任务时按**已确认子集**建档，未确认的任务不建、不执行并在对话中说明略过项；`tasks check` 的「通过」定义为 error 0 且 warn 0，**校验失败则停在建档阶段、报告问题项，不进入实现**；`task-spec.md` 自查清单补「任务档自包含、无指向对话的指代」。
10. **体量控制**：新增内容压缩到约 700 字符以内，`SKILL.md` 保持 ≤200 行 / ≤8000 字符；示例压成一行括注、失败模式每条一行、不复述既有条款。
11. **两段式流程**：用户先说「先落档」再说「开始」时，第二次授权检查已建齐则直接开工，缺哪个补哪个，**不覆盖已建内容**；「开始」不要求重新建档。
12. **任务增删回写**：中途新增 / 裁剪任务时，除更新展示表，还须同步受影响档的「计划位置 / 前置 / 后继」；档间引用一律写任务唯一键，不写 active 路径。

# 改为全局规则上报技能使用

## 背景

Hook 方案依赖各家 Agent 的配置：dsh 的桥接插件虽能加载，但 Hook 进程受运行时文件沙箱限制，写不了家目录下的统计库（诊断输出 `Access to the path ... is denied`）；Trae 还需 IDE 侧额外启用。只要上游配置或沙箱策略变化，采集就会静默失效。改为「全局规则 + 显式上报命令」为一等通道，与 Hook 二选一、由 `usage.channel` 决定，不再依赖任何 Agent 的私有配置。

## 方案

1. 新增 `usage.channel` 配置（`rule` / `hook`，默认 `hook` 兼容存量）落实二选一：
   - `record` 只在 `channel=rule` 时写入；`ingest`（Hook 入口）只在 `channel=hook` 时写入，从机制上杜绝同一调用被记两次
   - 新增 `usage channel [rule|hook]` 查看 / 切换；非法值报错退出（降级不静默）；切换时提示另一通道的已有配置需自行清理
2. 新增 `toolkit usage record --skill <名称> [--skill <名称> ...]`：
   - 成功时静默（stdout 为空、退出码 0），任何失败也不阻断任务（错误只走 stderr）
   - 是否统计、统计哪些来源 / 技能，全部复用 `usage` 配置（`enabled`、`sources`、`skills.mode`），规则里不写死技能范围
   - 字段采集按 `capture.*`；规则只传技能名，触发词 / 参数不由规则转述
   - 会话标识优先 `--session`，其次已知环境变量，最后按日期兜底；事件 `agent` 记 `rule`（`shouldRecord` 对 `rule` 放行 Agent 开关，语义比 `manual` 清楚）
   - 多技能一次上报，每条事件独立 eventId；同批同一技能只记一条
   - 只统计 **toolkit 管理的技能**（包内一方 + toolkit 状态里登记的第三方来源），且**必须命中 `usage` 配置**：`enabled`、`sources.firstParty` / `sources.thirdParty`、`skills.mode`（all / include / exclude）。toolkit 装过但来源未开启、或未列入范围的技能同样不统计；`sources.unmanaged` 对规则路径不生效。非托管技能静默忽略、不写事件，文档写明边界（可走 Hook 或 `usage log` 手工补录）
3. `usage init --channel <rule|hook>`（交互向导同样询问，默认 `rule`）：选 `rule` 时只写采集配置、不安装任何 Agent 的 Hook，并输出 `usage rule` 提示；该路径不依赖本机是否检测到 Agent；选 `hook` 时维持现有按 Agent 安装流程；`--preset off` 与 `--channel` 同时出现时 **off 优先**，保持关闭
4. `usage info` 展示当前通道与规则入口；`hooks status` / `doctor` 在「已安装 Hook 但通道为 rule」或反之时给出告警
5. 重写 `toolkit usage rule` 输出：规则只要求「每批工具调用结束后，若本批用到技能则合并执行一次 record」，并在文案里点明「一批 = 同一批工具调用全部返回后；本批未用技能则不调用」，不枚举技能、不写死字段；关闭方式是删规则段或 `usage disable`；与 `docs/rules/usage.md` 的规则全文保持同源并加一致性测试；当当前配置不会统计任何技能（`skills.mode=none`、`mode=include` 但列表为空、或来源全关）时，输出前用 stderr 提示，避免规则空转
6. 文档改为二选一结构：`docs/usage/agents.md` 两栏对比（规则 / Hook 各自启用、关闭、卸载、限制）；dsh 标注沙箱限制、用规则自报；`docs/cli/usage.md` 补 `record`、`channel`、`init --channel`、`info` 展示；`docs/config.md` 补 `usage.channel`；`docs/rules/usage.md` 同步并更新锚点
7. 本机：dsh 桥接插件与 Hook 已卸载；Trae / Copilot Hook 由用户关闭；规则段由用户复制到全局规则

## 背景

## 20261107-唐启云-修正技能的规划态提交纪律

> 负责人：唐启云　状态：已完成　范围：toolkit　完成时间：2026-11-07 12:18

# 修正技能的执行态闸门与提交纪律

## 背景

用户发来一条需求 / 意见清单（编号 1–5，末项写「落档，继续评估」），本意是**继续沟通方案**；模型在评估完方案后直接进入执行：创建任务档、编辑文件、执行 2 条命令、调用技能，直到用户强行中断并补发「先出方案，等我说开始」，才回到预期流程。此前还出现过规划过程中把任务档更新逐次提交的问题（已撤回 6 个纯过程提交）。

## 原因分析

1. `fxri-plan-to-task` 的「开工闸门」写了「方案确认 ≠ 执行授权」，但没有把「需求清单 / 意见 / 继续评估」归类为**讨论态输入**，缺少「收到这类输入先出方案、等明确开始」的强制顺序
2. 把「落档」与「继续评估」混为一谈：两者含义不同、可单独出现；且容易被当成某一句固定话术，而不是按语义识别
3. 「落档」被误当成执行动作：技能没有区分**讨论态 / 方案态 / 执行态**，也没有要求在任何写操作前声明当前所处状态
4. 缺少「一次回复内只出方案、不得同回复内顺手执行」的约束，评估完方案就直接动手
5. 用户此前的「开始 / 按计划执行」授权没有按批次失效的规则，容易被沿用到新的需求讨论上
6. 提交纪律缺位：技能只写「若提交代码，按归档 → 验收 → 提交」，没有「规划态不提交、归档后每任务提交一次」

## 方案

1. `skills/fxri-plan-to-task/SKILL.md` 增加**三态闸门**：
   - **讨论态**：只分析、出方案、回答问题；不改仓库文件、不执行实现命令
   - **方案态**：输出结构化方案并明确「等你说开始」；此态仍不改代码
   - **执行态**：仅在用户明确说「开始 / 按计划执行」后进入，才允许写代码、跑实现命令、提交
   - 「需求清单、意见、问题、继续评估、复核」都是讨论态输入，不构成执行授权，且**不得把某一句固定话术当成唯一触发**，按语义识别
2. 区分两类讨论态意图（可单独出现、含义不同，不混为一谈）：
   - **落档**：任务档维护意图（创建 / 更新 / 拆分合并 / 复核后修订任务档）；变体如「记一下」「登记」「建档」「更新任务」「建个跟踪」，按语义识别
   - **继续评估**：只读复核意图（分析方案、列疏漏与建议）；变体如「再评估」「复核一下」「看看合不合理」「有没有漏」，按语义识别
   - 两者关系：评估默认只输出结论、不写文件；需要把评估结论写进任务档时，属于落档意图（可由同一句同时表达，也可分次表达）
   - 两类意图都**不等于执行授权**
3. 「落档」按下方《落档的动作边界》执行：允许任务档类操作，但仍属规划态，不得进入实现或提交
4. 授权按批次生效：用户的「开始」只对当次列出的计划有效；新需求需重新确认
5. 提交纪律：提交只在任务**归档之后**按收尾规则执行一次；一个任务允许多次提交仅限多次交付，不为任务档修订单独提交
6. `skills/fxri-plan-to-task/references/task-spec.md`：同步「任务档的规划态修订不进入提交」
7. `skills/fxri-plan-review/SKILL.md`：明确「复核结论落档由 plan-to-task 执行，但落档不提交」
8. 两个技能版本 +patch（双写位），同步 `skills/README.md` 与 `docs/guide.md` 两张版本表；新增 patch 变更集
9. 执行注意：本批改动技能后，后续任务开始前须重新读取磁盘上的新版 SKILL.md，不能沿用会话上下文里的旧版本

## 落档的动作边界

「落档」= 对任务档的规划性维护，允许在讨论态 / 方案态执行，不视为进入执行态：

| 动作 | 是否属于落档 | 说明 |
| --- | --- | --- |
| 创建任务档 | 是 | 新需求 / 新任务登记 |
| 更新任务档（方案、影响范围、决策、完成情况草案） | 是 | 方案沟通中的正常修订 |
| 复核 / 重新评估任务档 | 是 | 含增删方案条目、调整任务拆分 |
