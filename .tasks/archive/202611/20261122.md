# 多任务冲突体检

> 计划位置：第 2 个（共 2 个）；前置：无；后继：无

## 背景

计划表里任务多起来后，任务之间会「打架」：改同一文件不同区块、先后顺序颠倒、契约字段各写一套、文档页与 changeset 争用。当前靠用户每次手动补一句「定稿，然后所有任务综合评估一下，确保不冲突，再列总计划表」，陈述成本高且容易漏说。

结论：值得沉淀，但**不新建技能**——并入现有 `fxri-plan-task` 的任务分解步骤，达到「有两个及以上任务」时自动执行，用户无需再记这句话。`fxri-plan-review` 增加同一维度的复核。

## 实施方案

1. `skills/fxri-plan-task/SKILL.md` 第 0 步（任务分解与计划表）追加「冲突体检」：计划表形成后、建档前自动执行，条件为表内 ≥2 行。主文件只留触发条件与三行规则，细则按需加载，避免上下文膨胀。
2. 新增 `skills/fxri-plan-task/references/conflict-check.md`：检查维度、判据、分级与输出模板。
   - 文件争用：两任务改同一文件 / 同一区块
   - 顺序依赖：后置任务改的接口或结构，前置任务依赖其现状
   - 契约一致：字段名、信封、schema、命令名在各任务中是否同口径
   - 术语与版本：同一能力是否被叫成两个名字、版本括注是否冲突
   - 文档争用：多任务改同一页面 / 同一节
   - 变更集粒度：同一对象是否被拆到多个任务各自建变更集
   - 跨仓耦合：是否有任务依赖另一仓未完成的交付
   - 授权互斥：两个任务都需要发版 / 推送 / 全局安装，是否串行并合并授权
   - 共享测试现场：是否争用同一 fixture 目录或同一临时文件
3. **分级**：冲突分「阻断」与「提示」——阻断项必须先改顺序或拆分，提示项记录在表内不阻断；无冲突时不输出空表，只回一行「冲突体检：无」。
4. 触发时机：新建计划表、追加任务、调整顺序三种情形都重跑；单任务方案不触发。

# 升级迁移编排

> 计划位置：第 1 个（共 2 个）；前置：无；后继：20261122-唐启云-多任务冲突体检

## 背景

升到 2.0 要手工完成多件事：三层配置段名与旧键、`package.json` 的 prepare 钩子与旧命令名、技能旧名产物与状态文件、conventions 载体结构、历史 `.bak`。能力已分散在 `init`、`convention upgrade`、`skill install`、`update-check`，但用户必须照着升级页逐条手做：不可视、易漏、会留残留，也没有统一的「迁移完成」判据。

目标是一个长期存在的统一入口：迁移前说清要动什么，过程逐项可见，结果完整汇报，迁移后不留 v1 痕迹。

## 实施方案

### 1. 版本模型（两条轴，避免越做越重）

- **包大版本 hop**：注册表只保留「上一个 major → 当前 major」一档。到 v4 时只保留 `v3 → v4`，删除 `v1 → v2` 的规则与文档；跨多个 major 不硬扛，报错并给出「依次安装 v2 / v3 并各自执行 upgrade」的步骤。
- **配置 schema 修订**：与包版本解耦，覆盖 major 内部的段名 / 键变化（如 1.x 内部的键调整）。规则按「检测到的旧形态」匹配，不依赖旧补丁版本号。
- 不引入显式 `schemaVersion` 标记：以特征检测判定旧形态，避免为迁移在用户配置里新增键；若后续确实需要，再按独立任务加。
- **版本门禁**：迁移前读项目依赖里的 `@fxri/toolkit` 版本；低于目标 major 时默认拒绝（v1 CLI 读不懂 v2 配置，迁完反而坏），提示先升级依赖，`--allow-old-dependency` 才能越过并写警告；`workspace:*` / git 地址等非 semver 依赖不猜版本，只提示；用 `npx` / 全局运行、项目无依赖时放行。

### 2. 注册表与引擎

- 新增 `src/upgrade/registry.ts`：纯数据规则表（字段见 §15），`detect` / `apply` 放独立模块；surface 取 `config / project-file / skill / convention / backup`。
- 新增 `src/upgrade/engine.ts`：检测 → 生成有序计划 → 逐项应用 → 复检残留；全程幂等，写前判后写，单文件原子写。
- 并发保护：只在**应用阶段**加锁（预览 / `--check` 不加）；涉及多层时按「项目 → 全局」固定顺序获取，避免两个进程交叉持锁；陈旧锁按既有 skills 锁的 TTL 规则接管。
- 备份清单 `manifest.json` 记录「改写的原文件」与「新建的文件」；`--restore` 既还原原文件，也删除本次新建的文件，恢复后与迁移前逐字一致。

`docs/upgrade-v2.md` 顶部（页面重构为「一键迁移 + 手工兜底」）、根 `README.md`、`docs/getting-started.md`、`docs/cli.md` 命令表、`toolkit --help` 尾部；`update-check` 的 v1→v2 提示改为「运行 `toolkit upgrade`」。所有步骤随包分发，符合 C-49。

### 8. 残留分级与 `--check` 语义

- **自动残留**：注册表能处理却仍未处理（旧段名、旧钩子、旧技能名等）→ `--check` 退出 1
- **手动项**：规则快照正文、CI 文件里的旧命令名、无法确认归属的目录 → 只报 warn，不计入退出码，否则 CI 会永久红
- `status` 的「待迁移」提示复用同一判定；只有自动残留会标成待处理

### 9. 文档与支持矩阵生命周期

- 支持矩阵由注册表生成，文档不手写；每次增删 hop 由生成器同步
- 某个 hop 退役（如 v4 删除 v1→v2）时，对应迁移页同步退为历史说明并入 CHANGELOG，不再以「当前升级指南」出现

### 10. 行为等价与归属判定

- **硬不变量**：迁移前后 `config status` 的有效值逐项一致（三层合并结果），技能集合一致；迁移只改形态，不改行为。规范载体只报结构变化，不承诺内容等价。
- **技能归属优先级**：状态文件登记 > 指向包内 `skills/` 的软链 > 带本包标记或曾用名声明的副本（只报不删）> 其他（manual）。删不掉的旧名目录一律进报告，不猜归属。
- **固定顺序**：配置 → 工程文件 → 技能 → 规范载体 → 备份收编；规范载体的任务目录取自迁移后的配置，避免旧 `tasks.dir` 指错。

### 11. 写入形态与工程文件保护

- 配置与 `package.json` 保留原缩进（2 / 4 / tab）与键序，UTF-8 无 BOM、LF、末尾换行；只对目标键做最小替换，其余键逐字不动。
- `scripts` 只按命令 token 改写（以 `toolkit` 开头的命令段）；字符串里出现旧命令名但不在命令位置的一律不改，进报告。
- 只改 `prepare` 钩子，不动 `preinstall` / `postinstall` 等其他生命周期钩子。

### 12. 失败、分层与退出码

- **层隔离**：全局层不可写（CI、容器、只读 home）不阻断项目 / 本地层，逐层报告；自动项失败整体退出 1。
- 失败即停并写入 manifest 的已应用项；重跑按残留继续，不自动回滚，回滚由 `--restore` 显式触发。
- 退出码：`0` 成功 / 已 v2 / 无资产；`1` 自动残留或应用失败；`2` 用法错误或非 TTY 缺参；`130` 取消。

### 13. 机器可读契约

- `--format json` 的 `data.plan[]` 项固定字段：`id / surface / action / risk / files[] / status / reason`；`status` 取 `planned / applied / skipped / manual / failed`。
- 文本与 JSON 由同一份计划数据渲染；诊断与告警走 stderr，stdout 只放机器可读输出。

### 14. 注册与裸命令语义

- `upgrade` 注册进命令注册表与 `docs/cli.md` 命令总览；`--help` 顶部展示当前支持的 hop 与「跨 major 须逐级」提示。
- 裸 `toolkit upgrade`：TTY 进向导；非 TTY 退出 `2` 并给出等价的 `--yes` 用法（动作型命令不空跑）。

### 15. 规则数据模型（可长期维护）

- 注册表是纯数据（只含元信息与文档链接），`detect` / `apply` 放独立模块，便于生成文档与做一致性校验。
- 每条规则字段：`id`、`surface`、`layers[]`、`introducedIn`、`removedIn`、`dependsOn[]`、`risk`、`manualHint?`。
- `removedIn <= 当前 major` 仍存在 `apply` 视为未清理：`check-consistency` 加一条守卫，防止退役 hop 的代码与文档残留。

### 16. 配置迁移的原子性

- 以**段**为单位整体迁移：段内全部键都能确定映射时才搬移并删除旧段；段内出现未知子键时整段保持原样并进 manual，不做「搬一半、删一半」。
- 同一文件新旧段并存：保留新段；旧段能与新值逐项对齐时删旧段，否则保留并报告差异。
- 解析失败的配置文件一律不改，进 manual 并给原始错误。

### 17. 预览与恢复安全

- `--diff` 输出计划与将改动的文件清单；交互清单为扁平列表（`组 / 项` 前缀），支持组级勾选与单项勾选，风险项默认不勾。
- 备份清单记录每个文件的 SHA-256；`--restore` 先校验再写回，按应用逆序执行。
- 恢复时不覆盖迁移之后被用户改过的文件（哈希不符即拒绝），除非显式 `--overwrite`。
- 备份目录本身排除在残留扫描之外。

### 18. 文档拆分与入口登记

- `docs/cli/upgrade.md` 只放命令参考（参数、退出码、JSON 契约），`docs/upgrade-v2.md` 只放「何时迁、怎么迁」；字段与支持矩阵只在注册表派生页维护，两页互不复制。
- 新页同批登记进 `README.md` 与 `docs/index.md` 的文档索引，并在 `docs/site-nav.json` 挂到 CLI 参考分组；漏登会被集合校验与导航校验拦住。

# JSON信封八键重构

> 计划位置：第 1 个（共 3 个）；前置：无；后继：20261122-唐启云-规范退休与调整

延续 统一JSON信封（见 archive/202611/20261121.md）。

## 背景

2.0 尚未发布，当前报告类 `--format json` 信封为 `{ schemaVersion, command, ok, data, issues }`。`ok` 可由 `code` 或 issues 推导，且缺 `message / extend / debug`，与本地 HTTP 信封 `code / message / data / extend / debug` 字段不齐。参照该信封的迭代结论，发布前按最优解定稿为 8 键超集：

`schemaVersion / command / code / message / data / extend / debug / issues`

前两键标识 CLI 操作，中间五键与 HTTP 信封逐字同形，最后一键承载检查聚合。该设计去掉重复的 `ok`，用整数 `code` 表达业务结论，`extend.exitCode` 单独承载进程退出码。`schemaVersion` 保持 `1`：2.0 是首个携带该契约的发布版本，1.x 没有同形信封，无需递增。

## 实施方案

1. 重写 `src/json-output.ts`：
   - `JsonIssue` 保持 `level / scope / message`。
   - 新增 `JsonEnvelopeInput<T>`：`command`、`code?`、`message?`、`data`、`issues?`、`exitCode?`、`extend?`、`debug?`。
   - `jsonEnvelope` 返回固定 7 个载荷键（`schemaVersion` 仍由 `toJsonText` 前置）：`command / code / message / data / extend / debug / issues`。
   - `code` 缺省由 issues 推导：含 `error` 时取 `422`，否则取 `200`；调用点可显式给 `409 / 500`，或按更严格的失败语义显式覆盖（如 `skill lint --strict` 只含 warn 但已失败时取 `422`）。
   - `message` 缺省：无 issues 取 `成功`；只有 warn / info 取 `成功（N 项提示）`；含 error 取首条 error 的 message。
   - `extend` 合并为 `{ ...input.extend, exitCode: input.exitCode ?? 0 }`（`exitCode` 作为一等入参，不允许被 `extend` 内的同名键覆盖）；`debug` 缺省 `{}`，`issues` 缺省 `[]`，不省略键。
   - `toJsonText` 继续前置 `schemaVersion: 1`，输出键序与上表一致。
2. 全部报告类调用点改为新签名（`rg "jsonEnvelope\\(" src`，当前 48 处，覆盖 config / convention / docs / release / scope / rule / skill / status / task / usage）。删除 `ok` 布尔参数；一般 check 类只传 issues，由构造器推导 code。`scope.ts` 有 5 处 `console.log(toJsonText(jsonEnvelope(...)))` 手工包裹，统一改为 `printJson`。`skill lint` 在 `--strict` 下只含 warn 也可能失败，显式传 `code` 与 `exitCode`。
3. `extend.exitCode` 显式传参，不读全局 `process.exitCode`：由调用点按报告结论与 `--check` 开关计算。`status` 无 `--check` 时即使 `code=422`，`exitCode` 仍为 0；`docs check` / `rule check` 的 `exitCode` 与结论一致。这样可以避免「先打印、后设退出码」导致信封里的 `exitCode` 恒为 0。
4. 明确数据流例外不套信封：`usage data export`、`task export <path>`、`release changeset` 透传保持原格式；`task export .json` 仍为 `{ schemaVersion, summary, items }`。
5. 失败口径不变：报告类业务失败仍在 stderr 报错并保留退出码，不在 stdout 输出半截 JSON；`code` 只表达报告结论。
6. 测试：
   - `json-output.test.ts` 锁定 8 键集合、键序、code 推导、message 缺省、空对象与空数组形态。
   - 各域 JSON 用例改为读 `code / data / issues`，不再读 `ok`。
   - `cli-golden` 快照更新；导出类补「不套信封」对照。
7. 文档与变更集：字段定义只放在 `docs/cli.md` 一处；`docs/api.md`、`docs/cli/exit-codes.md`、`docs/upgrade-v2.md` 与各域 CLI 页改为引用该页，不重复 8 键字段表；`.changeset/cli-json-envelope.md` 改写为 8 键口径（major）。
8. 规范载体：20261122-唐启云-规范退休与调整 会同步 C-48 的 F-4 与相关文档；本任务先确保代码、测试、文档三处一致。

## 设计底座

### 事实分四类，手段分四级（只可向下退）

| 类别 | 例子 | 允许的处理 |
| --- | --- | --- |
| A 代码事实 | 退出码、状态集合、阈值、目录清单、前缀 | 运行期派生；派生不了才生成 |
| B 契约事实 | JSON 信封、配置键、命令元数据 | 代码为源 + 文档生成或指针 |
| C 叙述事实 | 开工词、判定表、流程措辞 | 一处散文 owner，其余指针 |
| D 外部约束 | `package.json` engines、CI 配置 | 一致性校验兜底 |

手段阶梯：**派生 → 指针 → 生成 + `--check` → 一致性校验**。同一事实不得同时存在生成器与校验器两份实现。

### 落地规范（防「统一了又长回来」）

- **事实 ID**：`F-<n>` 稳定编号，不复用；owner 变更须同批改注册表并写 `history.md`
- **生成块标记**：统一 `<!-- toolkit:<fact-id>:start -->` / `:end`，缺标记即 `--check` 失败并给出修复命令
- **守卫载体优先级**：单测 → 现有 `check-*.mjs` → 新脚本；新增脚本须带 `--self-test`（C-44）
- **生成物入库**：生成块与产物必须提交（包内文件直接分发，不在发布时补生成）
- **散文数字禁令**：文档 / 技能正文不写可派生的数量（模块数、技能数、脱敏类数、状态数、字符阈值）
- **生成器输入契约**：脚本不得以正则解析 TS 源码结构；优先读数据文件，必须解析源码时加「解析条数 == 结构出现次数」
  不变量并在 `--self-test` 覆盖（现状：`scripts/generate-exit-codes.mjs` L18-25 与
  `scripts/generate-upgrade-table.mjs` L13-20 均为正则解析，需补不变量）
