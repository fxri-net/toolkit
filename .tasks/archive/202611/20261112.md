## 20261112-唐启云-门禁提速

> 负责人：唐启云　状态：已完成　范围：toolkit　完成时间：2026-11-12 13:43

# 门禁提速

> 计划位置：第 1 个（共 4 个）；前置：无；后继：20261112-唐启云-预演迁移标记、20261112-唐启云-旧名清理前确认新名、20261112-唐启云-残留扫描路径去重

## 背景

本机 `pnpm verify` 约 180 秒。分步实测：单测+覆盖率 79s（html / json 报告只占约 3s，插桩是主成本）、文档站构建 35s、
打包构建 20–40s、并行检查组 16–20s、其余约 10s。三个重步骤互不依赖，却排在一条串行链上。
对照 GitHub CI 并不更快，观感差异主要来自 Linux 文件系统、Defender 实时扫描、每步 pnpm 垫片启动与多 job 并行。

## 实施方案

1. `scripts/verify.mjs` 改为三阶段：并行检查组 → 重步骤并发（单测+覆盖率 / repo-guard / 构建 / 文档站构建）→ 串行收尾。
2. 热门步骤绕过 pnpm 垫片：用 `process.execPath` + 本地包 bin 直调（`createRequire` 解析，失败回落 `pnpm exec`），
   覆盖 tsc / vue-tsc / eslint / vitest / tsup / vitepress。
3. 门禁里的覆盖率只出 `text` 报告；`json` / `html` 留给手动 `pnpm test:coverage`（CI 未消费这两个产物）。
4. `typecheck:docs` 复用 `docsNeeded`：未触及 `docs/`、`README.md`、`skills/` 时跳过；CI 环境仍强制全量。
5. 每个步骤打印自身耗时，末尾给并行段 / 串行段汇总，后续优化有据可依。
6. 检查项一个不减；并发导致单测超时或内存吃紧时回退为「文档构建与单测并发、构建串行」的保守版。

## 影响范围

- 代码：`scripts/verify.mjs`。
- 文档影响：无（验收清单真源不变，AGENTS 只引用聚合命令）。
- 用户可感知：无；本地与 CI 门禁耗时下降。
- 产物：无变更集。

## 验证方式

- 基线：本机 `pnpm verify` 约 180 秒（2026-11-12 实测）。
- 改动后：同机跑一次 `pnpm verify`，记录分步耗时与总时长，目标 ≤ 130 秒；检查项仍为原有集合。
- 归档在前、验收在后。
- 回滚：单次提交整体 revert，恢复原串行调度。

## 完成情况

- `scripts/verify.mjs`：改为「并行检查 → 重步骤并发（单测+覆盖率 / 构建 / 文档构建）→ 串行收尾」三阶段；每步打印耗时与阶段小计。
- 绕过 pnpm 垫片：tsc / vue-tsc / eslint / vitest / tsup / vitepress 直调本地包 bin（`createRequire` 解析，失败回落 `pnpm exec`）。
- 覆盖率在门禁内只出 `text`；`json` / `html` 留给 `pnpm test:coverage`（CI 未消费这两个产物）。
- `文档类型检查` 与 `文档站构建` 复用改动面判断：未触及 `docs/`、`README.md`、`skills/` 时跳过；`--skip-docs` 仍只裁剪构建、不裁剪类型检查。
- 新增 `--local`：忽略被 IDE / 终端注入的 `CI` 变量，恢复改动面裁剪与 eslint 缓存；检测到 CI 变量且非 GitHub / GitLab 时提示该入口。
- `vitest.config.ts`：超时由 15s 提到 30s，覆盖并发重步骤时的偶发超时（保留余量，不放宽断言）。
- 实测（同机、CI 变量注入的终端）：
  - 基线：约 180s。
  - 改造后默认（CI 全量）：160.1s；分步：并行检查 23.2s、单测+覆盖率 112.6s（并发）、构建 38.4s、文档 76.3s、收尾约 20s。
  - `--local`（改动面裁剪 + 缓存）：127.0s，达到 130s 目标。
- 放弃的方案：单测与构建 / 文档三并发在部分运行时会出现随机超时（已用 30s 余量兜住）；把 repo-guard / 文档无损移入并发段反而被拖慢（23s / 15s），故保留串行。
- 回滚：单次提交整体 revert，恢复原串行调度与 15s 超时。

# 技能改名后的选择集与产物管理

> 计划位置：第 1 个（共 1 个）；前置：无；后继：无

## 背景

产物修剪也按名字查真源。来源内技能改名后三路同时失控：

1. 旧名在新来源中已无真源，链接成断链；`installSkills` 保留历史条目时用 `existsSync` 判定现场，断链恒为 false，
   条目被静默剔除（`src/skills/install.ts` L311-329）。此后 `status` 无从得知该名字，`--prune` 也因 `byName` 缺失跳过
   （`src/skills/install.ts` L165-190），断链永久隐形。
2. 新名不在已保存名单里被判「未选择」（`src/cli.ts` L298-309、`src/skills/status.ts` L229-240），
   而 `status` 对 `not-selected` 不输出（`src/skills/status.ts` L217），既不安装也不提示。
3. `saveGlobalSelection` 按本次安装结果覆盖写名单，某来源本次零装即写成空数组（`src/skills/install.ts` L435-453），
   把一次性失效固化为永久排除。

本机实测：4 个全局目标目录各残留 3 个断链（共 12 个），`toolkit skills status --scope all` 仍报「所有已纳入的目标均正常」；
`toolkit skills uninstall --skills <旧名> --dry-run` 无输出，即卸载同样管不到。

## 实施方案

### 1. 改名声明（previousNames）

- 两处声明、清单优先：`skills.json` 条目级 `previousNames: string[]`；`SKILL.md` frontmatter `metadata.previousNames` 行内数组
  （与既有 `requires` 同为缩进键形态）。
- 校验（`src/skills/source.ts` 的清单与 frontmatter 解析）：只认一级、去重、不得与当前名相同、同一来源内不得与其他技能名或别名冲突；
  违反即整源报错拒绝加载，不静默剔除。不支持多级改名链（A→B→C 需两步声明）。
- 用途：选择集按别名替换并去重；状态条目按别名改名（保留 mode / version）；旧产物按旧名定向清理
  （link 形态直接摘除，copy 形态与真源一致才删，否则报冲突）；`status` 文案提示「已改名为 X」。

### 2. 选择集解析单点化与失效自愈

- 新增 `src/skills/selection.ts`：输入统一技能条目与按来源保存的名单，输出每个来源的有效名单与失效名单；
  `src/cli.ts` L298-319 与 `src/skills/status.ts` L229-240 共用，消除「全局面按白名单、项目面对外部源默认全选」的口径分叉。
- 整源失效（该来源已保存名单非空且与当前技能集零交集）：按默认口径重算——内置源取 core、外部源全选，并向 stderr 告警一行（列出失效名）。
- 部分失效：保留有效名、剔除失效名并告警，新增名不自动入选（避免第三方来源往用户环境塞技能）。
- 内置源与外部源、全局面与项目面同一口径。

### 3. 状态与产物

- `src/skills/install.ts` L311-329：保留判据由 `existsSync` 改为 `lstatSync` 成功，断链仍属现场，用户手工删除的条目才丢弃。
- `pruneEntries`（L165-190）：来源已无此名的条目——登记为 `link` 直接摘除，`copy` 无法校验则保留并报冲突。
- `saveGlobalSelection`（L435-453）：某来源本次零装时删除来源键，不再写空数组。
- `removeSkills`（L552-579）：状态未登记但用户显式点名的名字，逐目标检查同名链接/junction 且目标落在已登记来源根或本包技能目录下才摘除，
