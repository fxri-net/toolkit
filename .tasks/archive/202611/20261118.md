## 背景

执行授权目前靠语义推断，且规则明文禁止闭集：SKILL.md「不得把固定话术当唯一触发，按语义识别（非穷举）」，
另有「措辞只是线索，不作开关」（SKILL.md 开工闸门）与「判据看意图与最终动作，措辞只是线索」（docs/rules/ai.md）。
结果是「继续 / 推进 / 按这个做吧 / 方案可以」等词都可能被当成开工。

对外口径也互相矛盾：docs/handbook.md 把「按这个做吧」列为推进授权，而 SKILL.md 的 description 又把同一短语列为建档触发。

用户诉求：只有明确的开始词才开工，其余保持评估态；但「继续」在开工被用户打断后必须能恢复执行，不能一刀切排除。

## 方案

### 1. 授权粒度二分

| 粒度 | 判据 | 触发条件 |
| --- | --- | --- |
| 对象级（微操作） | 明确指向单个文件 / 单条命令 / 单个改动 | 直接执行，无需开工词，范围止于指明对象 |
| 方案级（批次） | 按计划实施多步、多文件或多任务 | 开工词 + 范围明确 + 方案已定稿 |

对象级授权不得夹带方案步骤：「把这些都改一下」若指代的是方案任务清单，按方案级处理。

⚠️ 与既有条文正面冲突须一并改写：`skills/fxri-plan-to-task/SKILL.md` L73 现写「动作型短语不等于执行授权：统一掉 / 改一下 / 删掉 / 修一下 / 处理掉等说法只表达目标，助手应回到方案态」。
该条按「无对象」场景成立，但一刀切会否掉对象级授权。改写为按宾语判定：**有明确单点对象**（把 X 改成 Y、删掉这段、跑一下某测试）→ 对象级执行；
**无对象或指代方案清单**（把这些都改一下、统一掉）→ 回方案态。两句并存会让 AI 按旧条退回方案态，必须同批改掉。

### 2. 授权状态机

```text
U 无授权（讨论 / 方案 / 定稿）
A 执行中（含批次待续）
P 已暂停（授权挂起，未撤销）
```

| 事件 | 转移 |
| --- | --- |
| U + 开工词 + 范围明确 + 已定稿 | → A |
| A + 暂停词 / 用户提问 / 新话题 | → P（写进度锚点） |
| P + 恢复词 | → A（回显范围 → 复核现场 → 继续） |
| A 或 P + 取消词 | → U |
| A 或 P + 方案变更 | → U（回定稿） |
| 任意 + 会话结束 / 上下文重置 | → U |

状态不确定一律按 U；状态靠任务档的 `status: 进行中` 与正文进度锚点重建，不靠记忆。

⚠️ **状态维度不止两套，落地时须在 SKILL.md 里写明映射，否则同文件会堆起「三态」「四态」「六态」三组数字状态互相打架**：

| 维度 | 取值 | 回答什么 |
| --- | --- | --- |
| 任务状态 | 待办 / 进行中 / 阻塞 / 搁置 / 已完成 / 已放弃（任务 1 引入） | 这件事在任务区处于什么处境（写在 frontmatter） |
| 闸门态 | 讨论 / 方案 / 定稿 / 执行 | 本轮允许做哪类动作（能否写仓库文件） |
| 授权态 | U / A / P | 方案级授权凭证是否在手、是否处于暂停 |

对应关系：闸门态「执行」= 授权态 A；授权态 P 落在闸门态仍属「执行」，只是挂起；U 可落在讨论 / 方案 / 定稿任一闸门态。
任务状态是磁盘上的持久事实，另两个是对话内的会话状态，三者互不推导——任务档 `status: 进行中` 不代表授权态是 A（跨会话即为 U）。

术语约定：分别叫「任务状态」「闸门态」「授权态」，**不再使用「三态 / 四态 / 六态」这类数字叫法**——数字会随版本失效，
且三组数字相邻时读者无法判断在说哪一个。

⚠️ 「继续」的双重歧义须给判据：会话内且存在 active 上下文 → 按上表解释为恢复执行 / 推进下一步；
新会话、无上下文、或明确带「上次 / 做到哪」→ 判为 `fxri-session-recap` 的恢复现场，只读。两者都叫「继续」，缺判据会互相吞掉。

### 5. 语义护栏

- **否定优先**：「先别开始」「不用执行」一律不动作
- **引述与假设不算**：转述、假设、教学语境里的触发词不构成授权
- **问句不算**：问句只回答；例外是 AI 上一轮明确询问「是否开始」，用户答「可以 / 好 / 开始」构成授权
- **显式覆盖**：「别评估了，直接做」以最后的显式动作意图为准
- **条件式**：条件满足后先回显再执行；条件判断带主观性时先确认
- **限制粘性**：「别提交 / 只改 X」在本批次内持续有效，优先于常驻授权

### 6. 恢复三联

回显范围（恢复哪项、暂停在哪）→ 复核现场（git status、任务档进度锚点、期间方案是否变更）→ 再动手。

### 7. 暂停时写进度锚点的授权归属

写进度锚点是**暂停流程内的组成部分**，随暂停动作一并获准，不需要额外开工授权；写入范围只限任务档正文的进度锚点与 `updated`，
不得顺带改方案、改状态以外的字段或改代码。恢复态下若发现锚点缺失，先补记再续做。

### 8. 失效条件

会话结束、上下文重置、方案变更、范围扩张、取消词、工作区被外部改动。

**批次授权不跨会话**：新会话一律回 U，须重新给开工词；不把「批次授权：是」写进任务档正文——那会把对话状态塞进任务记录，污染任务档语义。
会话内批次未跑完即被暂停时，靠任务档的 `status: 进行中` 与进度锚点重建现场，再按 U 态重新索取授权。

### 9. 不可逆动作

发版、推送、发布、删远端、全局安装在任何状态都逐次授权，不随「继续」继承。

## 关键词全量盘点

关键词按动作语义分为十六族（见上表），另有三类需特别处理：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 复合句 | 先评估再开始 | 允许顺序授权；阶段切换回显，评估改变方案则回定稿 |
| 冲突句 | 不用评估了，直接做 | 显式覆盖生效，按执行处理 |
| 夹带句 | 开始吧，顺手把文档也改了 | 原范围执行，扩面单独确认 |
| 英文混用 | start、go ahead、proceed、continue、resume、pause、stop、cancel | 与中文词表同义，按状态解释 |
| 语气词 | 吧、呗、试试、看看 | 语气不改变动作类型；「看看」属只读 |

## 与搁置状态的交叉歧义

「先放着 / 以后再说 / 先搁置」有两种含义：指当前这一步是会话暂停；指整个任务是任务状态搁置。
判据看宾语是「这一步 / 这里」还是「这个任务 / 这件事」；拿不准问一句。

# 新增搁置任务状态

> 计划位置：第 1 个（共 2 个）；前置：无；后继：20261118-唐启云-收紧执行授权触发

## 背景

任务区当前只有执行状态（待办 / 进行中 / 阻塞 / 已完成 / 已放弃），没有「已建档但本阶段不投入」的承载位。
用户诉求：任务先排起来、但列计划与恢复现场时不被当成当前工作。

现状的绕行做法都不合适：用阻塞会把「主动不排期」误表达成「外部卡点、等待解除」；用已放弃要进归档、重启须重写档且污染放弃率；
自造 frontmatter 字段会触发 check 的未知字段软告警，破坏 warn=0 门槛；另建目录会命中游离任务文件告警。

## 方案

### 状态语义与流转

```text
待办 ⇄ 搁置          建档即搁置：先排着
进行中 → 搁置        做到一半暂缓
阻塞 → 搁置          决定不跟进，但保留
搁置 ⇄ 阻塞          重启条件变成外部卡点 / 卡点解除但暂不投入
搁置 → 待办          唤醒（须用户确认）
搁置 → 已放弃        终结（须 completed）
搁置 ✗→ 已完成       须先唤醒，避免「没做就算完成」
已完成 → 搁置        仅限尚未归档的 active 档；须清空 completed（改主意，撤销完成结论）
已归档 ✗→ 搁置       归档块不可变，不给改；确有需要走新任务并标注来源链
```

- 与阻塞的分界（判定问句）：依赖明天就绪会立刻开工 → 阻塞；不会 → 搁置
- 与已放弃的分界：搁置不终结、不归档、可唤醒；放弃是终结记录
- 唤醒归入待办（不是进行中），保持「进行中 = 正在动手」的口径
- 与「会话暂停」的分界：「先放着 / 以后再说 / 先搁置」的宾语是「这一步 / 这里」→ 会话暂停；宾语是「这个任务 / 这件事」→ 任务状态搁置。
  后者按本条落状态，前者属执行授权状态机的暂停，见 `20261118-唐启云-收紧执行授权触发`；拿不准问一句
- 转回非终结态须清空 `completed`：`check` 只校验「终结态缺 completed」，不校验「非终结态残留 completed」，
  已完成任务改回搁置时若不清理会留下自相矛盾的时间字段。此约束由技能条文承载，不加 check 告警
- `已完成 → 搁置` 允许且只允许发生在尚未归档的 active 档：归档块不可变是既有纪律，已归档任务不给回改，
  需重做时新建任务并标注 `延续 {原任务名}（见 archive/{YYYYMM}/{YYYYMMDD}.md）`

### 配套机制（状态本身不够，以下四条决定它是否好用）

1. 入场规则：建档时用户表达「先不做 / 以后再说 / 排着 / 不急」，直接落为搁置；搁置档正文必写四行——搁置原因、重启条件、进度锚点（已完成到哪、剩余什么、关键上下文）、搁置日期
   - ⚠️ 写法须避开 check 的游离待办扫描：`check` 把行首 `- 待评估 / 待排期 / 待确认 / 待核对 / 待实施 / TODO` 判为未闭合待办并告警。
     搁置档天然会写「以后评估」，须写成叙述句（`- 重启条件：季度复盘时再评估`）而非 `- 待评估：季度复盘`，否则搁置会稳定产生告警噪音
2. 视野规则：不进展示型计划表、不进恢复输出的「建议的下一步」；恢复时 L0 索引给一行「搁置 N 项」，L1 只读摘要（frontmatter + 上述四行），用户点名或盘点时才展开
3. 复盘规则：恢复与收尾时盘点 `toolkit tasks list --status 搁置`，给三选一（唤醒 / 继续搁置 / 放弃）；以正文「搁置日期」为计时基准判断 90 天与 1 年（frontmatter `updated` 会被任意编辑刷新，只作近似参考）
4. 唤醒规则：唤醒即复核原方案是否仍成立，不直接沿用；唤醒时重排批次与计划位置；检查下游 depends_on 是否因此解封

## 覆盖性评估

### 场景盘点

| 场景 | 一个搁置能否覆盖 | 补什么 |
| --- | --- | --- |
| 本阶段不做、以后确定做 | 能 | 无 |
| 不确定做不做 | 能 | 重启条件可写「季度复盘再定」 |
| 等外部依赖、就绪即开工 | 不宜 | 走阻塞，判定问句兜底 |
| 做到一半暂缓 | 能 | 进度锚点三行 |
| 多个搁置项排序唤醒 | 不能 | 重启条件文本排序，暂不引入优先级字段 |
| 到期自动回到视野 | 不能 | 用盘点节奏替代，不引入日期字段 |
| 未成形的原始想法 | 不应入任务区 | 任务档要求自包含，想法池另置，不混入 |
| 搁置任务被下游依赖 | 能建档但不拦 | 盘点时检查下游是否悬空 |
| 原批次与计划位置 | 能 | 保留历史行，恢复排序时排除搁置，唤醒时重排 |
| 唤醒时方案已过期 | 能但不自动 | 唤醒即复核原方案 |
| 长期搁置变垃圾场 | 不能 | 90 天提示、1 年建议终结 |
| 多人协作旧版 CLI | 不能 | 旧版读到搁置会报 status 非法，须同步升级 |
| 统计口径 | 能 | 滞留排除、状态分布单列 |
| 方案内部分任务搁置 | 能 | 展示表列但标「搁置，本轮不执行」 |

### 成熟设计对照

| 体系 | 对应做法 | 启示 |
| --- | --- | --- |
| GTD | Waiting For / Someday-Maybe / Tickler 文件 | 阻塞与搁置各司其职，另有一层时间触发；我们缺时间层，用盘点节奏替代 |
| Things 3 | Someday 列表 + Upcoming 开始日期 | 同缺日期维度，属可接受裁剪 |
| Linear | Backlog 状态 + Priority + Cycle + 陈旧自动归档 | 状态之外用独立维度与自动化清理，避免状态膨胀 |
| Shape Up | Icebox → Backlog → Up Next | 未成形想法不入库；搁置应只装已成形任务 |
| Jira | Backlog 与 Sprint 的承诺边界、Deferred / On Hold | 状态越加越像 Jira，是要避免的方向 |
| Kanban | Blocked 通常作标记而非列 | 阻塞与搁置不可互换 |

### 结论与边界

- 一个搁置覆盖「不排期」这一维，覆盖不了时间、顺序、进度三类诉求；三者用规则与档内文本承载，不扩 schema
- 明确不做：想法池、优先级字段、到期日期字段、独立 backlog 目录、自动归档
- 明确不加校验：搁置档缺「搁置原因 / 重启条件 / 搁置日期」四行时**不加 check 软告警**——新增 warn 规则会让状态切换瞬间短暂告警，
  且与仓库「不为检测扩 schema / 告警」的既有取舍一致；该约束只由技能条文承载
- 已知局限：「按批次」汇总会把搁置任务的旧批次行一并计入；量小可接受，不单独处理
- 升级触发条件：搁置项超过约 30 个，或出现「按日期自动唤醒」的真实诉求时，另立任务评估 tickler / 优先级字段
