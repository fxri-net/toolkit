# 修复 rules compose 剪贴板中文乱码

> 计划位置：第 1 个（共 2 个）；前置：无；后继：无（与「补中文路径跨进程用例」并行）

## 背景

`toolkit rules compose` 交互后复制的内容粘出来是乱码（现场：中文 Windows，`Untitled-1.ini` 呈现 `瑙勫垯鏇存柊鏃堕棿` 形态，即 UTF-8 字节被按 GBK 解码）。

根因在 `src/rules/clipboard.ts`：Windows 分支用 `powershell -NoProfile -Command "$input | Set-Clipboard"`，文本经 stdin 传入；PowerShell 5.1 从重定向管道读 `$input` 时按系统 ANSI 代码页解码，Node 写出的是 UTF-8 字节，于是中文被误解码后写入剪贴板。`clip` 兜底同样走 ANSI 通道，必然乱码。

   `Set-Clipboard -Value (Get-Content -Raw -Encoding UTF8 -LiteralPath $env:FX_TOOLKIT_CLIP_FILE)`，`finally` 中递归删除临时目录（成功与失败路径都清理）。
2. 移除 `clip` 兜底（该通道必然乱码）：PowerShell 不可用时返回明确错误，由命令层以非 0 退出并给出原因（降级不静默）。

4. 变更集：patch，说明剪贴板中文乱码修复。

# 优化 CI 关键路径耗时

> 计划位置：第 1 个（共 1 个）；前置：无；后继：无

## 背景

实测（GitHub run 44806742689，提交 41aadf1）：

| job | 耗时 | 步内构成 |
| --- | --- | --- |
| check | 1m02s | 安装/环境 13s + 门禁 45s + 打包上传 2s |
| windows | 1m16s | 环境 + `verify --skip-coverage --skip-docs` |
| macos | 1m28s | 环境 23s（setup-node 14s）+ 门禁 56s |
| node18 | 22s | 依赖 check 产物，串行在其后 |

关键路径 ≈ `check + node18`（84s）与 `macos`（88s）取大。对比 1.16.21（check 55s / win 1m48 / mac 1m22，无 node18），单 job 并未变慢，变慢感来自 job 数增加与新增的串行依赖。

`scripts/verify.mjs` 现状：`--skip-docs` 只裁剪文档构建与产物校验，windows / macos 仍完整执行类型检查、文档类型检查、规则产物同步、可读性、eslint、构建与 10 个收尾 CLI 检查——其中静态检查与类型检查与平台无关，属于重复劳动。

## 实施方案

1. **并行取消过期运行**：`.github/workflows/ci.yml` 增加 `concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }`，连续推送只跑最新一次。
2. **打包拆为独立 job**：新增 `pack` job（checkout + pnpm + node + `pnpm build` + `pnpm pack` + upload），node18 改为依赖 `pack`，与 check 并行；`check` 只保留门禁与自身产物校验。

4. **check 的文档构建按改动面裁剪**：`scripts/verify.mjs` 支持环境变量 `VERIFY_DIFF_BASE`，脚本内比对 `git diff --name-only <base> HEAD`，仅在触及 `docs/`、`README.md`、`skills/` 时构建文档站；工作流只负责传 base（push 用 `github.event.before`，PR 用 `github.event.pull_request.base.sha`），首推 / 强推 / 取不到 base 时保守构建。判断逻辑留在脚本内，避免 workflow 与本地出现两套口径。

# 修复交互取消卡死与取消退出码口径

> 计划位置：第 1 个（共 2 个）；前置：无；后继：20261121-唐启云-统一交互层与全量接线

## 背景

在 `toolkit scope` 交互中，于「这套规则作用于」选择页按 Ctrl+C：界面卡住，需连按多次回车才回到「作用域」主菜单；回到主菜单后再按 Ctrl+C 需按两次才能退出。同类交互（`toolkit usage` / `toolkit scope add|remove|mount` / `toolkit rules compose`）需一并排查。

根因（排查结论）：

1. `@inquirer/prompts` 的 Ctrl+C 语义是 reject `ExitPromptError`，随后在 `.finally` 中 `screen.done()` → `rl.close()`（关 readline、退出 raw mode、暂停 stdin），再交给调用方。官方口径是「让你拆除环境」，不是「继续开下一个提示」。
2. `src/scope/wizard.ts` 却把取消当作「返回上一级」：`catch → 静默 return`，紧接着在同一个 stdin 上重建提示，形成 readline / raw mode / SIGINT 监听的中间态。伪 TTY 回放证明纯逻辑层不复现，说明残留发生在终端层交接。
3. `selectLayer` 没有「返回」项，用户想退回上级只能按 Ctrl+C，这是踩入该路径的直接诱因。

## 交互语义（设计口径）

- **Ctrl+C = 中止整个命令**：退出码 130，不打印堆栈、不二次确认；不承担「返回上一步」。
- **「← 返回」= 普通菜单项**：选中后回到上层菜单，走正常应答路径、不触发取消/拒绝——这是与 Ctrl+C 的关键区别，也是本次卡死的根治点（不再在拒绝之后重建提示）。
- **顶层「退出」= 正常退出**：退出码 0，区别于用户中断的 130。
- **ESC = 返回**：与「← 返回」项等价（结束当前子流程、回「作用域」主菜单）；只在子流程内绑定，顶层菜单不绑定 ESC（避免误退出）。实现方式为自建 keypress 监听并调用 `prompt.cancel()`，走 inquirer 自身的取消清理、不产生 SIGINT；readline 对单独 ESC 有约 500ms 判定延迟，属已知代价。`CancelPromptError` 在本包装内按「返回」处理，`isPromptCancel` 仍保留该 name 作为兜底。
- **不用「按两次 Ctrl+C 才退出」的确认式退出**：本次故障的多次按键体验正是这类反模式放大的结果。
- **覆盖边界**：`isPromptCancel` / `exitOnPromptCancel`（130）与 `askWithBack` 都放在 `src/prompts.ts`，属全局复用，所有交互命令（scope / usage / rules / skills）取消时一致以 130 收口；「返回 / ESC」只对有层级的流程有意义，本任务只接 `toolkit scope` 的层级。`usage init`（十余步线性向导）与 `skills install`（选技能 → 选目标 → 确认）同属多层但本次不接，另立任务待确认。

# 内容闸门接管范围配置化

> 计划位置：第 5 个（共 6 个）；前置：20261121-唐启云-统一作用域模式匹配与判定基准；后继：20261121-唐启云-技能级作用域判定与呈现

## 背景

用户明确：闸门接管范围不能写成技能清单（`src/skills/types.ts L27` 的 `GATE_SKILLS`），否则每新增一个技能都要改代码。已确认采用「配置规则 + 技能 opt-out」：默认全量接管，可通过 include / exclude 裁剪，技能自身可声明退出。

另外，`guard` 目前只认包内技能（`src/scope/guard.ts L30-L35` 用 `skillsSourceDir()` 直取），外部来源（如 playbook）即使写了入口壳也取不到正文——不解决这一点，「全量接管」只是包内全量。

## 方案

1. **配置模型**：`skillsInstall.gate` 支持 `true` 或 `{ include?: string[], exclude?: string[] }`；缺省 include 为 `["*"]`（全量）。数组项**复用匹配语法**（glob / `re:`）但按技能名扁平匹配——不做 `~` 展开、真实路径与分隔符归一；大小写按平台口径（win32 不区分）。参数非法按降级不静默处理：非布尔非对象告警回落 `true`，数组内非法项告警剔除；开关全量非法时报错退出。
2. **技能 opt-out**：`SKILL.md` frontmatter 增 `metadata.gate: false` 时该技能不写入口壳；缺省随全局配置。字段非法值告警并按缺省处理。
3. **删除枚举**：`GATE_SKILLS` 常量及全部引用（`src/skills/types.ts`、`src/skills/install/global.ts L87`、`src/skills/status.ts L252`、`src/commands/skills.ts L833`）改为「按规则计算是否接管」，install / status / `--gate` / `--embed` / 向导闸门共用同一判定函数。
4. **guard 来源解析**：按技能名查状态文件 `sources` 定位真源根（内置源为包根，外部来源为登记根）；来源缺失或根已不存在时退出码 `1` 并给出原因（stdout 仍为空）；`gate-drift` 判定复用同一解析函数，避免两套口径。
5. **入口壳字段确认**：壳只保留 `name` / `description`；依赖 `version` / `tier` / `requires` 的逻辑一律走真源读取（status 现状已如此，执行时逐处复核）。
6. **文档与提示**：`skills status` 显示闸门开关、接管规则与命中数量；`skills install --gate` 帮助文案说明「默认全量、可用 include / exclude 或技能 opt-out 裁剪」。
7. **性能约束**：全量接管后每次技能激活多一次 `guard` 进程（实测约 76ms），在文档中明确，不为此改回枚举。
8. **安装时来源校验**：写入口壳前解析技能来源根；来源不可用（临时来源失效 / 外部根被删）时跳过该技能并告警，不写空壳；`--dry-run` 同样报告跳过项。

# 作用域扫描交互流程

> 计划位置：第 3 个（共 6 个）；前置：20261121-唐启云-统一作用域模式匹配与判定基准、20261121-唐启云-递归扫描仓库与剪枝规则；后继：20261121-唐启云-作用域名单管理交互

> 延续「交互式作用域管理」（见 archive/202611/20261120.md）。

## 背景

用户设想的链路：一条命令进入交互 → 输入父目录 → 扫出真实项目 → 多选 → 选择进白名单还是黑名单；要求尽可能傻瓜化，减少心智负担。

现状缺口：

- `runScopeSetScope` 只给固定候选（cwd / 父目录 / home / 已有序条目），没有「输入父目录 → 扫描」步骤；
- `runScopeAdd` 固定加白名单并强制切 allowlist，没有「选白还是黑」的岔口；
- 写入固定全局 `~/.toolkitrc.json`（`src/scope/config-file.ts` 只有全局 writer），用户看不到规则归属；
- 加白名单会隐式把模式切成 allowlist，等于「其余全部不生效」，当前没有任何预告。

## 方案

1. **入口**：菜单中的「设置生效范围」改为新流程（归属选择 → 扫描 → 手动补充路径），不新增并列项；`toolkit scope add` 无参进入同一流程；原「在项目里批量安装技能」更名为「批量安装技能到项目」，避免两个都含扫描与多选的菜单项混淆；不新增需要记忆的命令名。
2. **第一步定规则归属**（先于扫描，解决「写入当前项目」歧义）：
   - `我所有的项目（全局 ~/.toolkitrc.json）`；
   - `仅当前项目（.toolkitrc.json，随仓库共享）`；
   - `仅当前项目的本机（.toolkitrc.local.json，不入库）`。
   - 选后两者时**不进入扫描 / 多选**，直接做「本项目是否生效」的单项目确认；若此时已有跨项目扫描结果，后两项置灰并说明「该规则只在本项目内读取，指向其他项目不会生效」；
   - cwd 不在任何仓库内（无 git 根、无 `.tasks` 根）时，后两项同样置灰并说明：项目层 / 本地层需要项目根才能定位写入文件；
   - 项目层 / 本地层的「本项目是否生效」写入口径固定为：生效 → `mode: allowlist` + `include: [项目根]`；不生效 → `mode: allowlist` + `include: []`（空白名单即不生效）。写入沿用读-合并-原子写，只改 `mode` / `include` / `exclude`，保留 `markers` / `gitRemotes`；该层已有同类规则时在 diff 预览中列出将被覆盖的条目。
3. **扫描阶段**：输入父目录（默认 cwd；可一次输入多个父目录，逗号或换行分隔，结果合并去重）；输入本身是仓库时反问「收录它，还是扫描其内部」；调用递归扫描（见前置任务）；0 结果时给就地选项「下探更深 / 包含隐藏目录 / 包含嵌套仓库 / 取消」；结果超过 30 条时先问一次关键字过滤再进多选；扫描可随时中断，中断即退出且不写配置。
4. **多选阶段**：复选框展示相对父目录的路径与 `[白]` / `[黑]` / `[已收录]` 标记；**已在册条目默认不勾选**，勾选后按所选去向处理（同侧不重复写入，对侧触发互转）；分页 15–20（`@inquirer/prompts` 复选框不支持搜索，用关键字过滤替代）。
5. **去向选择**：`加入白名单 / 加入黑名单 / 从名单移除 / 保持不动`，默认「加入白名单」。追加语义：保留该层既有的 `include` / `exclude` 条目，仅追加本次选中项；整体重建不提供入口，需要时直接编辑该层配置。模式只在加入白名单时自动切 `allowlist`；加入黑名单不强制切模式——`all` 下排除天然生效，`allowlist` 下作为更细排除，`denylist` 下直接追加。
6. **冲突就地处理**：同一路径在另一侧时，不再只提示，直接给动作选择——「移入白名单并从黑名单删除（推荐）/ 保留黑名单（排除优先）/ 取消本次写入」，默认第一项。
7. **写入前 diff 预览**：列出新增、移除、互转条目与模式变化，明确标注「切换为 allowlist 后，未列出的项目都不再生效」；用户确认后原子写。
8. **写入层支持**：`src/scope/config-file.ts` 增加项目层 / 本地层 writer（项目层写 `inspectConfigLayers` 定位到的项目根 `.toolkitrc.json`，本地层写 `.toolkitrc.local.json`），沿用读-合并-原子写。
9. **非 TTY 等价路径**：`scope add <dir>...` 支持多个目录，保持现有「加入白名单并切 allowlist」语义，但不弹交互、仍执行冲突检测与告警（降级不静默）：同路径已在黑名单时按推荐互转处理（自动从另一侧移除并告警），不保留冲突共存；交互无法进行时给等价命令而非直接失败；所有交互告警都必须带就地动作，不允许「请稍后运行 X」式提示。
10. **取消语义**：Ctrl+C / ESC 不写任何文件；重复条目自动去重并计数提示。
11. **公共逻辑复用**：冲突检测、路径归一与「已被父级规则覆盖」判定抽为共享函数，与任务「作用域名单管理交互」共用，不各写一套。
12. **保留「全部项目」入口**：新流程必须提供「清除限制（全部生效）」选项——写 `mode: all` 并清空 `include` / `exclude`（diff 预览后确认）；否则旧的「设置生效范围」被替换后，用户没有路径从 allowlist / denylist 切回默认。

# 递归扫描仓库与剪枝规则

> 计划位置：第 2 个（共 6 个）；前置：无；后继：20261121-唐启云-作用域扫描交互流程

> 延续「全局作用域解析与只读命令」「交互式作用域管理」（见 archive/202611/20261120.md）。

## 背景

用户指出固定扫描层数不成立——不同人的项目深度不一致。改为**递归发现 + 命中即剪枝**（参考 ghq、Sourcetree / GitHub Desktop 的 scan folder、JetBrains 的 exclude 目录列表），深度只作安全上限而非用户必填参数。

现有 `src/scope/plan.ts L15-L27` 只扫一层，判据为 `.git` / `package.json` / `.tasks` 任一存在：

- `package.json` 会把 monorepo 子包、脚手架残留当成项目；
- 跳过表只有 `node_modules / dist / coverage / .git / .turbo / .next`，`vendor`、`.venv`、`target`、`build` 等未覆盖；
- 不解析软链、不去重、无上限、无跳过统计。

⚠️ 另一处约束：`runScopeMount` 也调用 `scanRepositories` 往项目里写技能文件。改为递归后若直接复用，会把技能装进深层嵌套项目。本任务必须让两个调用方语义分离（见方案第 6 条）。

## 方案

1. **扫描签名**：`scanRepositories(parent, options)`，返回 `{ repos, skipped, truncated }`；`repos` 含 `name` / `path` / `kind: "git" | "tasks" | "npm"`。
2. **判定顺序（命中即剪枝）**：
   - 目录名命中依赖 / 产物黑名单 → 跳过并计入 `skipped`；黑名单在现有基础上补 `vendor`、`bower_components`、`jspm_packages`、`Pods`、`.venv`、`venv`、`target`、`build`、`out`、`.pnpm-store`、`.cache`；
   - 默认跳过 `.` 开头的隐藏目录（`.git` 永远跳过），`hidden: true` 时放行；
   - 命中 `.git`（目录或文件，覆盖 worktree / submodule）→ 记为 `git` 仓库并**停止下探**（仓库内的依赖与产物因此永远不会被扫到）；`nested: true` 时才继续深入已识别仓库；
   - 命中 `.tasks` → 记为 `tasks` 项目；
   - 无 `.git` / `.tasks` 但存在 `package.json` 且存在任一 lock 文件（`pnpm-lock.yaml` / `package-lock.json` / `yarn.lock`）→ 记为 `npm` 项目；仅 `package.json` 不算，避免脚手架与子包误判；
   - 其余目录继续向下，直到上限。
3. **安全上限**：`maxDepth` 默认 8、`maxDirs` 默认 5000、`maxMs` 默认 3000，任一触发即截断并标记 `truncated` 原因；扫描过程可被调用方中断（交互层 Ctrl+C 即退出且不写配置）；网络盘 / UNC 路径以 `maxMs` 兜底，超时按截断报告并提示缩小范围。
   - 边界保护：父目录为盘符根（如 `D:\`）或 home 根时，由调用方（交互层）二次确认或直接拒绝并建议更小范围；扫描器只接收显式 root，不自行弹交互。
4. **路径形态**：默认不跟随符号链接（防循环与跨盘穿透）；对每个候选取真实路径去重（C-32），排序稳定。
5. **错误处理**：无权限 / 读取失败计入 `skipped` 并保留原因，不中断；父目录不存在由调用方预先校验。
6. **调用方隔离**：`runScopeMount` 保持现有「只扫一层 + `.git` / `package.json` / `.tasks`」语义，或显式传 `maxDepth: 1` 与旧判据；新交互流程使用新的递归扫描。不得让装技能这类写操作因扫描改深而扩大写入范围。
7. **纯函数**：扫描逻辑不读文件内容、不执行命令，便于单测。

# 统一作用域模式匹配与判定基准

> 计划位置：第 1 个（共 6 个）；前置：无；后继：20261121-唐启云-作用域扫描交互流程、20261121-唐启云-内容闸门接管范围配置化、20261121-唐启云-技能级作用域判定与呈现

> 延续「全局作用域解析与只读命令」「交互式作用域管理」（见 archive/202611/20261120.md）。

## 背景

用户要求作用域名单支持全名、通配与正则，并确认判定基准改为**项目根优先**：在仓库子目录里执行时，按项目根匹配，`include: ["D:/work/proj"]` 即可覆盖其下全部子目录，不必手写 `/**`。

复核现状发现四处与文档不符或能力缺口：

- `src/scope/glob.ts` 只支持 `**` / `*` / `?`，无正则；
- `src/scope/paths.ts L9` 的 `expandHome` 未被匹配链路调用，`include: ["~/work/**"]` 实际不命中，而 `docs/config/activation.md` 明确写了「`~` 展开为 home」；
- 相对路径同样未解析，与文档「相对路径按当前工作目录解析」不符；
- 判定取 `context.cwd`（`src/scope/decide.ts L35`），导致精确路径只命中当前目录本身。

本次把这些收敛为一个统一匹配入口，并补上判定基准，后续扫描交互与闸门配置都复用它。

## 方案

1. **统一匹配入口**（`src/scope/glob.ts` 扩展或新增 `pattern.ts`）：
   - 分两层：语法层（解析 `re:` 前缀 / glob、编译、复杂度校验）与路径层（归一化后匹配）；语法层独立导出，供任务 5 / 6 的技能名扁平匹配复用，不重复实现；
   - `re:` 前缀按正则处理（如 `re:^D:/work/(a|b)$`），其余按现有 glob 子集；
   - 正则编译前校验：长度上限 200 字符、`new RegExp` 异常捕获；拒绝嵌套量词（如 `(a+)+`）与单条量词超过 20 个的形态，防回溯爆炸；非法条目**告警并从本次匹配中剔除**（降级不静默，C-26）；
   - 匹配前对规则与目标同时归一：`~` 展开、相对路径按判定基准解析、分隔符统一、盘符与大小写按平台口径、去尾斜杠、取真实路径（C-32）；
   - 正则与 glob 共用同一大小写口径：win32 默认加 `i` 标志，其它平台区分大小写；
   - `matchedRule` 回显命中的规则原文（含 `re:` 前缀），供 status / list 解释。
2. **判定基准改为项目根**：`resolveScope` 计算 `baseDir`——git 根（`findGitRoot` 命中）优先，其次向上最近的含 `.tasks` 的目录，都没有则回落 `cwd`；`ScopeContext` 新增 `baseDir`，`decideScope` 用 `baseDir` 参与 `include` / `exclude` 匹配。
3. **契约**：`ScopeDecision` 新增 `baseDir` 字段，`scope status --json` / `scope list --json` 同步输出；`matchedRule` 保持原口径。
4. **markers / gitRemotes 不变**：标记仍在 `baseDir` 与 git 根查找；远端匹配逻辑不动。
5. **兼容性**：纯 glob 且无 `~` / 相对路径的既有配置行为不变；`cwd` → 项目根属行为变化（子目录内可能由「不命中」变「命中」），按 minor 记变更集并在文档写明。
6. **迁移诊断**：`scope status` 在 `baseDir !== cwd` 且 `include` / `exclude` 非空时，同时按旧口径（cwd）与项目根口径判定，两者结论不同即提示「判定基准已改为项目根，本目录结论与旧口径不一致」；`markers` / `gitRemotes` 不依赖 `baseDir`，不参与对比，避免假告警；不新增子命令。
