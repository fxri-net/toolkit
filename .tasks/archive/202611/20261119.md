# 优化文档无损检查取数

> 计划位置：第 1 个（共 6 个）；前置：无；后继：`20261119-唐启云-构建步骤按改动面裁剪`

## 背景

`pnpm verify --full` 实测中，收尾阶段的「文档无损（整句比对）」耗时 11.8s，是收尾阶段最大单项。根因在 `scripts/check-doc-loss.mjs`：基线内容逐文件执行 `git show <tag>:<file>`，二三十个文件即二三十次子进程启动（每次数十毫秒）；单句覆盖率判定已基于全仓双字集合，扫描本身不是瓶颈。

## 方案

1. 基线取数改为一次批量读取：先用一次 `git ls-tree -r --name-only <tag>` 得到清单，再把全部 `<tag>:<path>` 写入单次 `git cat-file --batch` 的标准输入，按 `<oid> <type> <size>` 头 + 定长内容的协议解析出各文件基线文本，替换现有逐文件 `git show`。
2. 覆盖率判定保持现有口径不变（全仓双字集合 + 每句自身双字命中率阈值），不引入更复杂结构，避免改变告警结果。
3. 输出必须与改动前零差异：同样的 tag 选取、文件过滤、句切分、排序、每文件前 5 句截断、汇总行；仍然只告警不阻断、退出码恒 0。
4. 按规范 C-44 补假现场用例：在临时目录 `git init`、提交基线文档并打 `v*` 标签，构造两种现场——基线整句被删除（应报出）、基线句仅改写措辞（不应报出）；无标签现场断言脚本打印跳过且退出码 0。用例通过 `node` 子进程运行真实脚本，不在测试内复刻取数与比对逻辑。

## 影响范围

- 代码：`scripts/check-doc-loss.mjs`、`src/__tests__/doc-loss.test.ts`（补一类现场用例）。

- 手工对照：用当前最近的 `v*` 标签分别跑改动前后脚本，逐行比对输出一致。

## 回滚

还原 `scripts/check-doc-loss.mjs` 并删除新增测试文件即可，无数据迁移与外部依赖。

## 完成情况

- 基线取数由逐文件 `git show` 改为单次 `git cat-file --batch`，按字节长度切分内容；批量读取失败时打印跳过、退出码 0。

## 背景

`docs/site-nav.json` 侧边栏有两种父项模式：

| 模式 | 实例 | 结构 |
| --- | --- | --- |
| 纯分组 | `开始` / `指南` / `使用统计` / `全局规则` | 只有 `items`，无 `link`（本身没有对应页面） |
| 有独立页的父项 | `CLI 参考`（`/cli`）、`配置参考`（`/config`） | `link` + `items` 并存，点标题进整页、展开看子项 |

`常见问题` 有独立页 `/faq`，属第二种模式，但当前只有 `items` 没有 `link`：
从任一锚点子项进入后，侧边栏再也没有回到整页的入口，且与 `CLI 参考` / `配置参考` 的写法不一致。

反例（不采纳）：另加一条「全部问题」子项。父项本身能点即可达到同一效果，
增子项会让「常见问题」变成第三种模式，且其他有独立页的父项都得跟着加，属自造冗余。

## 方案

给「常见问题」父项补 `"link": "/faq"`，保留现有 `collapsed: false` 与四个分组锚点子项：

```json
{
  "text": "常见问题",
  "link": "/faq",
  "collapsed": false,
  "items": [
    { "text": "安装与环境", "link": "/faq#安装与环境" },
    { "text": "技能与规则", "link": "/faq#技能与规则" },
    { "text": "任务与流程", "link": "/faq#任务与流程" },
    { "text": "发版与升级", "link": "/faq#发版与升级" }
  ]
}
```

顶栏「帮助」保持两项不变；`schemas/site-nav.schema.json` 的 `sidebarItem` 允许 `link` 与 `items` 并存。

## 影响范围

- 风险：父项可点后点击标题会跳整页，展开靠折叠箭头——与 `CLI 参考` 的既有交互一致，不引入新行为

# 统一安装命令写法

> 计划位置：第 3 个（共 3 个）；前置：无（与任务 2 无依赖，按计划位置串行）；后继：无
>
> 由「收敛全局规则为薄壳」的复核拆出——同一仓库混用 `pnpm i -g` 与 `pnpm add -g`，与薄壳收敛的改动面不同，独立交付。
> 首次归档后用户要求按「通用安装语法」重做，已撤销归档、恢复本档并改写方案。

## 背景

用户提问「`pnpm add -g` 与 `pnpm install -g` 有什么区别」时暴露出仓库内写法不统一：

| 文件 | 行 | 现写法 |
| --- | --- | --- |
| `README.md` | 116 | `pnpm i -g @fxri/toolkit` |
| `docs/faq.md` | 22、87 | `pnpm i -g @fxri/toolkit` |
| `docs/handbook.md` | 13 | `pnpm i -g @fxri/toolkit` |
| `docs/getting-started.md` | 64 | `pnpm i -g @fxri/toolkit` |
| `docs/getting-started.md` | 106 | `pnpm add -g @fxri/toolkit` |
| `docs/faq.md` | 23 | `pnpm add -g @fxri/toolkit` |
| `templates/rules/env.md` | — | `pnpm add -g @fxri/toolkit` |

各包管理器的全局安装语法并不一致，所以「统一成一条命令」不成立，能统一的是**动词 `add`**：

| 管理器 | 可用写法 | 备注 |
| --- | --- | --- |
| pnpm | `pnpm add -g` | 文档形式；`pnpm i -g` 也生效但属未文档化的位置参数 |
| npm | `npm add -g` / `npm i -g` | `add` 是 `install` 的官方别名（npm 10 帮助中明示 `aliases: add, i, …`） |
| yarn 1.x | `yarn global add` | **不支持 `yarn add -g`**，`global` 位置不同 |
| yarn 2+ | 无全局安装 | 只能 `yarn dlx` 临时执行 |
| bun | `bun add -g` | 支持 |

## 方案

### 1. 统一动词为 `add`，按管理器如实列出差异

`docs/getting-started.md` 安装节代码块写成四行，并补一句升级口径：

```bash
pnpm add -g @fxri/toolkit      # pnpm
npm add -g @fxri/toolkit       # npm（= npm i -g）
yarn global add @fxri/toolkit  # yarn 1.x（2+ 无全局安装，改用 yarn dlx）
bun add -g @fxri/toolkit       # bun
```

升级用同一条安装命令即可，不额外说明"裸 install 不升版本"（属无人会踩的赘述）。

### 2. 其余位置只写 pnpm

`README.md` L116、`docs/faq.md` L22 / L87、`docs/handbook.md` L13 统一为 `pnpm add -g`，不展开四种写法——安装节已是全量对照，别处重复会稀释文档。

### 3. 规则模块补半句

`templates/rules/env.md` 在安装命令后补「npm / bun 用 `add -g`，yarn 1.x 用 `global add`；其他细节见文档站」。
该模块现 148 字符、棘轮上限 165，补句后预计约 190，须把 `scripts/check-consistency.mjs` 的 `env.md` 上限调到 200，并在提交说明写明「为覆盖多包管理器语法而放宽」。

### 4. 产物与变更集

- `docs/rules/ai.md` 由 `rules compose` 重新生成、`rules.generated.ts` 重生成、`cli-golden` 快照更新
- `.changeset/` 新建 patch 变更集（原 `task-install-wording.md` 已随撤销归档一并重写）

- 风险：`env` 模块放宽上限属棘轮调整，须在提交说明留理由，否则棘轮会被当橡皮筋

## 20261119-唐启云-收敛全局规则为薄壳

> 负责人：唐启云　状态：已完成　范围：toolkit　完成时间：2026-11-19 09:33

# 收敛全局规则为薄壳

> 计划位置：第 2 个（共 3 个）；前置：20261119-唐启云-收口授权技能的时间源与反问边界；后继：无
>
> 延续 `20261119-唐启云-收口授权技能的时间源与反问边界`（见 archive/202611/20261119.md）——复核全局规则时发现薄壳原则已系统性失效。

## 背景

`AGENTS.md` 质量门 5 要求：可变流程细节只进 skills，`docs/rules/ai.md` 的「规则全文」保持薄壳——只承载稳定纪律与对 fxri-* skill 的引用。
实测已明显偏离：

| 模块 | 行数 | 字符 | 判读 |
| --- | --- | --- | --- |
| `workflow.md` | 33 | 2637 | 占六个模块总量（约 5360 字符）的 49%，其中绝大多数是与技能重复的流程枚举 |
| `commit.md` | 49 | 943 | 独立真源模板（`docs` 与 `.trae` 为镜像），不属薄壳违例 |
| `core.md` | 13 | 674 | 基本合规，末条半薄壳（列了 BOM / 行尾表，同时指向技能） |
| `usage.md` | 9 | 509 | 全是操作细节，但无技能承载，属「无家可归」的细节 |
| `env.md` | 14 | 445 | 安装 / 升级命令，属可变命令但属环境前置，可接受 |
| `output.md` | 7 | 152 | 合规 |

`docs/rules/ai.md` 的复制块（core + output + workflow + env）约 3.9k 字符，其中 workflow 占 67%。

漂移是系统性的，不是本次新增造成：

- `CHANGELOG.md` 记载过「全局规则收敛为薄壳」，之后 workflow 又长回 33 行
- 历史任务档多次断言「规则全文保持薄壳」，但没有任何机制阻止继续追加
- 本次两轮改动我又往 workflow 加了开工词闭集、微操作、反问兜底共 3 条

根因两条：一是缺少**准入标准**（什么算稳定纪律、什么算可变细节），二是缺少**防漂移门禁**（规则页与技能双写却无一致性与体量校验）。

## 方案

### 1. workflow 模块收敛

保留（脱开 skills 仍成立的红线）：

1. 方案先行：动手前先出方案，含目标 / 步骤 / 影响 / 验证与回滚
2. 方案确认 ≠ 执行授权：开工词 + 范围明确 + 方案已定稿；白话像开工但未命中词时反问
3. 只读型请求默认只读
4. 微操作属对象级授权，范围止于指明对象
5. 不可逆动作逐次授权；当前指令已含授权则直接执行
6. 质量门：项目聚合验收命令必须通过，验收与 CI 同源
7. 动作不算、改动才算；归档 + 规范沉淀即终点；提交随收尾、推送与发版须明确
8. 一行指针：任务状态 / 粒度 / 建档判据 / 时间源 / 收尾流程的细节一律见对应 fxri-* 技能

删除（内容已在技能，属纯删除，不丢能力）：

- 执行顺序探测（`pnpm exec toolkit` → `npx` → 全局）
- 项目初始化 `toolkit init` 命令细节
- 工具不可用的两分支降级流程
- 逐仓逐任务建档、建档评估三情形判别表
- 跨仓库各自归档的判据展开
- 按序交付、逐任务提交的执行细节
- 修缺陷优先于扩能力的证据门槛展开（保留「无证据只作提示」一句）
- 四级时间源（真源 `task-spec.md` §2.2）
- 技能上报条（与 `usage.md` 模块重复，归后者唯一承载）

目标：workflow 从 33 行 / 2637 字符降到约 10 行 / ≤1100 字符。

### 2. core 末条精简

保留「脚本与文本文件按读取方定字节形态，遵循已加载的 `fxri-text-encoding` 技能，写盘后复核」，删除 BOM / 行尾的具体形态表（技能内已有）。

### 3. usage 模块：承认例外

`usage.md` 的操作细节没有技能承载，不强行迁出。改为在模块顶部注明「本模块暂无对应技能，细节直接由本模块承载」，避免后续复核反复把它判为违例。
同时删除 `workflow.md` 里重复的技能上报条（见第 1 项删除清单），上报口径只保留这一处。

### 4. env 模块：改指针但保留最短安装命令

- 保留：`pnpm add -g @fxri/toolkit` 一行命令（`complete` 预设靠它才能装起来，全删会让装配后无安装步骤）
- 保留：AI 不自行执行全局安装
- 删除：`toolkit skills install` 细节、升级说明、`FX_NO_UPDATE_CHECK`、就绪校验四条
- 补一行指针：技能分发与升级细节见文档站快速开始
- 安装与升级命令的写法统一（`pnpm i -g` 与 `pnpm add -g` 混用等）不并入本任务，另立 `20261119-唐启云-统一安装命令写法`

### 5. 准入标准写入模块顶部

workflow 模块顶部加一句：新增纪律前先问「脱离已加载技能是否仍成立」——成立才进全局规则，否则只进技能。

### 6. 防漂移门禁

`scripts/check-consistency.mjs` 增加一条棘轮：`templates/rules/workflow.md` 字符数 ≤1100，`core` ≤700，`env` ≤260，`usage` ≤560，`output` ≤200；超限即失败并提示「把细节移回 skills」。
上限取收敛后实测值的约 1.1 倍，留出小修余量；调整上限须在同一提交里说明理由，防止棘轮被随手抬高而失去意义。

### 7. 规则页同步

- `docs/rules/ai.md` 复制块由 `rules compose` 重新生成
- 「逐段说明」表同步精简（现有多行在复述细节，属第三处维护）
- 页首补一句：本规则假定已安装 `@fxri/toolkit` 与 fxri-* 技能；未安装时仅保留红线判断，任务流程需按文档手工执行
- `rules.generated.ts` 重新生成、`cli-golden` 快照更新
- 变更集 patch

- 对外行为：`complete` 预设注入量下降约 50%（约 3.9k → 1.9k 字符）；已装技能的用户行为不变，
  未装技能的用户只保留红线与最短安装命令，流程细节转由文档与技能承载

## 背景

上一轮交付把「关键词全量盘点」的十六族落成 `gate-auth.md` 的八族词表与九条护栏，压缩时靠临场判断，导致：

- 「委托与裁量」族（你看着办 / 随你 / 都行 / 按你的建议来）既不在词表也不在护栏，规则对该输入无答案，AI 只能现场决定，很可能直接开工
- 开工词是闭集，闭集之外的明显开工说法（开整 / 上手 / 干起来 / 走起）不会触发，也没有反问兜底，用户会以为"说了没反应"

根因不是体量门禁，而是压缩时缺一张对账表：漏族只在记忆里检查，看不见。

## 方案

### 1. 词表补「委托与裁量」族

| 词族 | 代表词 | U | A | P |
| --- | --- | --- | --- | --- |
| 委托与裁量 | 你看着办、随你、都行、按你的建议来 | 一句确认：先回显「我打算做 X」，等用户点头 | 不改变状态，按当前批次继续 | 不改变状态 |

并明确两种粒度：

- 委托**当前这一步**（「这个你看着办」且对象明确）→ 按对象级授权执行
- 委托**整个方案**（「剩下的你看着办」）→ 回方案态，先列将做什么再确认，不得整批直接跑

### 2. 反问兜底

护栏新增一条：表达明显指向开工、但未命中开工词闭集时（开整 / 上手 / 干起来 / 走起），**反问一句「要我开始吗」**，不静默不动，也不自行开工。

### 3. 关键词族落点表（对账基准）

`gate-auth.md` 末尾加十六族落点表，逐族标注「词表 / 护栏 / 别处承载」，落点为空即视为未承载。开头加维护纪律：新增或压缩词族时先更新落点表再动正文。

任务档只记本次新增与移动的族，不复制整张表（避免两处维护再次漂移）。
