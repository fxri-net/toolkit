# 变更集级别口径整改

> 来源链：延续 `archive/202609/20260929.md` 的「20260929-toolkitrc本地配置层」（确立 C-31「变更集级别例外」）；同主题历史锚点见 `archive/202609/20260914.md`（确立「类型 → 建议 bump」纪律表）与 `archive/202609/20260930.md`（多次按 C-31 申报例外）。

## 背景

原 bump 口径以「条目类型前缀 → 建议 bump」映射判定（`新增：` / `修改：` → minor），并为少数「配套修补型」改动开例外通道（C-31），须在任务档申报「已知与惯例相左」。该口径的问题在于：**把条目前缀当成了版本号的决定因素**——前缀本只是给条目归组用的信号，版本号应按改动的业务能力量级判定。后果是「在现有能力上新增的小命令 / 小参数」这类改动被强制按 minor 记，须绕道例外申报，或反过来被误降级。

用户据此定下新口径：**版本号由改动的能力量级决定，与条目前缀正交**——发布全新大功能才发第二个版本号（minor），在现有功能上做小修补、哪怕是新增的小功能，也发第三个版本号（patch）。

本任务把口径真源、技能说明与 conventions 载体一并改齐，并随之取消原「例外申报」概念（新口径下新增小能力天然为 patch，无需例外）。

## 实施方案

1. **真源改写** `skills/fxri-release-changelog/references/changelog-format.md` §2：把「类型 → 建议 bump」映射表 + 「级别例外口径」替换为「**能力量级 → bump**」表——major=破坏性变更（既有契约 / 行为不兼容）、minor=新增全新大功能 / 独立新能力、patch=存量能力上的修补与增量（修复、优化、配套补齐，以及新增的小命令 / 小参数 / 小产物）；保留「条目须分条登记用户可感知的变更」，补入防降级护栏（不得为凑版本号把全新大功能降为 patch；`重大：` 不可降至 patch），并显式写明「判 bump 看能力量级、不看前缀」。
2. **技能同步** `skills/fxri-release-changelog/SKILL.md`：第 1 步改述为按能力量级选影响级别；失败模式表末行去掉「配套修补型」例外措辞、改述新口径；版本双写递增 1.1.7 → **1.1.8**（frontmatter `metadata.version` 与正文首部声明值两处一致）。

## 背景

根因不是「写错了词」，而是**任务档的视角**：任务档是仓库自述，跨仓库是会话属性而非仓库属性；当初把接入方仓库的工作记进了本仓库的任务档。故治理分两手——立纪律防再生 + 一次性脱敏存量。使用者诉求：仓库文本一律不体现跨仓库痕迹，像每个仓库的独立任务一样。
