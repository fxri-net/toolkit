# CHANGELOG 语义分组扩展

## 背景

CHANGELOG 的分组标题由 changesets 按 SemVer bump 类型硬编码生成，恒为 `### Major/Minor/Patch/Dependent Changes` 四组；`src/changelog/format.ts` 只做标题字符串替换，无法增组。后果是分组语义与实际变更性质脱节：同批 1.9.2 的改动实为新增对外输出（`schemaVersion`、技能版本展示），因按 patch 发版被迫归入「🐛 补丁修复」，措辞失实。

参考成熟设计取「约定式前缀归类」机制：Keep a Changelog 确立「语义分类与版本号正交、空分类省略、每条恰好归一类」；GitHub `.github/release.yml` 确立「规则匹配 + 兜底类别」；Conventional Commits 确立「type 前缀驱动分组」。本方案把三者收敛为：**条目自带中文类型前缀，`toolkit changelog version/format` 依据前缀把条目归入语义组**。前缀词表直接复用仓库既有类型字典（新增/修改/修复/优化/清理/文档），不新增配置面。

**分组维度与版本号维度彻底正交**：有前缀时只看前缀，与 bump 级别无关（`文档：` 条目出现在 patch 版本里即进「文档更新」，不会被拉去「问题修复」）；无前缀时按 bump 兜底，其中 `### Patch Changes` 的兜底落点为中性的「📦 其他变更」——patch 语义宽泛，不预设为修复。由此「不涉及功能的改动只升第 3 位版本号」天然成立：用 patch 变更集 + 对应类型前缀即可，分组自动落位。

## 实施方案

### 分组表（槽位级全局定义，各语言 8 组 + 1 兜底，空组省略）

| 语义槽位 | 识别前缀（全局一份，所有语言共用） | zh 组标题 | en 组标题 |
| --- | --- | --- | --- |
| `breaking` | `重大：` / `Breaking:` | `### 🚨 重大变更` | `### 🚨 Breaking Changes` |
| `added` | `新增：` / `Added:` | `### ✨ 新增功能` | `### ✨ Added` |
| `changed` | `修改：` / `Changed:` | `### 🔧 功能调整` | `### 🔧 Changed` |
| `improved` | `优化：` / `Improved:` | `### ⚡ 优化改进` | `### ⚡ Improved` |
| `fixed` | `修复：` / `Fixed:` | `### 🐛 问题修复` | `### 🐛 Fixed` |
| `docs` | `文档：` / `Docs:` | `### 📝 文档更新` | `### 📝 Docs` |
| `removed` | `清理：` / `Removed:` | `### 🧹 清理移除` | `### 🧹 Removed` |
| `deps` | changesets 自动生成的依赖条目（识别基准：**语言无关的源文本** `- Updated dependencies`，不走前缀解析） | `### 🔗 依赖变更` | `### 🔗 Dependency Updates` |
| `other` | 兜底：Patch 块无前缀，或前缀未识别 | `### 📦 其他变更` | `### 📦 Other` |

- **前缀识别与输出语言解耦**：新增语言无关的 `SLOT_PREFIXES`（槽位 → 识别前缀），全局定义一份、所有语言共用，故「全语言互认」由框架保证、无需每个语言重复声明前缀。各语言的 `groups` 只声明槽位与本地化标题，组序即槽位定义顺序。
- **前缀只决定分组、不决定版本号**：版本号由变更集文件声明的 bump 决定，`changelog version` 不按条目前缀推导 bump；任意前缀均可出现在任意 bump 级别的版本块中（minor 块里放 `修复：`、patch 块里放 `新增：` 都按前缀归组）。「类型 → 建议 bump」纪律表只作建议，不做门禁。
- **反向建议（bump → 建议类型）**：变更集 bump 声明为 major 时，条目建议以 `重大：` 开头，使该版本块至少出现「🚨 重大变更」组；同样仅作建议、不做门禁——若某 major 块条目全为其他前缀，允许输出中不出现重大变更组。
- 组序固定按上表；空组不输出，单版本块通常只出现 2–3 组。zh / en 组标题逐条一一对应，仅标题本地化，归属规则完全同构。
- **同槽位跨源组合并为单组**：同一版本块内可并存多个源组（如同时有 `### Minor Changes` 与 `### Patch Changes`），落入同一槽位的条目**合并输出为一个组标题**；组内条目按其在原文件中的出现顺序排列（源组先后 → 组内序），不重排、不按字母序。
- **互认覆盖全语言、非中英专属**：实质是「变更集条目语言 ≠ 输出语言」时仍正确归组，与输出语言是哪种语言无关——中文条目输出 en、英文条目输出 zh、日文条目输出 zh 等一律成立。
- **自定义语言**：`groups[].prefixes` 为**可选**追加项，用于本语言自有前缀（如日文 `新規：`），识别时与全局表取并集；不写则完全沿用全局表。
- 无前缀条目的 bump 兜底（各语言一致）：Major 块 → `breaking`；Minor 块 → `added`；Patch 块 → `other`。**兜底依据的「bump 级别」取自条目所属的源组标题**（`### Major/Minor/Patch Changes` 本身即 bump 声明），**不从版本号推导**——版本号推不出 bump（首个版本块无前驱可比），且同一版本块可同时含 Minor 与 Patch 两块，只有按源组取值才能逐条正确兜底。
- 兜底语义修正：`### Patch Changes` 的兜底标题由「🐛 补丁修复」改为中性的「📦 其他变更」——这是本任务要解决的措辞失实点（非功能改动不再被误标为修复）。
- **执行顺序：`regroupSemantic()` 前置于 `replacements`**：把现位于函数开头的 `replacements` 循环（src/changelog/format.ts L21）**整体下移到 `regroupSemantic()` 之后**；`regroupSemantic()` 紧随**现有两步清理之后**（commit hash 剥离 L25 → 双前缀伪影清理 L29），**这两步的相对先后维持现状不动**（本任务不调换 hash 剥离与伪影清理的顺序，避免「伪影 + hash」叠加行（`- - 800a1cf: x`）的处理结果被顺手改动）。必须先于替换——替换后 zh 的 `### Minor Changes` 已成 `### ✨ 新增功能`，与历史块标题同名，「英文源标题块」这一新旧判据即失效，历史块会被误重排（44 处无前缀条目全部掉进「📦 其他变更」）；en 侧同理（`### Patch Changes` → `### 📦 Other` 后不可辨）。归类完成后再跑 `replacements` 做条目文案兜底。
- 前缀识别时机：在 `regroupSemantic()` 内按顶层 `- ` 条目取首行前缀；该条目的缩进续行视为同一子条目整体迁移。
- **`deps` 槽位不走前缀解析**：changesets 生成的依赖条目（源文本顶层 `- Updated dependencies`，zh 替换后为 `- 更新依赖`）不是「类型：」形式，识别信号有二——① 源组标题 `### Dependent Changes` 整块直接归入 `deps`；② 顶层条目文本与**语言无关的源文本** `- Updated dependencies` 等值。⚠️ 信号② 不比 `language.deps`——regroup 前置于替换，此时 zh 条目尚未替换为 `- 更新依赖`，比 `language.deps` 恒不命中。命中后该条目连同其缩进子项整体迁移，不参与前缀匹配、也不落兜底组。
- **幂等**：只对 changesets 新写入的英文源标题块（`### Major/Minor/Patch/Dependent Changes`）做归类迁移；已中文化的历史块原样保留、不追溯改写，故 `changelog format` 重复运行结果稳定、历史 CHANGELOG 零 churn。
- **历史版本块不追溯**（已确认）：现有 44 个历史标题（`🐛 补丁修复` / `✨ 新增功能`）与无前缀条目一律不动。追溯改写会因历史条目缺类型前缀而全部落兜底组、反而损失信息，且无可靠依据还原原始归类，属臆造记录。

### 代码改动

1. `src/changelog/languages/index.ts`：新增语言无关的语义槽位 `SemanticSlot`（9 个）与前缀表 `SLOT_PREFIXES`（槽位 → 识别前缀，全局一份，全语言互认的基础）；`ChangelogLanguage` 增加**可选** `groups` 字段（有序数组，元素 `{ slot, title, prefixes? }`，可选 `prefixes` 仅用于追加本语言自有前缀、识别时与全局表取并集），`replacements` 降为兜底与兼容用途；zh、en 各自逐条补齐 8 组 + 兜底的本地化标题（以上方分组表为准）。**删除两个内置语言的四个英文源标题映射**（zh 的 `### Major/Minor/Patch/Dependent Changes` → 中文、en 的四条半英映射全部移除）——标题一律由 `groups` 产出，源头靠 `regroupSemantic()` 前置识别英文源标题块；留着即死映射，且与新标题口径冲突（如 en 的 `### Minor Changes` 仍指向旧的 `### ✨ Minor Changes`）。zh 的 `replacements` 仅保留三条**中文自映射**（`### 重大变更` / `### 新增功能` / `### 补丁修复` → 带 emoji 形态，供手工模式与幂等兜底）与依赖条目映射 `- Updated dependencies` → `- 更新依赖`；en 的 `replacements` 收敛为空对象。
2. `src/changelog/format.ts`：把现位于函数开头的 `replacements` 循环**下移到 `regroupSemantic()` 之后**，`regroupSemantic()` 插在 commit hash 剥离 → 双前缀伪影清理之后（两步相对先后维持现状）——按版本块切分 → 仅处理英文源标题块（`### Major/Minor/Patch/Dependent Changes`，这是「本次新写入块」的唯一判据）→ 用 `SLOT_PREFIXES` ∪ `groups[].prefixes` 识别条目前缀并归类重排（同槽位跨源组合并为单组，组内按原出现顺序）→ 无前缀时按**所属源组标题**声明的 bump 兜底（Major→`breaking`、Minor→`added`、Patch→`other`）→ 删除被搬空的源组标题；归类完成后再跑 `replacements`。另新增只读导出 `countUntypedEntries(dir, lang): number`（遍历 `collectChangelogs`，只统计英文源标题块内缺前缀条目数）供 cli 预扫——定位为**内部工具，不加入 `src/index.ts` 公共出口**（cli 直接 import `./changelog/format`），不扩大公共承诺面。**`formatChangelog` / `formatChangelogs` 的签名与返回类型保持不变**，避免触及 src/index.ts L19 已导出、docs/api.md 已列示的公共 API（改返回对象会把本 patch 版升级成 API 破坏性变更）。整体顺序：归一化 → commit hash 剥离 → 双前缀伪影清理 → `regroupSemantic()` → `replacements` → 依赖条目合并 → 连续重复条目合并 → 补发布日期 → 脱敏。另**顺手修**：同一函数内的日期行识别硬编码（L60 的 `isDate` 判据写死 `/^> \d{4}-\d{2}-\d{2} (?:发布|released)$/`，与 L68 写入用的 `lang.released` 不对称），改为按 `lang.released` 构造正则（自定义值先做正则转义）——否则自定义语言（如日文 `リリース`）的既有日期行恒不被识别，每次都落「缺发布日期」分支、在版本标题下重复追加日期行，该语言的幂等承诺不成立（存量缺陷，与语义分组无关，本次一并修；内置 zh / en 行为零变化）。
3. `src/cli.ts`：changelog 域复用现有 `--warn` 开关，对无类型前缀的条目输出软告警（提示按「类型：描述」撰写变更集条目），stdout 保持纯输出不受影响。**`version` 与 `format` 两条子命令都发**——两者都做归类重排，能力同源、开关同一，只发一条会让「手工 `format` 路径」静默丢失提示；各自在归类前取数：`version` 于 `runChangeset(["version"])` **之后**、`formatChangelogs(...)` 之前——须待 changesets 写入新块后再取数，置于 `runChangeset` 之前则英文源标题块尚未生成、恒零命中（实施期以临时样本实测发现并修正）；`format` 于 `formatChangelogs(...)` 之前。**告警范围限定为本次新处理的英文源标题块**（即即将被归类的块），历史版本块零告警——历史块 44 处条目多无前缀，全量扫描会刷屏。计数取 `format.ts` 新增的只读导出 `countUntypedEntries(dir, lang)` **预扫**——归类完成即前缀缺失信息丢失，事后无从统计。**两条告警文案须可区分**：既有「⚠️ 存在未归档的 active 任务，建议先归档再发版」（任务纪律）保持不动，新增条目告警另起措辞（如「⚠️ N 条变更集条目缺类型前缀，建议按『类型：描述』撰写」），两者可同时出现但不混淆。

# 技能版本可视化与旧会话一致性校验

## 背景

真实痛点：技能以软链形式分发（`toolkit skills install` 默认 junction），但**旧会话上下文中已加载的技能内容是否随 CLI 升级自动更新，无法验证**。最初设想的机制是「CLI 展示技能最新版本 + 旧会话里也输出技能版本 → 两边比对」，核查后发现该机制有致命漏洞：

- 在旧会话里执行 `toolkit skills status`，跑的是磁盘上已升级的 CLI、读的是磁盘真源，打印值恒等于最新版，与会话上下文中实际加载的内容无关；
- 结果必然是「两边一致」的假阳性，恰好掩盖要抓的「上下文已过期」问题。

据此把方案修正为**两条腿**，缺一不可：

- **腿一（技能侧自证）**：让版本号随技能内容一起进上下文——每个 SKILL.md **正文**首部显式声明版本，并补纪律「被问版本时报正文声明值，不读磁盘、不跑 CLI」。
- **腿二（CLI 侧对照基准）**：`skills status` 常驻打印包内各技能真源版本，`--format json` 新增 `skillVersions` 字段，作为磁盘基准值。

闭环用法：旧会话问 agent 技能版本 → 报上下文里的旧值；同会话跑 `skills status` → 得磁盘最新值；两者不等说明会话上下文已过期，开新会话即可。

> ⚠️ 前提实测：技能 loader 可能剥离 frontmatter，仅靠 `metadata.version` 进不了上下文——这正是版本要写进**正文**的原因。动手第一步先实测正文声明值是否进入上下文，再决定腿一措辞。

## 实施方案
