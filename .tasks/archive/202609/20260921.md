# 技能链接锚点改为 pnpm 稳定入口

延续 技能包内分发与全局安装（见 `archive/202609/20260912.md`）

## 背景

用户实测：`@fxri/toolkit` 由 1.10.2 升级到 1.10.3 后，Trae CN 等 5 个 agent 全局技能目录下的 junction 全部悬空。

- 现象：junction 目标写死为 `<pnpm 全局目录>\.pnpm\@fxri+toolkit@1.10.2\node_modules\@fxri\toolkit\skills\<技能名>\`，升级后该版本段目录被 pnpm 剪除（实测 `Test-Path` 为 False），链接成为死链，agent 技能加载器读到空目录。
- 触发链：`resolvePackageRoot()` 从 `import.meta.url` 取 realpath，pnpm 布局下即含版本段的 `.pnpm/@fxri+toolkit@x.y.z/node_modules/...`；`writeArtifact()` 把该路径直接写入 junction，因此链接只在同一版本内稳定。
- 兜底链：`autoLinkSkills()`（`skills.autoLink` 默认 true）在任意 `toolkit` 命令启动时对状态文件记载的链接补链/修链，实测已把上述 15 处链接修回 1.10.3。故真实缺陷不是「必须重跑分发」，而是**存在一个窗口期**——从升级完成到下次运行任意 `toolkit` 命令之间，新会话读不到技能。
- 表述落差：`archive/202609/20260912.md` 已记录「升级跟随的诚实边界」，但 `docs/ai-rules.md`、`docs/handbook.md`、`docs/guide.md` 对外仍写「升级自动跟随 / CLI 升级后技能即新版，无需额外命令」，未含该限定。

关键实测事实：pnpm 在 `<pnpm 全局目录>\<global 段>\node_modules\@fxri\toolkit` 维护一个**稳定入口 junction**，升级时由 pnpm 重写（当前已指向 1.10.3，而技能链接仍停在 1.10.2）——这是可用的不漂移锚点。

## 实施方案

1. `src/skills.ts` 新增稳定锚点解析：
   - 纯函数 `pnpmStableEntry(pkgRoot)`：识别 `<X>/.pnpm/<pkgDir>/node_modules/@fxri/toolkit`（global 布局）→ `<X>/node_modules/@fxri/toolkit`；`basename(X) === "node_modules"`（项目内布局）→ `<X>/@fxri/toolkit`；无 `.pnpm` 段（npm / yarn 真实目录，本就不含版本段）→ 空串。
   - `resolveLinkRoot()`：候选非空且存在、且 `realpathSync(候选)` 与 `resolvePackageRoot()` 经 `pathKey` 比对相等才采用，否则回落真源 realpath；结果随 `resetSkillsRootCache()` 一并重置。
   - 导出 `skillsLinkDir()`；新增测试注入点 `setPackageRootForTest()`（与既有 `setHomeDirForTest` 同风格）。
2. 调用点分流（真源读取不变，只改「期望链接目标」）：`installSkills` / `autoLinkSkills` / `skillsStatus` 用 `skillsLinkDir()`，存量旧锚点链接首次运行即判 `wrong` 并重建（一次性迁移）；`removeSkills` 双锚点接受，避免 `autoLink` 关闭时把本包旧锚点链接误判为外来产物而漏摘；副本复制、内容比对、版本读取维持 `skillsSourceDir()`。
3. 单测：`pnpmStableEntry` 三例（global / 项目内 / 非 pnpm），以及「模拟升级」端到端用例——临时目录造 `.pnpm` 布局与稳定入口 junction，安装后把稳定入口重指到新版本段并删旧版本段，断言 `skillsStatus()` 报正常且 `SKILL.md` 可读，全程不跑修复命令。
4. 文档表述对齐（A 部分）：`docs/ai-rules.md`（含锚点时间更新）、`docs/handbook.md`、`docs/guide.md`、`docs/cli.md`、`docs/faq.md`、`skills/README.md`（`docs/config.md` 走查后判定无触达）。
5. 建 patch 变更集。

# 收紧 Node 引擎版本门槛并同步文档

延续 验证 node18 兼容性（见 `archive/202609/20260903.md`）

## 背景

`archive/202609/20260903.md` 当时以「保持最低支持版本 Node ≥20」收口，未区分 20 线的补丁号。本次对 14 / 16 / 18 / 20 / 22 / 24 六个主版本（含 20.11.1、20.19.0、22.11.0 等边界补丁号）做实测复核，结论是真实下限为 **20.19.0**（22 线为 22.12.0），`engines.node` 的 `>=20` 会误导 20.0–20.18 用户以为受支持。

实测矩阵（`dist` 为当前源码重建产物）：

| Node | 启动 `--version` | tasks 域 | 库双入口 import/require | `changelog` 透传 changesets |
| --- | --- | --- | --- | --- |
| 14.21.3 | 失败（`SyntaxError: Unexpected token '||='`） | 失败 | 失败 | 失败 |
| 16.20.2 | 通过 | 通过 | 通过 | 失败 ERR_REQUIRE_ESM |

| 22.22.3 | 通过 | 通过 | 通过 | 通过 |
| 24.21.0 | 通过 | 通过 | 通过 | 通过 |

两处门槛性质不同：

1. **语法门槛**：`tsup.config.ts` 的 `target: "node20"` 使产物保留逻辑赋值运算符 `||=`，Node 14 直接 SyntaxError——这是本仓库可控的产物目标。
2. **功能门槛**：`src/cli.ts` 以子进程执行 changesets bin（CJS），changesets 内部 `require` 纯 ESM 的 `human-id@4.2.1`，宿主 Node 未默认开启 `require(esm)` 即 ERR_REQUIRE_ESM；该默认开启自 **Node 20.19.0 / 22.12.0** 起，属上游生态限制。

CI 基线 `.node-version` 为 `20.20.2`，恰高于门槛，故该缺口在当前流水线下永不暴露。

## 实施方案

1. `package.json`：`engines.node` 由 `>=20` 收紧为 `>=20.19.0`。
2. 同步四处「环境要求」表述：`README.md`、`docs/index.md`、`docs/guide.md`、`docs/faq.md`；并把 `docs/cli.md`、`docs/guide.md` 中「Node 18 下不可用」的例外说明补全为覆盖 Node 20.0–20.18（同属 20.19.0 以下）。
3. 建 patch 变更集 `.changeset/patch-engines-node-floor.md`——engines 收窄对使用者可感知（安装时引擎校验提示变化），按质量门第 4 条补建。

不改动项：`tsup.config.ts` 的 `target` 维持 `node20`（20.19.0 在语法层面无新增缺失）；CI 三处基线与 `.node-version` 均 ≥ 20.19.0，无需调整。
