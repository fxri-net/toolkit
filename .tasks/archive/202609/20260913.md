# 优化 CLI 命令退出卡顿与升级检查链路

## 背景

用户反馈 `toolkit tasks` 等命令在输出完成后会「卡顿一下」才交还终端。实机计时体检（Windows/本机 SSD，取第二次运行）结果如下：

| 命令 | 默认 | `FX_NO_UPDATE_CHECK=1` | 差值 |
| --- | --- | --- | --- |
| `--version` | 94 ms | 92 ms | ≈0 |
| `tasks` | 1169 ms | 94 ms | 1075 ms |
| `tasks --view all` | 957 ms | 115 ms | 842 ms |
| `tasks check` | 1283 ms | 102 ms | 1181 ms |
| `tasks stats` | 1465 ms | 113 ms | 1352 ms |
| `tasks normalize` | 989 ms | 106 ms | 883 ms |
| `tasks archive --dry-run` | 952 ms | 94 ms | 858 ms |
| `skills status` | 937 ms | 125 ms | 812 ms |
| `skills path` | 946 ms | 95 ms | 851 ms |

真实业务逻辑耗时仅 50–80 ms（含 ~44 ms node 启动），**每条命令固定多等 0.8–1.4 s，全部来自升级检查**；`--version` 不受影响，因 commander 内部 `process.exit` 早于 main 末尾。

根因：`src/cli.ts` 尾部以 `void startUpdateCheck(version)` fire-and-forget 调用升级检查，命令输出虽已完成，但该异步任务内部的 `fetch()`（`AbortSignal.timeout(1000)`）在联网挂起期间持有 socket/DNS 活动句柄，Node 事件循环无法空转退出，只能等超时或被拒后才结束进程。

附带发现一个真 bug：`src/update-check.ts` 的 `startUpdateCheck` 仅在 fetch **成功**时写缓存，失败直接 return，导致缓存永不生成 —— 离线或不稳定网络下每条命令都重新联网等待。

同类问题排查：全仓 grep `void xxx(` / `async` / `await` / `fetch` / `setTimeout` / `setInterval`，仅命中 5 个文件；除 update-check/version 外，import.ts、export.ts 的 async 均在命令内 await，不留挂起句柄；唯一 `spawnSync`（claude changesets）属设计如此。结论：延迟退出类问题全仓仅升级检查一处。其余候选（scan `statSync` 串行、query 比较器内重复算 `timeKey`、无跨进程缓存、autoLink 固定开销）实测收益均 <20 ms，不做改动以避免过度设计。

## 实施方案

参考 `update-notifier`（npm/yarn/pnpm 事实标准）的成熟设计：「同步读缓存 + 分离子进程后台刷新 + 命中缓存才提示」。

### 1. `src/update-check.ts`：拆分父进程同步路径与后台 worker

- 新增 `UPDATE_CHECK_WORKER_ARG` 常量，作为内部 worker 的 argv 标记。
- 父进程 `startUpdateCheck(currentVersion)` 改为**纯同步、零网络**：读缓存 → 命中且版本更高则提示 → 缓存不新鲜则 `spawn` 分离子进程刷新 → 立即返回。
- 新增 `runUpdateCheckWorker(currentVersion)`：联网拉取版本并读写缓存，供子进程调用。
- 缓存结构由 `{ ts, latest }` 扩展为 `{ ts, latest, ok }`：成功 TTL 24 h，失败负缓存 TTL 1 h，避免失败态每条命令重试联网，也避免一次瞬时失败长时间不再刷新。
- 子进程派生参数：`detached: true` + `stdio: "ignore"` + `windowsHide: true` + `unref()`，保证父进程立即退出且子进程独立存活（已用探针实测：父进程 98 ms 退出、子进程独立完成；非 detached 子进程会被连带终止）。

### 2. `src/cli.ts`：前置内部 worker 分支

- `main()` 最前插入 `if (process.argv[2] === UPDATE_CHECK_WORKER_ARG) { await runUpdateCheckWorker(process.argv[3]); return }`，早于 `autoLinkSkills()`，保证内部 worker 不做技能自愈等无关工作。
- 末尾调用由 `void startUpdateCheck(version)` 改为直接调用同步函数（不再产生未 await 的 Promise）。

### 3. 对外行为变化（唯一一处，需文档同步）

升级提示由「本轮立即提示」变为「延后一次命令从缓存提示」。与 `update-notifier` 语义一致：首次运行只静默刷新缓存，下一次运行才提示。用户可感知收益：所有命令恒定 ~100 ms、不再卡顿；离线时不再每条命令联网。

### 4. 测试与文档

- `src/__tests__/update-check.test.ts`：按新契约重写（父进程同步分支 / 缓存命中提示 / 缓存过期派生 / 负缓存 TTL / 双开关 / worker 写缓存）。
- `docs/config.md`、`docs/guide.md`：把「命令末尾异步查询 registry」「不阻塞命令」改为与后台刷新语义一致的措辞。

### 5. 变更集

新建 patch 变更集，描述「不再卡顿 / 离线不再每条命令联网 / 提示延后一次」。
