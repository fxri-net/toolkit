该判断成立，且指向上一任务的一处设计错位：

| 时点 | 可否重来 | 门禁价值 |
| --- | --- | --- |

## 背景

「本地自检通过、CI 报错」的根因是本仓库存在**四份手写门禁清单**，彼此从未对齐：

| 步骤 | GitHub `check` | GitHub `windows` | GitLab `test` | AGENTS「验收方式」（本地实际执行） |
| --- | --- | --- | --- | --- |
| install `--frozen-lockfile` | ✓ | ✓ | ✓ | ✗ |
| typecheck | ✓ | ✓ | ✓ | ✗（上一任务已补） |
| lint | ✓ | ✓ | ✓ | ✓ |
| test | ✓ | ✓ | ✓ | ✓ |
| test:coverage | ✓ | ✗ | ✗ | ✗ |
| build | ✓ | ✓ | ✓ | ✗ |
| docs:build | ✓ | ✗ | ✓ | ✗ |
| CLI 冒烟 | 3 条 | ✗ | 仅 `--help` | ✗ |
| tasks check / normalize | ✓✓ | ✗ | 仅 check | 仅 check |

本地清单最弱，却是我每次收尾真正执行的那份——**用最弱清单去对最强门禁**，漏检必然。附带三个漂移轴：本地 `eslint --cache` 命中缓存（CI 每次冷跑，本地检查量更少）、本地非 frozen 安装、CI 注入 `fetch-depth: 0` 与环境变量。

## 实施方案

1. **单一真源**：新增 `scripts/verify.mjs`，串行执行 CI 全量步骤（frozen 安装 → typecheck → 冷缓存 lint → test → coverage → build → docs:build → CLI 冒烟 3 条 → tasks check → tasks normalize），首行打印 node / pnpm 版本并与 `.node-version`、`packageManager` 比对（不一致仅告警），失败即非零退出并汇总失败步骤；支持 `--skip-coverage` / `--skip-docs` 供跨平台 job 裁剪
2. **三处 CI 退化为调用方**：`.github/workflows/ci.yml` 的 `check` → `pnpm verify`、`windows` → `pnpm verify --skip-coverage --skip-docs`（并把 `node-version: 20` 改为 `node-version-file: .node-version`）；`.gitlab-ci.yml` 的 `test` → `pnpm verify`（顺带补齐它一直缺的 coverage 与 normalize），镜像钉到 `node:20.20.2`
3. **本地强制**：新增 `.githooks/pre-push` 跑 `pnpm verify`，启用方式写入 AGENTS（`git config core.hooksPath .githooks` 由用户执行）
4. **AGENTS「验收方式」收敛为单条命令** `pnpm verify`，删手写步骤枚举
5. **入规防复发**：`references/task-spec.md` 与 `docs/ai-rules.md` 增加「验收与 CI 同源、不手写清单」纪律；conventions 载体新增索引条目
6. **变更集**：建 patch 变更集，交代新增 `pnpm verify` 单源门禁、本地 pre-push 钩子与技能纪律补充（是否随发 1.10.2 待定）

# 20260916-唐启云-建档判据通用化与收尾动作边界

## 背景

起因：v1.9.5 发版、三方一致性对齐（`3c5f9b2`）、v1.10.0 发版三件事均未走建档评估，发版后也未触发收尾自查。归因结论为「执行失职为主、规范存在兜底缺口为辅」。

用户给出的三条裁决：

1. 发版这个动作本身不算任务
2. 两个任务完全一样时，若没有代码之类的改动，不需要重新建档
3. 其他建议与遗留项按合适方案评估处理

进一步要求：这些需求面向使用者，须**更加通用**——即不得写成只适配本仓库的治理条款，要落到面向使用者的通用能力层。

## 实施方案

### 一、通用化检验标准（本条写入本任务正文，作为改造的判据依据）

任何写进 `SPEC.md` / `task-spec.md` / `skills/` 的条文须同时满足：

1. **生态无关**：不出现 npm / pnpm / changesets 等本仓库专有词
2. **工具无关**：不依赖 toolkit CLI 也成立（手工执行同效）
3. **可判定**：任何人、任何项目、任何 AI 得到同一结论，不靠「拿不准」

原方案三处不合格：判据用「有无增量」（主观）、发版条款绑定 changesets、归档更正无通用出口。

### 二、三条裁决 → 三条通用规则

**规则 A：动作不算，改动才算**

> 任务 = 已确认的方案 + 它落地的仓库文件改动。收尾动作（提交、发版、推送、部署）及其固有产物（版本号、更新日志、标签）不构成任务、不建档；这些动作过程中凡需改仓库文件才能解决的缺陷，该修复按普通任务建档。

兼作自洽性保障：发版本号 / CHANGELOG 本身是文件改动，若不显式豁免「固有产物」会被规则 B 反向判成需建档。

**规则 B：判据从「增量」改为「本次是否产生仓库文件改动」**

> 判据不靠「是否含新需求点」（主观），而看本次是否产生仓库文件改动：需写入版本控制的工作区文件的增 / 改 / 删（源码、配置、文档、技能、任务区自身均计入）；纯读取、纯执行、纯汇报不计入。有改动 → 建档（延续则标来源链）；无改动 → 不重复建档，提示「同主题任务已归档于 {日期}」，直接执行。

收益：客观可验，且顺带解决悬问——「描述完全一样但这次确实改了代码」不再是判断题，按判据直接建档。

**规则 C：归档块默认不可变 + 唯一例外「事实更正」**

> 归档块不追加新的工作内容（延续 / 扩展走新任务并标注来源链），元数据行（唯一键 / 完成时间 / 范围）一经归档即冻结。唯一例外是事实更正：后续核实推翻原块结论时，在其正文末尾追加「修订记录」——保留原结论、不动元数据行、附更正时刻与依据。

# 规范载体目录化与端分类

## 背景

1. **必然膨胀**：它是「每次建档 + 每次会话恢复必须全量读入」且「只增不减」的唯一文件；兄弟机制 archive 已有全量索引 / 近窗精读 / 空洞降级的分层，conventions 一层都没有，设计不对称是膨胀根源。条文式项目（无其他规则文件）尤其无处分流。
2. **无端分类**：多端项目（前端 / 后端 / app / admin / server …）的规范不通用，现结构只有一个平面，无法按端拆分与按需加载。
3. **文档承诺未实现**：`docs/guide.md` 承诺 conventions.md「两种形态 skill 均支持」，但 SPEC.md、task-spec.md、两个 SKILL.md 均无「形态」概念——文档承诺了未实现的能力，属三方失一致，无论是否升级本项都须修正。

同时使用者侧无迁移教程：存量项目已有 `conventions.md`，升级路径无任何说明（guide 只讲形态、handbook 六节无迁移节、faq 无相关问答）。

## 实施方案

### 目标结构

```
.tasks/conventions/
├── index.md      # 唯一入口（常驻读）：端清单 + 每条一行指针
├── common.md     # 全端通用条文（按需创建）
└── <端名>.md     # 各端专有条文，端名 = 任务 scope 取值（按需创建）
```

### 端名取名与判定规则（核心设计）

- **取名**：无全局词表，端名与任务 frontmatter `scope` 取值**逐字一致**（两者共用同一套词表，读取时才能机械匹配）；非空、不含空格与路径分隔符；保留字 `index` / `common` 禁用；风格随项目 scope 既有写法
- **判定源唯一**：`index.md` 顶部「端清单」节显式声明（不扫目录——扫目录会漏掉暂时无条目的端，也会把临时文件误判成端）
- **读取判定**：常驻只读 `index.md`；按需取任务 `scope` 每个值，命中端清单的加载对应分册并叠加 `common`；scope 含非端值静默跳过；scope 空则只加载 `common`
- **写入判定**：「所有端都适用？」是 → `common`；否 → 逐端确认 → 入命中的端分册；禁止跨端合并归属
- **分册按需创建**：判据是「该归属下有无需独立承载的条文」，非条数阈值——溯源索引式项目可能始终只有 `index.md`
- **一致性**：索引「归属」列必须 ∈ {`common`} ∪ 端清单，否则悬空（skill 提示，CLI 不解语义）

### 存量迁移（三段式）

1. **机器搬骨架**：建 `conventions/`，旧文件整体搬为 `index.md`（原文不丢），删旧文件
2. **AI 提归属建议**：读原条目逐条给「common / 某端」建议 + 理由，逐条列出结论
3. **用户逐条确认**：确认后写索引行 + 拆分册；未确认条目保持原样留在 `index.md`

可中断：中途停下 `index.md` 即完整原文，不丢内容。

# CLI 解析错误文案中文化

## 背景

自有命令的解析类错误走 commander 默认错误通道，输出为英文、无 ⚠️ 前缀、无后续指引，与 `tasks` 白名单报错（中文 ⚠️ + exit 1）口径不一。实测三条入口：

| 输入                            | 当前输出                                                                 | CommanderError code         |
| ------------------------------- | ------------------------------------------------------------------------ | --------------------------- |
| `toolkit bogus`                 | `error: unknown command 'bogus'`                                         | `commander.unknownCommand`  |
| `toolkit skills bogus`          | `error: too many arguments for 'skills'. Expected 0 arguments but got 1.` | `commander.excessArguments` |
| `toolkit init --bogus`          | `error: unknown option '--bogus'`                                        | `commander.unknownOption`   |

来源：上一任务 `20260916-唐启云-CLI帮助呈现对齐与安全兜底` 的遗留项 1。

## 实施方案

1. 新增 `src/errors.ts`：导出 `formatCommanderError(err: CommanderError): string | null`，按 code 映射中文并附「运行 toolkit --help 查看可用命令」指引行；非 `CommanderError` 或未收录的 code 返回 `null`。
2. `src/cli.ts`：`program.exitOverride()`，`parseAsync` 外层 `try/catch` —— 命中映射则 `console.error` + `process.exitCode = 1`，未命中则重抛。
   ⚠️ `exitOverride()` 会让 `help()` 同样抛异常（`commander.helpDisplayed`，`exitCode` 为 0），catch 必须先放行 `exitCode === 0`，否则 `changelog version --help` 的拦截与 `toolkit help tasks` 会被自己的 catch 打断。
3. `src/__tests__/errors.test.ts`：直接构造真实 `CommanderError` 断言映射结果，不复刻映射表。

### 边界

`changelog` 透传给 changesets 的英文输出不改 —— 那属第三方 CLI 自身的帮助与报错通道。

### 落地偏差

- 实测 `commander.error()` 先自行把英文正文写 stderr 再抛异常，只加 `exitOverride` 会残留英文原文 → program 上补 `configureOutput({ writeErr })` 缓冲；catch 命中中文映射才丢弃缓冲，未命中则原样写出。
- 未采用原方案的「先放行 `exitCode === 0`」判定：改为以 `formatCommanderError` 返回 `null` 作为放行条件，等价覆盖帮助 / 版本 / 未收录 code 三类，判定口径集中在一处。
- 实际映射 3 个 code：`unknownCommand` / `unknownOption` / `excessArguments`（含相似项提示转中文）；`missingArgument` / `invalidArgument` 走 `null` 回退 commander 原文，未收录。

## 背景

`toolkit --help` 的 Commands 清单里 `skills` 是光杆一行，既无 `[options]` 也无 `[command]`，而同级的 `init [options]` / `tasks [options] [command]` / `changelog [options] [command...]` 都有后缀，观感对不齐。全量排查后发现 6 类同源现象，本轮修其中 4 类：

1. **P1 呈现失配（本轮修复）**：commander `subcommandTerm()` 只拼「名字 + 有非 help 选项才加的 `[options]` + 声明的位置参数」，不认真子命令、不用 `usage()`。`skills` 无自有选项、无位置参数声明，4 个子命令不被计入，父级清单只剩名字；而 `skills --help` 自身 Usage 行是 `toolkit skills [options] [command]`，同一命令两套渲染规则。
2. **P0 副作用缺陷（本轮修复）**：`changelog` 域的 `passThroughOptions(true)` 使 `changelog version --help` 的 `--help` 被当作透传操作数丢弃，命令照跑 `runChangeset(["version"])`（实测输出 changesets 的 `No unreleased changesets found` 后退出；若有待发布变更集会真升级版本号并写 CHANGELOG）；`changelog format --help` 同理会真跑 `formatChangelogs()` 改写 CHANGELOG。
3. **P2 文案不齐（本轮修复）**：全仓库无 `helpOption()` / `helpCommand()` 调用，`-h, --help  display help for command` 是 commander 英文默认值，与 `-v, --version 显示版本号` 及 `docs/cli.md` 的「显示帮助（全局或子命令）」不一致。
4. **P2 行为静默（本轮修复）**：`tasks` 的 `[command]` 是手写位置参数，`tasks bogus` 静默回落成「任务总览」，exit 0 无任何提示。
5. **P3 根描述文案（本轮不做，单独立项）**：根描述只提「任务管理 + 多语言 CHANGELOG」，未含 `init` / `skills` 两域；该句与 README、package.json、docs 站点配置等共 5 处同源，需同批改。
6. **遗留（本轮不做）**：`skills bogus` 报 commander 英文「too many arguments」、未知命令报英文「unknown command」，属 commander 默认错误通道，改动面独立。

## 实施方案

1. `src/help.ts`（新增）提供两个可测函数：
   - `setupHelp(cmd)`：递归遍历命令树，逐命令 `helpOption("-h, --help", "显示帮助")` 并 `configureHelp({ subcommandTerm })`，口径统一为「父级清单条目 ≡ 该命令自身 Usage 行」。⚠️ 必须递归——commander 每个命令各自 `createHelp()`，且 `_helpConfiguration` 只在 `.command()` 建子命令时按引用复制，命令声明完毕后再设置不会回溯。
   - `shouldPrintChangelogHelp(operands)`：判定 changelog 域是否应拦截 `--help` 打印本域帮助。
2. `src/cli.ts`：
   - changelog action 顶部按上述判定提前打印本域帮助并返回（自处理子命令 `version` / `format` 后的 `--help` 不再落入执行分支；其余子命令的 `--help` 仍透传给 changesets）；
   - 命令声明完毕后调用 `setupHelp(program)` + `program.helpCommand("help [command]", "显示帮助")`；
   - tasks action 顶部补子命令白名单（`archive` / `check` / `normalize` / `stats`），表外值报错 exit 1。
3. `src/__tests__/help.test.ts`（新增）：直接调用上述真实实现断言，不复刻其逻辑。
