# 任务方案复核

> 本技能版本 1.0.8（随 @fxri/toolkit 同批分发）。被问版本时即报此值（不读磁盘、不跑 CLI）；与 `toolkit skills status` 的磁盘值不一致即说明会话上下文已过期，开新会话即可。

## 何时使用

- 方案已落档、任务已拆分后，用户表达复核意图（继续评估 / 再评估一下 / 这些任务合理吗 / 拆得太细或太粗 / 有没有漏掉 / 复核任务 / 审查任务拆分 / 重新评估开发计划 / 还有什么建议和问题 / 还有啥坑 / 你再看下 / 帮我过一遍）——语义触发，示例非穷举；前提是上下文已有落档任务或明确任务清单，方案尚未落档时只提示「先建档再复核」
- 落档后追问建议类问题即视为复核：按单表输出（疏漏 / 建议、说明、后续是否落档），不停留在条目式建议
- 拿不准是否已落档时问用户，不猜
- 不加载：初次方案讨论、单纯建档 / 归档、会话收尾、发版动作本身，以及「评估技术方案性能 / 依赖版本」等非任务集评估

## 输入

当前计划、`.tasks/active/` 任务、conventions 载体与仓库规则。复核前先跑 `toolkit tasks check`（不可用则手工核对），并读全量 active 任务，不依赖对话上下文记忆；结构问题以命令结果为准，语义问题再按清单判断。核对「已落档 / 未落档」时逐条对照任务档的「实施方案」，不是关键词命中，已落档项不回列。

## 复核清单

1. 每个任务是否可独立验收、独立回滚、单独提交后仓库自洽。
2. 是否按用户可感知的交付结果拆分，而不是按文件、步骤或实现层拆分。
3. 是否存在单组件特例：跨切面能力只落在一个命令或一个技能上。
4. 是否覆盖全部触达面：命令、技能、来源、文档、变更集、发版。
5. 任务顺序与依赖是否成立，是否存在下游先于上游。
6. 是否与 active / archive 既有任务重复。
7. 任务粒度不等于发版粒度：一次发版可包含多个任务、多个变更集；细则以 `SPEC.md` 与 `task-spec.md` 的显式条款为准。
8. 哪些规则可以落成 CLI / `pnpm verify` 的自动检查，避免长期靠人工复核。
9. 是否全部任务已建档、每档是否自包含（背景 / 方案 / 影响范围 / 验证 + 计划位置 / 前置 / 后继）；发现未建档只标 `需要确认`，不越权写任务档。

## 输出

统一为单表，列为「疏漏 / 建议 | 说明 | 后续是否落档」。后续是否落档取三个标签，单独成列、不用括号：

- `直接落档`：安全、可逆、不改用户语义的修正；用户表态**明确指向接受本份评估结论并落档**时直接写入；
- `需要确认`：涉及任务范围、版本、任务合并 / 删除、用户正文语义的改动；先问再写，只有用户逐条确认或明确说「全部接受 / 都落档」时才应用；
- `仅作提示`：后续增强、超出本次范围的风险与建议；只展示，不写入任务档。

输出纪律：

- 会话内输出的任何评估 / 建议表格，无论内容是否已落档，都必须带「后续是否落档」列；尚未分类时默认 `仅作提示`，不得省略动作列。
- **评估 / 复核 / 计划表 / 检查类请求属只读型**（意图是获取信息与判断）：只输出结论，不执行写操作——即便措辞像命令（如「复核一下」「把这个检查一遍」）也不视为执行授权；落档动作按「后续是否落档」列处理，不自动开始执行任务。写操作与不可逆动作的判定以 `fxri-plan-to-task` 的讨论态 / 方案态 / 执行态闸门为准。
- 触发场景按语义判断，示例非穷举；未列举但语义等价的复核请求按同一原则受理。
- 只列**新增**的疏漏与建议；已确认、已落档的内容不重复；没有新增时明确说「无新增疏漏」并停止。
- 结论为「合理」或「需调整」；无问题时明确输出「未发现需调整项」，不硬凑问题。
- 建议项不自动拆任务，需用户确认后另行建档。
- 关注表态的语义而非字面：只有指向「接受这份评估结论并落档」才生效；「继续评估 / 再看看 / 可以吧」等指向讨论的表达一律不动。含糊回应（嗯、再说）不自动落档。
- 只应用 `直接落档` 项；`需要确认` 逐条问；`仅作提示` 不动；未标记条目一律按 `仅作提示` 处理。
- `仅作提示` 项在会话结束前统一声明「转任务」或「不再跟踪」，避免同一建议跨轮重复提出。
- 写入前后都列出将被改 / 已改的文件与变更摘要，禁止静默改用户内容。

## 不做

不自动建档、不自动改任务文件、不替代 `fxri-plan-to-task` 的建档与归档流程；落档执行仍由 `fxri-plan-to-task` 完成。落档属规划态、不进入提交（提交只在任务归档后一次），也不等于执行授权。
