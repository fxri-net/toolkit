# 复核清单、反例与输出模板

> 由 `../SKILL.md` 按需加载。任务粒度与提交边界以仓库 `SPEC.md`、`fxri-plan-to-task/references/task-spec.md` 为准，本文件不复制细则。

## 一、复核清单

| 检查项 | 通过标准 | 常见不通过 |
| --- | --- | --- |
| 独立交付 | 每个任务可独立验收、独立回滚，单独提交后仓库自洽 | 编码 / 测试 / 文档各建一个任务；拆出的中间态仓库验收不过 |
| 拆分维度 | 按用户可感知的交付结果拆，不按文件、步骤、实现层拆 | 按 `src/a.ts`、`src/b.ts` 拆；把文档 + 技能 + 变更集从代码任务里拆出 |
| 单组件特例 | 跨切面能力要么全局覆盖，要么明确只覆盖某范围 | 版本自检只写进一个技能，其他技能没有；新命令只在一条路径提示 |
| 触达面 | 命令、技能、来源、文档、变更集、发版均有交代 | 只改代码不改文档；只改一个技能漏掉其他技能；漏变更集 |
| 顺序与依赖 | 前置未完成时下游不开工；串行写在正文「批次 / 前置」行 | 下游任务先于上游；串行依赖被误写成 `depends_on` |
| 重复 | 与 active / archive 同主题任务有判别结论 | 同主题重复建档；已有归档任务却重新开一条 |
| 版本范围 | 发版可包含多个任务与多个变更集；任务粒度不约束发版范围 | 把同一版本的能力硬拆到后续版本；或反过来把多个任务攒成一个提交 |
| 自动化 | 能自动检出的规则指出应落到 `tasks check` / `pnpm verify` | 长期靠人工复核、无检测入口 |

## 二、默认处置判定

- `无需确认`：只改文档措辞、补测试、补一致性断言、补边界说明等安全可逆项；不改用户已确认的范围、版本、任务结构。
- `需要确认`：改任务范围、改版本号、合并 / 删除任务、改用户正文语义、改变交付顺序。
- `仅作提示`：后续增强、超出本次版本范围、需要新依赖或新分发机制的建议。
- 不确定时一律归 `需要确认`；未标记时按 `仅作提示`。

## 三、输出模板

| 疏漏 / 建议 | 说明 | 默认处置 |
| --- | --- | --- |
| 示例：任务 2 缺少失败路径测试 | 只覆盖成功分支，建议补 CI 失败用例 | 无需确认 |
| 示例：是否把能力 A 并入本版本 | 涉及版本范围，需用户拍板 | 需要确认 |
| 示例：未来支持系统代理 | 需引入代理依赖，超出本次范围 | 仅作提示 |

结论：合理 / 需调整。无新增问题时只输出「未发现需调整项」或「无新增疏漏」。

## 四、落档协议

1. 用户表达明确接受语义（落档 / 开始 / 可以 / 继续 / 都按这个来 / 全部接受）时，应用 `无需确认` 项；只说「开始」不自动应用 `需要确认`。
2. 用户明确说「全部接受 / 都落档」时才应用 `需要确认` 项。
3. `仅作提示` 永不写入；未标记项按 `仅作提示`。
4. 写入前列出将改文件与变更摘要；写入后列出已改文件与未应用项。
5. 落档执行由 `fxri-plan-to-task` 完成；本技能不直接改任务文件。
