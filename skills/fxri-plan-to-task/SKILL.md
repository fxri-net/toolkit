# 方案落盘：任务建档与归档

> 本技能版本 1.10.5（随 @fxri/toolkit 同批分发）。被问版本时即报此值（不读磁盘、不跑 CLI）；与 `toolkit skills status` 的磁盘值不一致即说明会话上下文已过期，开新会话即可。

## 何时使用

- 方案已确认、表达开始落地/登记记录的意图（建档 / 任务登记 / 落盘 / 归档 / 任务校验 / 规范载体迁移与升级 / 按这个做吧 / 记一下 / 建个任务跟踪），或即将动手改仓库文件前
- 方案未确认时先出方案等确认，不建档
- 不用于：会话收尾整场沉淀（fxri-session-recap 模式一）、收尾动作本身（动作不算、改动才算）、普通 TODO / issue / 日历待办 / 提交信息撰写

## 读取地图

| 你在做什么 | 必读 | 可跳过 |
| --- | --- | --- |
| 建档、填 frontmatter、归档、落档边界 | `references/task-spec.md` | 其余三篇 |
| 读写 / 修订规范载体，或处置存量、v1 / v2 升级 | `references/conventions-spec.md`、`conventions-maintenance.md`、`conventions-migration.md` | 模板篇 |
| 落笔条文、模板或文风偏离 | `references/conventions-templates.md` | 迁移篇 |

`task-spec.md`（任务文件规范）、`conventions-spec.md`（载体结构）与 `conventions-maintenance.md`（载体维护）是规则真源，本文件只写流程；不涉场景不读。

## 核心规则

### 四级时间源（completed 取证唯一口径）

终结态补 `completed` 时按以下优先级取证，禁止凭记忆估算或做时区换算：

| 级 | 时间源 | 取证 |
| --- | --- | --- |
| 0 | 当场打点 | 完成时立即取时（Windows `Get-Date -Format "yyyy-MM-dd HH:mm"`，macOS/Linux `date "+%Y-%m-%d %H:%M"`）——首选 |
| 1 | 聊天记录时间戳 | 用户贴过的日志 / 输出时间戳、口述的确定时刻 |
| 2 | git 提交时间 | `git log --format="%h %ci" <file>` |
| 3 | 系统时间兜底 | 当场取时 + 正文标注「收尾补记」 |

## 工作流

### 开工闸门（先判定所处状态，再进入后续步骤）

三态按「是否改变仓库或远端状态」划分，任何写操作前先声明当前所处状态：

| 状态 | 允许 | 典型输入 |
| --- | --- | --- |
| 讨论态（含评估） | 分析需求、回答问题、输出方案与建议；允许落档（仅维护 `.tasks/active`），不改代码、文档、技能等其它仓库文件、不跑实现命令、不提交 | 需求清单、意见、问题、继续评估、连续落档 |
| 方案态 | 输出结构化方案并标注「等你说开始」；仍不改代码 | 方案成型、等用户拍板 |
| 执行态 | 按当批计划写代码 / 文档 / 技能、跑实现命令、归档、验收、提交 | 明确的「开始 / 按计划执行」 |

- **判据是意图与最终动作**：要「获取信息与判断」→ 只读、只输出结论；要「改变仓库或远端状态」→ 进入写操作。措辞只是线索，不作开关，示例非穷举
- **只读型请求默认只读**：检查、核对、复核、评估、体检、列清单、解释现状一律不写文件、不提交；发现问题先报告，改不改由用户决定
- **讨论态输入不构成执行授权**：收到需求清单、意见或复核请求后先出方案、等「开始」；不得把固定话术当唯一触发，按语义识别（非穷举）；复述或调整方案不等于开始执行
- **方案确认 ≠ 执行授权**：写文件、删除、提交、发版、推送等改变状态的动作须有明确授权；含糊回应（可以、行、好的、嗯）不构成授权。授权按动作与范围界定，会话级授权仅本次会话有效、未点名动作仍需询问
- **授权按批次失效**：推进授权只对当次列出的计划生效，同一回复内不得顺手执行；新需求重新确认
- **授权到达即完成前置**：方案已确认时收到明确推进授权（如开始 / 按计划执行）→ 按展示表（无表按方案步骤）建完全部任务档 → `tasks check`（error 0 且 warn 0）→ 才改第一处文件；
   单任务同样适用，不再追问「要不要落档」。反例：继续评估 / 方案可以 / 先落档 / 再看看（「先落档」只授权任务档维护）；校验失败停在建档阶段。先落档后开始的只补缺档、不重复建档。
   一条授权覆盖表内全部任务的建档与交付，**不覆盖不可逆动作**（发版 / 推送 / 打远端标签 / 全局安装）；范围内细化视为已授权，新增独立范围须确认
- 硬闸门：「等我说开始」「先别动」「只出方案」优先级最高，即使同句出现执行类措辞也不执行

#### 两类讨论态意图（都不等于执行授权）

- **落档** = 任务档维护（新建 / 更新 / 拆分合并 / 修订，变体如「记一下」「登记」）；**继续评估** = 只读复核、只输出结论。两者可同句出现，把评估结论写回任务档属落档。
   「落档」的动作边界见 `references/task-spec.md` §7。
- **落档 ≠ 落地**：「落档」只授权任务档维护，不含改代码 / 文档 / 技能；只有用户明确表达按该方案推进的意图（示例非穷举）才构成执行授权。
- **动作词优先于指代**：指令同时含指代（按你说的 / 按推荐方案）与动作词（落档 / 评估 / 执行）时，动作以句中动词为准；指代只取内容，不取动作；两者冲突时先一句话确认再动手。
- **动作型短语不等于执行授权**：统一掉 / 改一下 / 删掉 / 修一下 / 处理掉等说法只表达目标，助手应回到方案态——先落档并列出改动范围，等用户明确表达按该方案推进的意图、或对具体方案作出明确确认后再动手。
   判据是意图与最终动作，示例非穷举，不把固定话术当唯一开关。
- **连续多轮落档 / 评估 / 讨论 / 合并属正常规划行为**，不因轮次累积推定执行授权；用户字面含「落档」时按任务档维护处理。
- **状态自证**：动作前用一句话自证本轮状态（只落档 / 开始执行），作为给用户的确认信号；说错即用户可立即纠正。仅在状态切换、授权措辞含糊或代词式指令时出现，不每轮重复。
- **复核请求的接手**：落档后回答「还有什么建议 / 问题 / 漏掉什么」时，按 `fxri-plan-review` 的单表口径输出（含「后续是否落档」列），不停留在条目式建议。

### 0. 任务分解与展示型计划表（方案确认后、建档前；两个及以上任务才出）

- 粒度：一个任务 = 可独立验收、可独立回滚、单独提交后仓库自洽的最小交付单元，且不跨仓库（不约束发版范围；判据、判定顺序与反例见 `task-spec.md`）
- 两个及以上任务时给出唯一一张表，列为「序号 | 仓库 | 任务 | 前置」，跨端跨仓同表，按执行先后排列；单任务方案不出表，以方案里的实施步骤为建档依据
- 表只作展示与排序：不落档、不写入任务正文、不设状态列（状态以 frontmatter 为唯一真源）；计划调整先更新表；串行先后写在表与任务正文「批次 / 计划位置 / 前置」行，
   不写 `depends_on`（只用于仍 active 的并行依赖）

### 1. 动手前置：全部任务建档（所有仓库文件改动前必做）

- 无 `.tasks/` 时先执行 `toolkit init`（幂等，已存在不覆盖）
- **逐仓逐任务建档**：每个将产生仓库文件改动的仓库各自独立建档，全部建完再改第一处文件；
   只读仓库不建档；依据为展示表（无表按方案步骤）；只确认部分任务时按子集建档，其余不建不执行并说明
- **每档自包含**：写全背景 / 方案步骤 / 影响范围 / 验证方式，并标「计划位置 / 前置 / 后继」（写任务唯一键，不写 active 路径）；禁止指向对话的指代（引用任务档 / 归档路径合法）；
   执行到任一任务只读该档即可恢复；任务增删须回写受影响档
- `.tasks/` 自身读写不单独构成建档理由（避免自证循环）；archive 同主题仍按下方「仓库文件改动口径」
- 列出 `active/` 下全部 `.md`（含 `{YYYYMM}/` 一层），并核对 `archive/` 是否已有同主题任务
- 读 conventions 载体（存在时）：常驻只读 `index.md`，按本任务 `scope` 加载端分册 / 分类标签分册并**恒叠加 `common`**；
   `history.md` / `retired.md` 按需读；旧单文件 `.tasks/conventions.md` 兼容读取并提示迁移（见 `conventions-maintenance.md`）；载体不属任务，
   不为其建档
- **同主题判别表**（按此决策）：
  | 现状 | 本次是否产生仓库文件改动 | 处理 |
  | --- | --- | --- |
  | active 有同主题 | 补充/细化（同需求未完） | **更新原文件**，updated 同步，不新建 |
  | active 有同主题 | 已分叉成不同范围 | 问用户：拆新任务 or 合并更新 |
  | active 无、archive 有 | 否（重复提议 / 重复执行） | 提示「已归档于 {日期}」，不重复建档，直接执行 |
  | active 无、archive 有 | 是（延续 / 扩展 / 重新实现） | **重新建档**，首行标注 `延续 {原任务名}（见 archive/{YYYYMM}/{YYYYMMDD}.md）` |
  | active 无、archive 有 | 否，仅修正旧记录时间/内容 | 走 fxri-session-recap 模式三，**不建档** |
  | 均无 | — | **建档后再动手**（硬前置） |
- **仓库文件改动口径**：需写入版本控制的工作区文件增 / 改 / 删计入（源码、配置、文档、技能、任务区自身），纯读取 / 执行 / 汇报不计；拿不准列差异问用户，不猜
- **动作不算，改动才算**：提交、发版、推送、部署及其固有产物（版本号、更新日志、标签）不构成任务；过程中需改仓库文件才能解决的缺陷按普通任务建档
- **跨仓库改动各自归档**：任务档只记本仓的改动与动机；判据取视角（描述的是不是本仓），非词表——依赖包名 / 被调接口名等本仓事实照写
- **归档块不可变**：已归档块不追加新内容，延续需求走新任务；唯一例外是**事实更正**——正文末尾追加「修订记录」（保留原结论、附更正时刻与依据），可改受影响事实字段，但唯一键 / 完成时间 / 状态 / 负责人冻结
- 唯一键 `{YYYYMMDD}-{用户名}-{任务简述}`；多人同一需求共用一个文件

### 2. 建档

- 整段复制 `assets/active-task-template.md` 再填空（不凭记忆组装 frontmatter），放入 `active/{YYYYMM}/`；`created` 等于文件名日期前缀，`updated` 随修改同步

### 3. 过程更新

- 五态流转：待办 → 进行中 → 阻塞 →（已完成 | 已放弃）；后两者为终结态，必须补 `completed: YYYY-MM-DD HH:mm`（按四级时间源）；阻塞须在正文记原因，解除须用户确认并转回进行中、记解除原因
- 正文出现「待实施 / 待核对 / 待评估」等游离子项时，拆为独立任务

### 4. 校验

按 `task-spec.md` 的自查清单逐项核对，发现问题当场修复后再进入下一步。

### 5. 归档

按 `task-spec.md` 的手工归档步骤执行，可 `toolkit tasks archive` 自动化。

⚠️ 项目若有触达比对脚本，须在**归档前**跑完——归档删除 active 源文件后比对只能空转；命令以项目自检脚本为准，无则跳过。

### 5.5 任务级规范沉淀（归档后执行）

- 读载体（`index.md` 常驻 + 按 `scope` 加载分册），判断是否产出可升格规范：用户明示「以后都要这样」的规则、与既有规范重复印证的决策；无候选 → **完全静默**
- 有候选 → 先问「是否所有端都适用」（是归 `common`，否则逐端写入，`common` 不作暂存区）→ 输出给用户确认 → 写索引行（稳定 ID `C-<n>`）并把条文归位
- 语义修订、退休与存量迁移按 `conventions-maintenance.md` / `conventions-migration.md` 处置；一次性决策留在任务正文

### 6. 收尾边界

- **归档 + 沉淀即流程终点**：提交、发版、推送非必经，是否执行取决于规则或授权（不可逆动作默认逐次授权）；若提交，按「归档与沉淀 → 验收 → 提交」顺序一次执行，任务记录与代码同一提交；
   规划期（讨论 / 方案）的任务档修订不进提交，一个任务允许多次提交仅限多次交付
- **逐任务交付**：按展示表顺序推进，前置未完成不下游开工；每任务完成即「归档 → 验收 → 提交」，不攒批、不混无关改动（至少一次提交、允许多次）
- ⚠️ **验收须晚于归档**：归档会改写 `.tasks/` 且自身不做阻断式校验，早于归档跑验收就覆盖不到终态；归档块「完成情况」只记改动事实与所用验证命令，不抄验收输出

## 失败模式

| 症状 | 处置 |
| --- | --- |
| active 下出现同名任务文件 / completed 明显异常（零点整、晚于当前） | 合并为一个后删除多余；按四级时间源重新取证 |
| 只建了一个任务档，其余任务无记录 | 先按展示表（无表按方案步骤）补建其余档，`tasks check` 通过后再动手 |
| 任务档写「详见对话 / 见上文」或后续任务无档 | 补建剩余任务档并互链；档内写全方案与计划位置，引用任务档 / 归档路径合法 |
| 下游先于上游开工 | 以展示表顺序为准，先解除阻塞 |
| 归档与校验类排障（创建日与 completed 不符 / 并发写归档冲突 / depends_on 指向已归档） | 见 `task-spec.md` §4–§6（四级时间源、`normalize --fix`、依赖随归档解除） |
| 展示表被写进任务正文 | 表只在对话展示；正文只留「批次 / 计划位置 / 前置」一行 |

## 可选加速（不构成依赖）

⚠️ 探测顺序：`pnpm exec toolkit --help`（npm 项目用 `npx toolkit`）→ `toolkit --help`；都不可用即未安装，按各步手工继续，**不安装、不阻塞**。下列命令按探测到的前缀执行：

- `toolkit tasks` / `check` / `archive`：总览、自动校验、自动归档（替代第 1 / 4 / 5 步；archive 带排他锁，`--dry-run` 预演）
- `toolkit tasks normalize`：归档后核验，`--fix` 自动修复
- `toolkit conventions status` / `upgrade` / `format`：载体体检、v1 / v2 → v3 升级、表格归一（均幂等，`--dry-run` 预演；替代第 1 步判形态、
   第 5.5 步沉淀前后自查）
- 任务目录非默认 `.tasks` 时加 `--dir <path>`
