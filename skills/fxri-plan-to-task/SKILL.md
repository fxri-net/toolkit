# 方案落盘：任务建档与归档

## 何时使用

- 用户确认实施方案后，表达开始落地/登记记录的意图（语义触发，不要求字面一致）：建档 / 任务登记 / 落盘 / 归档 / 任务校验 / 按这个做吧 / 记一下 / 建个任务跟踪
- **即将动手改仓库文件前**（方案已确认、准备执行改动）也是本技能适用场景——动手前先做建档评估（见工作流第 1 步），避免跳过建档直接执行
- 触发前置条件：**方案已确认**。用户说「开始/开工」但方案尚未确认时，先出方案等确认，不建档
- **何时不使用**：方案未确认的对话；会话收尾的整场沉淀与归档（那是 fxri-session-recap 模式一）；与方案落盘无关的普通 TODO、issue 管理、日历待办、日常提交信息撰写

## 核心约定

任务文件规范（目录结构、命名、frontmatter 字段、归档格式、手工归档步骤、自查清单）全部以 `references/task-spec.md` 为准，本文件只写流程。执行任何写操作前先读它。

## 核心规则

### 四级时间源（completed 取证唯一口径）

终结态补 `completed` 时按以下优先级取证，禁止凭记忆估算或做时区换算：

| 级 | 时间源 | 取证 |
| --- | --- | --- |
| 0 | 任务完成当场打点 | 完成时立即执行命令取时间（Windows `Get-Date -Format "yyyy-MM-dd HH:mm"`，macOS/Linux `date "+%Y-%m-%d %H:%M"`）——首选 |
| 1 | 聊天记录可见的准确时间戳 | 用户贴过的日志/输出时间戳、用户口述的确定时刻 |
| 2 | 任务改动的 git 提交时间 | `git log --format="%h %ci" <file>` |
| 3 | 系统当前时间兜底 | 当场取时 + 正文标注「时间为收尾补记」 |

详细口径与告警语义见 `references/task-spec.md`。

## 工作流

### 1. 动手前置：建档评估（先查后写的流程落点，所有仓库文件改动前必做，防漏建档/重复建档）

- 无 `.tasks/` 任务区时先执行 `toolkit init` 建骨架（幂等，已存在不覆盖）
- 列出任务目录 `active/` 下全部 `.md`（含一层 `{YYYYMM}/` 月份子目录），并核对 `archive/` 是否已有同主题任务
- 读 `.tasks/conventions.md`（存在时）：项目协作规范在建档与执行时须遵守；规范文件本身不属于任务，不为其建档
- **同主题判别表**（建档前必须按此决策）：
  | 现状 | 增量情况 | 处理 |
  | --- | --- | --- |
  | active 有同主题 | 补充/细化（同需求未完） | **更新原文件**正文，updated 同步，不新建 |
  | active 有同主题 | 已分叉成不同范围 | 问用户：拆新任务 or 合并更新 |
  | active 无、archive 有（已归档完成） | 无增量（重复提议同一件事） | 提示「同主题任务已归档于 {日期}」，不重复建档，直接执行 |
  | active 无、archive 有 | 有增量（延续/扩展） | **重新建档**，正文首行标注来源链 `延续 {原归档任务名}（见 archive/{YYYYMM}/{YYYYMMDD}.md）` |
  | active 无、archive 有 | 仅修正旧记录的时间/内容 | 走 fxri-session-recap 模式三（历史修正），**不是建档** |
  | active 与 archive 均无 | — | **建档后再动手**（硬前置，不建档不许改文件） |
- **增量判别口径**（不靠感觉）：新方案含原任务中不存在的新需求点/变更点/范围 = 有增量；完全同描述同范围 = 无增量；拿不准 → 列出差异问用户，不猜
- **归档任务不可变**：已归档块是终结记录，不向其追加新内容（追加会破坏完成时间/范围的可信度）；延续需求一律走新任务
- 任务唯一键：`{年月日}-{用户名}-{任务简述}`；多人对同一需求共用一个文件

### 2. 建档

- 整段复制 `assets/active-task-template.md` 再填空，不要凭记忆组装 frontmatter
- 文件放入 `active/{YYYYMM}/`；目录不存在时按规范创建
- `created` 必须等于文件名日期前缀；`updated` 随每次修改同步

### 3. 过程更新

- status 五态流转：待办 → 进行中 → 阻塞 →（已完成 | 已放弃）；后两者为终结态
- **阻塞解除归属**：进入阻塞须在正文记录阻塞原因；解除阻塞须用户确认，确认后转回进行中并在正文记录解除原因
- 进入终结态必须补 `completed: YYYY-MM-DD HH:mm`（按四级时间源取证）
- 方案正文出现「待实施 / 待核对 / 待评估」等游离子项时，拆分为独立任务文件，不在正文留游离待办

### 4. 校验

按 `references/task-spec.md` 的「自查清单」逐项核对，发现问题当场修复后再进入下一步。

### 5. 归档

按 `references/task-spec.md` 的「手工归档步骤」执行：合并归档块 → 降序重排 → 写回 → 删 active 源文件 → 清理空月份目录。可 `toolkit tasks archive` 自动化。

### 5.5 任务级规范沉淀（新增，归档后执行）

归档完成后按以下轻量步骤提炼本任务产出的规范（与会话收尾的会话级提炼同落点、互不重复）：

- 读 `.tasks/conventions.md`，判断本任务是否产出可升格规范：用户明示「以后都要这样」的规则、与已有规范重复印证的决策
- 有候选 → 输出给用户确认 → 写入 conventions.md（带 `来源：{任务文件}` 标注）；无候选 → **完全静默**
- 一次性决策不进规范，留在任务正文

### 6. 收尾边界（硬约束到沉淀）

**归档 + 规范沉淀即本技能流程终点**（先归档、后沉淀）。提交、发版、推送不是必经步骤，是否执行取决于用户的全局 / 个人 / 项目规则；若提交代码，先归档与沉淀、后提交，任务归档文件与 conventions.md 变更、代码变更落在**同一个 git 提交**（顺序不可颠倒），避免任务完成却滞留 `active/` 未归档，或归档单独成一条提交。

## 失败模式

| 症状 | 处置 |
| --- | --- |
| active 下出现同名任务文件 | 重复建档，合并为一个后删除多余 |
| completed 日期与文件名创建日不一致 | 核对是否填错；确为跨天完成则以 completed 日期归档 |
| depends_on 引用的任务已归档 | 正常，依赖随之解除；引用拼写错误则修正 |
| 并发写归档文件互相覆盖 | 归档前确认无其他写者同时操作；冲突时以重排后完整合并为准 |
| completed 填了收尾时刻而非真实完成时刻 | 按四级时间源重新取证（git log / 聊天记录时间戳） |

## 可选加速（不构成依赖）

⚠️ 工具探测顺序（先项目内、后全局）：先 `pnpm exec toolkit --help`（项目 devDependency，npm 项目等价 `npx toolkit`），失败再 `toolkit --help`（全局安装）；两者都不可用即工具未安装，按各步手工继续，**不安装、不阻塞**。探测成功后用对应前缀执行下列命令：

- `toolkit tasks`：查 active 总览（替代第 1 步人工翻目录）
- `toolkit tasks check`：自动校验（替代第 4 步自查清单）
- `toolkit tasks archive`：自动归档（替代第 5 步，含排他锁防并发；可 `--dry-run` 预演）
- `toolkit tasks normalize`：归档后核验归档块（元数据完整性/日期漂移/排序），可 `--fix` 自动修复
- 任务目录非默认 `.tasks` 时加 `--dir <path>`
