# 发版与 CHANGELOG

> 本技能版本 1.3.4（随 @fxri/toolkit 同批分发）。被问版本时即报此值（不读磁盘、不跑 CLI）；与 `toolkit skills status` 的磁盘值不一致即说明会话上下文已过期，开新会话即可。

## 何时使用

- 记录变更（创建变更集）、消费变更集发版、格式化 CHANGELOG（语义触发，不要求字面一致；触发词见 frontmatter `description`）
- 触发前置条件：**用户明确表达发版或记录变更意图**。⚠️ **git 提交 ≠ 发版**：用户说「提交个版本 / 先提交一版 / 提交一下 / commit 这版」通常指把当前改动 git 提交（涉及任务时先走 fxri-plan-to-task / fxri-session-recap 收尾再提交），**不触发本技能**；纯日常对话出现「版本」字样也不触发
- 拿不准用户意图时向用户确认，不猜

**何时不使用**：日常 commit message 撰写、git 提交操作、与发版无关的文档修改。

## 前置检查

- ⚠️ 发版不是必经步骤：仅在用户明确要求，或用户全局 / 个人 / 项目规则约定时才进入本技能，不主动发版
- ⚠️ **发版是收尾动作，不是任务**：本技能不为发版本身建档——发版的输入是「已归档的任务改动」，发版过程及其固有产物（版本号、更新日志、标签）不构成任务、不作为建档对象。例外：过程中暴露的、需改仓库文件才能修复的缺陷（打包配置错误、发布渠道错误、版本号冲突）→ 走 fxri-plan-to-task 先建档再改
- `.tasks/active/` 存在未归档任务 → 先完成归档再发版（任务归档是发版的前置顺序）
- **覆盖核对**：本次待发布的改动逐项确认已有归档记录；出现「有改动却无归档记录」→ 先补归档（fxri-session-recap 模式一）再发版
- 项目根存在 `.changeset/` 目录 → 走「changesets 流程」
- 不存在 → 走「手工模式」（规范见 `references/changelog-format.md`）

## 发布与推送的授权边界

- 发布（`npm publish`）、推送（`git push`）、打远端标签属不可逆动作，默认**逐次授权**：计划表里列出发版、上一任务发过版、前几次会话推送过，都不构成本次授权
- **当前指令已含发版 / 推送授权时直接执行**，不必重复询问；授权按语义判定（发版、发布、出个版本、推上去、同步远端等），示例非穷举
- 授权带范围：只说发版未说推送 → 推送仍需询问；只说推某个远端 → 其余远端不推
- 会话级显式授权（如「本次会话后续发版和推送都授权」）优先于逐次授权默认值，但仅本次会话有效、不持久化，用户撤回即失效（通用原则见 `fxri-plan-to-task` 的讨论态 / 方案态 / 执行态闸门）
- 执行到不可逆步骤必须停下单独询问，不得以「已经发版了，不推送没办法」倒逼用户

## changesets 流程

1. 记录变更：`npx changeset`（或项目包管理器等价脚本）
   - **写法**：变更描述逐条以 `- 类型：描述` 书写——`类型：` 前缀（`新增：` / `修复：` / `优化：`）作归类信号，`- ` 列表标记让每条独立成项（缺标记的裸行会被 changesets 并入相邻条目作续行，整段塌成一条、只有首行归组剥前缀）
   - **级别**：按用户影响阶梯选 bump（整体重做→major、破坏既有用法需改→minor、其余含新增小能力与同能力替代实现→patch，含 SemVer 偏离与迁移护栏的完整口径见 `references/changelog-format.md` 的「版本口径」）；前缀只看变更性质，与 bump 正交，patch 也可挂 `新增：`
   - **早期自查**：写完可跑 `toolkit tasks check`，它扫 `.changeset/` 下待发布变更集，逐文件报出缺前缀条目与未加 `- ` 的裸行及条数（免得到发版、变更集源被消费删除后才由 changelog 侧兜底告警）
2. 合并同版本变更集：消费前逐条核对 `.changeset/*.md`，以「从上一已发布版本升级上来的用户」为视角，只保留净用户可见结果；可先跑 `toolkit changelog audit` 获取同对象候选（只提示，不自动改写）
   - **判定基准**：看改动对象在上一已发布版本中是否已经存在。上一版不存在的新能力，本次内的 `新增 → 修改 / 修复` 折叠为一条最终状态；上一版已存在的行为，其 `修改` / `修复` 必须体现在最终条目中，不得整条丢弃；本版本内完全回退且从未发布的能力整条删除；`修改` 后又回退到上一版行为属净变更零，同样删除
   - **归并类型**：按相对上一版的净效果定类型——新能力仍是 `新增：`；既有行为的修正用 `修复：`、行为或参数调整用 `修改：`、体验与性能改进用 `优化：`；`重大：` 不降级、不与其它类型合并；依赖更新不参与合并
   - **边界**：只处理同一包、同一版本块（本次发布）；不跨版本、不改历史块；无法确认是否同源时保留原条目，不猜
   - **留痕**：输出折叠清单（保留哪条、哪条并入哪条、删除哪条及原因）；过程记录留在变更集、提交与任务档，不进入 CHANGELOG
   - 删除或改写被覆盖的变更集文件后，按净变更重新核对 bump：新能力被整体回退时，相应的 minor 不再成立
3. 消费发版：`npx changeset version`——自动写版本号与 CHANGELOG
4. 格式化：按 `references/changelog-format.md` 的语义分组规则归类条目、转换分组标题、润色为项目语言风格（中文示例：`### Patch Changes` 下的 `- 修复：xxx` → `### 🐛 问题修复` 下的 `- xxx`——归类后类型前缀被剥离，类型由分组标题承接）；分组维度与 bump 维度正交，条目归组只看类型前缀；无 `###` 分组的版本块（如手工维护的更新记录）同样按前缀生成规范分组并剥离前缀，默认只处理最新一块；格式化前再核对一次第 2 步的净变更，避免过程性条目漏收敛
5. 归一：润色后跑一次 `toolkit changelog format --history`——人工润色（含补写历史块明细）容易在条目之间留空行，该命令按「同组顶层条目逐行相邻」重排历史块；项目另有更新日志镜像页（如 `docs/changelog.md`）时再跑一次 `toolkit changelog doc`，否则镜像一致性校验会失败
6. 清理：删除已消费的 `.changeset/*.md`
7. 门禁：发布前跑一次项目的验收命令（如 `pnpm verify`）——**关卡设在发布前而非推送前**：发布到包仓库 / 制品库不可逆，推送失败重推即可，故必须拦在不可逆动作之前；任一步失败即中止发版，不进入提交、打标签、发布
8. 发布：提交版本与 CHANGELOG 改动 → 打 `vX.Y.Z` 标签 → 按项目渠道发布（如 `npm publish`）

⚠️ 自动生成的条目必须人工核对润色，与仓库既有 CHANGELOG 风格保持一致。

## 手工模式（无 changesets 项目）

版本号与 CHANGELOG 全部手工维护：版本标题、发布日期行、分组标题与条目格式见 `references/changelog-format.md`；多语言四段结构（语义分组 / 标题替换映射 / 依赖更新文案 / 发布日期后缀）同文件。

## 失败模式

| 症状 | 处置 |
| --- | --- |
| version 后 CHANGELOG 分组标题仍是英文 | 按 references 的映射表补一次格式化 |
| CHANGELOG 出现「- - 条目」双前缀伪影（变更集条目以 `- ` 开头） | `toolkit changelog version/format` 已自动还原为顶层条目；手工模式按 references 规则手动清理 |
| 条目与仓库既有风格不一致 | 人工润色为项目语言与句式，勿保留机器直译 |
| 变更集遗漏（发版后才发现功能未记录） | 补建变更集随下次发版；本次在发布说明中人工补充 |
| `toolkit tasks check` 报「变更集条目缺类型前缀」 | 打开所列文件，给缺前缀的**顶层条目**按「类型：描述」补前缀（缩进续行随父条目迁属、无需加）；补前缀只改分类信号，不改变 bump 级别 |
| `toolkit tasks check` 报「变更集条目未加「- 」列表标记」 | 打开所列文件，把裸行逐条改为 `- 类型：描述`（成因见 changesets 流程第 1 步）；若已发版才发现，说明该版本块条目可能已挤在单组且前缀未剥离，按 references 的「人工事实更正」修 `CHANGELOG.md` 并重跑 `toolkit changelog doc` |
| 改动已发布却无归档记录（有提交、无任务档） | 先补归档（fxri-session-recap 模式一）再继续发布后续步骤；发版本身不补建档 |
| 发版后历史块内出现多余空行（`自举一致性` 类零改动用例失败） | 跑 `toolkit changelog format --history` 归一（**必须带 `--history`**，默认模式不动历史块），再补跑一次 `toolkit changelog doc` |
| 格式化时 stderr 报「归类后条目数由 N 降为 M，疑似丢失内容」 | 归类只应搬移条目，减少即疑似丢内容：核对该版本块是否含非纯条目分组（标题下先出现正文）或被保留分组；若已在流程第 2 步按净变更合并，条目减少属预期，对照折叠清单确认后忽略，否则按 references 的归类规则修回 |
| 同一版本块同时出现「新增 X / 修改 X / 修复 X」，用户只需知道最终能力 | 按流程第 2 步做净变更合并：只折叠上一版不存在的能力；上一版已存在行为的修改 / 修复必须体现在最终条目中；输出折叠清单后再格式化 |
| 一批改动含新增能力 / 参数，却整批按 `修复：` 前缀登记（整块落 `问题修复` 组）——常见于 bump 判定为 patch 时，误以为级别与条目前缀绑定 | 前缀按**变更本身性质**逐条定：新增命令 / 参数 / 产物用 `新增：`、缺陷纠正用 `修复：`。分组只看前缀、与 bump 正交，**patch 也可挂 `新增：`**——bump 按用户影响阶梯判（新增小能力即 patch），口径见 references 的「版本口径」 |

## 可选加速（不构成依赖）

⚠️ 工具探测顺序（先项目内、后全局）：先 `pnpm exec toolkit --help`（项目 devDependency，npm 项目等价 `npx toolkit`），失败再 `toolkit --help`（全局安装）；两者都不可用即工具未安装，按各步手工继续，**不安装、不阻塞**。探测成功后用对应前缀执行下列命令：

- `toolkit changelog add`：创建变更集（等价 changeset）
- `toolkit changelog version`：发版并自动做中文分组标题格式化
- `toolkit changelog audit`：扫描待发布变更集，列出同对象「新增 + 修改 / 修复 / 优化」候选（只提示，不自动改写）
- `toolkit changelog format`：仅格式化既有 CHANGELOG
- `toolkit changelog format --history`：连带追溯改写历史版本块（用户主动要求修正历史块时才加，默认不动）
- `toolkit changelog version --lang <语言>`：切换输出语言（内置 zh / en，其余可配置扩展）
- `toolkit tasks check`：扫 `.changeset/` 下待发布变更集并逐文件报出缺前缀条目与未加 `- ` 标记的裸行（流程第 1 步的早期自查入口，归档前的 `tasks check` 即含此项）
- `toolkit skills install` / `toolkit skills status`：把本包 fxri-* 技能分发到目标技能目录（`--scope` 缺省按 CLI 安装位置自动判定全局面 / 项目面；项目面真源落 `<仓库根>/.agents/skills/`、其余候选目录落入口薄壳，随仓库入库后队友 clone 即用）/ 查看链接、副本与项目面现场（技能随包同源分发，与 CLI 同一发布批次；技能内容版本独立编号，`skills status` 会打印各技能真源版本）
