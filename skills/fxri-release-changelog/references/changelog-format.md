# CHANGELOG 格式规范

## 1. 文件结构（中文示例）

```markdown
## 1.5.3

> 2026-09-03 发布

### 🐛 问题修复

- 修复xxx：……

### 📦 其他变更

- 补齐某处兜底逻辑
```

规则：

- 版本标题 `## {版本号}`；隔一行后接引用行 `> {YYYY-MM-DD} 发布`（标题与日期行之间保留一个空行）
- 分组标题 = emoji + 组名，一行一组，按**语义分组顺序**输出——重大变更 → 新增功能 → 功能调整 → 优化改进 → 问题修复 → 文档更新 → 清理移除 → 依赖变更 → 其他变更；空组省略
- 条目一行一条，项目语言句式（中文条目句末不加句号），与仓库既有风格一致
- 同一分组内顶层条目**逐行相邻输出**（条目之间不留空行，缩进子项紧随父条目），分组之间与日期行前后各留一个空行——这是格式化的**不动点**：合规文件重复执行 `toolkit changelog format` 应零改动，`--history` 归一之后同理
- ⚠️ 变更集条目以 `- ` 开头时，changesets 会写入 `- - 条目` 首行并把后续行缩进 2 空格（伪影）；`toolkit changelog version/format` 会自动还原为顶层条目，手工模式需手动清理
- 分组标题集合随版本演进而变化；**历史版本块保留当时口径，`toolkit changelog format` 不追溯改写**（只归类 changesets 本次新写入的英文源标题块）
- ⚠️ **人工事实更正**：已发布版本块原则上不追溯改写；确需更正**事实性错误**（归组误判、错别字等）时允许人工修改——仓库 `CHANGELOG.md` 为真源，已发布的包产物与版本标签是**不可变快照**、不回补，正确版随下次发版由整份 CHANGELOG 带入

## 2. 语义分组归类

分组维度（条目**变更类型**）与版本号维度（bump）正交：条目归入哪一组，只看条目自带的**类型前缀**，与它来自 `Major/Minor/Patch Changes` 哪一块无关。

**类型前缀 → 语义槽位**（全局一份、全语言共用，故任一语言的条目在任何输出语言下都能正确归组）：

| 类型前缀（中 / 英） | 语义槽位 | zh 组标题 | en 组标题 |
| --- | --- | --- | --- |
| `重大：` / `Breaking:` | `breaking` | `### 🚨 重大变更` | `### 🚨 Breaking Changes` |
| `新增：` / `Added:` | `added` | `### ✨ 新增功能` | `### ✨ Added` |
| `修改：` / `Changed:` | `changed` | `### 🔧 功能调整` | `### 🔧 Changed` |
| `优化：` / `Improved:` | `improved` | `### ⚡ 优化改进` | `### ⚡ Improved` |
| `修复：` / `Fixed:` | `fixed` | `### 🐛 问题修复` | `### 🐛 Fixed` |
| `文档：` / `Docs:` | `docs` | `### 📝 文档更新` | `### 📝 Docs` |
| `清理：` / `Removed:` | `removed` | `### 🧹 清理移除` | `### 🧹 Removed` |
| `依赖：` / 源文本 `- Updated dependencies` | `deps` | `### 🔗 依赖变更` | `### 🔗 Dependency Updates` |
| 无前缀兜底 | `other` | `### 📦 其他变更` | `### 📦 Other` |

**无前缀条目的兜底规则**：按条目**所属源组标题**声明的影响级别归组——`### Major Changes` → `breaking`、`### Minor Changes` → `added`、`### Patch Changes` → `other`；不从版本号推导。

**缺前缀的检测入口**：`toolkit tasks check` 扫 `.changeset/` 下待发布变更集（`.md` 且非 `README.md`）的**顶层条目**，逐文件报出缺前缀条目数与首条行号（归档前的早期自查）；发版时 changelog 侧另有兜底告警。前缀识别取全局表与各配置语言 `prefixes` 的并集（自定义语言不误报），依赖源条目归 `deps` 不计缺前缀，缩进续行随父条目迁属、不参与识别。

**追溯历史块的兜底规则**（`--history`）：历史块没有英文源组标题，改按**所属既有组标题**查槽位——先查当前语言组标题，再查历史组标题表（如 `### 🐛 补丁修复` → `fixed`）；两处都识别不出则整组连同标题保留、不臆造归属。

**依赖条目不走前缀解析**：源组标题 `### Dependent Changes` 整块，以及源文本 `- Updated dependencies`（含缩进子项）一律归入 `deps` 槽位。

**归类后剥离类型前缀**：条目归入槽位后，其已被识别的 `类型：` 前缀被剥离（`- 修复：xxx` → `- xxx`）——前缀只是归类信号，类型已由分组标题承接，留在明细里属冗余。未识别的前缀（如正文里的 `说明：`）与依赖源条目原样保留，剥离后文本为空也不改动。默认模式与 `--history` 追溯模式同此规则。

同一槽位来自多个源块时合并为单组，组内保持条目原出现顺序；缩进续行随父条目整体迁移。

**归类只搬移、不删内容**：归类只重组「纯条目分组」——分组标题下若在首个条目之前出现非空正文，判据不成立，整块保持原样以免丢内容；未参与归位的分组连同标题按原相对顺序附于块末，不臆造归属、不静默丢弃。CLI 在归类前后做条目数自检，减少即告警（正常合并发生在自检之后、不误报）。

**能力量级 → bump**（撰写变更集时按此选影响级别）——版本号由变更集 frontmatter 的 bump 声明决定，**与条目前缀正交**：前缀只负责把条目归入哪一组，不决定版本号。

| 影响级别 | 判定锚点（按改动的**能力量级**，不按条目前缀） |
| --- | --- |
| major | 破坏性变更——既有契约 / 行为不兼容 |
| minor | 新增**全新的大功能 / 独立新能力**——用户升级后获得一整块新的使用方式 |
| patch | 存量能力上的**修补与增量**——修复、优化、配套补齐，以及新增的**小命令 / 小参数 / 小产物**等，只要不属于「全新大功能」 |

口径要点：

- **判 bump 看能力量级、不看前缀**：`新增：` / `修改：` 只表示条目归入「新增功能」/「功能调整」组，不隐含 minor——新增的小能力照常按 patch 登记，无需例外申报
- **不得为凑版本号降级**：确属「全新大功能 / 独立新能力」的改动不得为对齐目标版本号而按 patch 记；`重大：`（破坏性）不可降至 patch
- 条目须**分条登记用户可感知的变更**——新增命令 / 参数分开列，不写抽象能力名（否则用户升级后不知多了什么）

## 3. 多语言扩展

每种语言约定四段结构：

- `groups`（可选）：语义分组表，每项 `{ slot, title, prefixes? }`——`slot` 取自全局语义槽位，`title` 为本语言组标题，`prefixes` 为本语言自有前缀（可选，识别时与全局前缀表取并集）；缺省时退化为纯替换（仅 `replacements` 生效）
- `replacements`：兜底替换映射表（源标题 → 目标标题）
- `deps`：依赖更新条目固定文案
- `released`：发布日期行后缀（中文为「发布」，英文为「released」；同时用于识别既有日期行，故自定义语言填非「发布/released」值也能幂等）

新增语言时先补全四段，再按映射转换标题、润色条目。
