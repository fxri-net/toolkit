# 会话归档、上下文恢复与历史修正

> 本技能版本 1.6.13（随 @fxri/toolkit 同批分发）。被问版本时即报此值（不读磁盘、不跑 CLI）；与 `toolkit skills status` 的磁盘值不一致即说明会话上下文已过期，开新会话即可。

## 何时使用

- **沉淀**（模式一）：会话接近尾声，用户表达收尾意图（今天先到这 / 收个尾 / 把结论记下来 / 归档本次会话）
- **恢复**（模式二）：新会话开场，用户表达接续意图（恢复上下文 / 继续上次 / 上次做到哪了）
- **修正**（模式三）：用户发现历史任务时间不准，要批量修正
- ⚠️ 触发识别靠语义不靠字面（意图与示例见 frontmatter `description`，非穷举）：「收个尾」可能指收尾工作也可能指会话收尾，结合上下文判断，无法判断时问用户
- 不使用：会话中途的常规方案建档（fxri-plan-to-task）、与交接无关的技术总结、日常对话

## 能力边界

- 新会话读不到其他会话的内部上下文；解法是把记忆**沉淀进仓库文件**（`.tasks/`）；个别 agent 可直读历史转录，属非通用高级路径，不依赖
- 本技能**不直接执行 git 提交**：提交 / 推送 / 发版由用户规则决定（见 R2）

## 读取地图

| 你在做什么 | 必读 | 可跳过 |
| --- | --- | --- |
| 收尾沉淀 | 本文件 R1–R3、规范提炼子流程、模式一 | 模式二 / 三 |
| 开场恢复 | 本文件 R1 / R2 + `references/mode-2-recovery.md` | 模式一 / 三 |
| 批量修正历史时间 | 本文件 R1 + `references/mode-3-time-fix.md` | 模式一 / 二 |
| 读写 conventions 载体 | 本文件 R3 + `../fxri-plan-to-task/references/conventions-spec.md`、`conventions-maintenance.md` | 其余 |

兄弟技能路径不存在时，改读 `toolkit skills status` 打印的「技能源」目录下同名文件。

## 核心规则

### R1 四级时间源（一切时间字段的唯一口径）

「会话当时的真实时间」不可凭空估算。created / completed / updated 按以下优先级取证：

| 级 | 时间源 | 取证 | 适用 |
| --- | --- | --- | --- |
| 0 | 任务完成当场打点 | 完成时立即执行命令取时间（Windows `Get-Date -Format "yyyy-MM-dd HH:mm"`，macOS/Linux `date "+%Y-%m-%d %H:%M"`） | 会话内即时归档（首选） |
| 1 | 聊天记录可见的准确时间戳 | 用户贴过的日志/终端输出时间戳、口述的确定时刻 | 收尾补档且上下文有可信时间 |
| 2 | 任务改动的 git 提交时间 | `git log --format="%h %ci" <file>` | 任务有对应提交 |
| 3 | 系统当前时间兜底 | 当场取时，**正文标注「时间为收尾补记」** | 前三级皆不可得 |

- 第 3 级是兜底不是默认——能用前三级必须用；用第 3 级必须显式标注，避免「看似精确实则编造」
- 归档块完成时间早于归档动作时间属正常（补档 / 历史修正）
- 完成时间晚于当前系统时间或恰为零点整会被 CLI 告警，说明时间源取错，需重新取证（前者含跨时区容差：晚于当前时刻 14 小时以上才告警）

### R2 统一收尾链路（能力终点 = 沉淀）

```
任务终结 → 归档 → 规范沉淀（硬终点） → 验收 → 提交/发版/推送（默认需确认；当次指令已含授权则直接执行）
```

- 顺序与边界以 `fxri-plan-to-task/references/task-spec.md` §6 为准：归档是中间步骤、验收须晚于归档、提交 / 发版 / 推送非必经、动作不算改动才算；本技能不重复
- 会话特有：规范沉淀与会话级提炼同落点、与已有规范合并去重；会话内发现的缺失归档须补档
- **跨仓库会话各自归档**：各仓在各自仓库建档归档，任务档只记本仓改动与动机；`scope` 只标本仓内的端 / 面

### R3 规范落点：`.tasks/conventions/` 载体

- 唯一落点 `.tasks/conventions/`：`index.md` 唯一入口（形态标记 + 端清单 + 活跃索引），`history.md` 语义演进（仅追加），`retired.md` 退休台账，
   `common.md`、端分册与主题分册承载条文；结构与分册表单见 `conventions-spec.md`，读写细则见 `conventions-maintenance.md`
- 两级沉淀同一载体：**任务级**（fxri-plan-to-task 归档时）只在单任务产出可升格规范时追加，无则静默；**会话级**（本技能）聚合全会话候选，与已有规范合并去重——跨任务重复模式在此补，用户明示规则兜底
- **归属判定**：先问「哪些任务会遇到这条」→ 跨面归 `common`，否则写入主题 / 端分册。禁止跨端合并；`common` 只放跨面原则、不是「不确定归哪」的暂存区。
   端名与 `scope` 取值逐字一致；`index.md` 顶部的端清单是端的唯一权威，不扫目录。
   读取按索引路由：按索引行适用面命中即读其归属分册或单一事实源，**无命中即止，不恒叠加 `common.md`**
- 写前**必须用户确认**；同义规范不重复记录，只补差异或合并增强；一次性决策留在任务正文（升格标准：重复出现 ≥2 次，或用户明示「以后都要这样」）
- 语义变更走「`history.md` 留痕 + 索引行更新」；条目作废走**迁出 + 三层清理**（索引行删并迁 `retired.md`、物理删除分册小节、外部单一事实源同步删改）
- 兼容读：先找 `conventions/index.md`，不存在再看旧单文件 `conventions.md`（提示可迁移），并存时以目录形态为准；表格形态按 `conventions-maintenance.md`；
   载体为 v1 / v2，或已成 v3 却残留 v2 独有列 / 表头首格非 `ID` 的形态残留时，按 `conventions-migration.md` 的迁移与升级链路处置（可中断不丢内容）

### 规范提炼子流程（三模式共用）

1. 收集候选：用户明示的规则、与已有规范重复印证的决策、跨任务重复模式
2. 输出候选清单（含来源任务、建议归属与理由），交用户确认
3. 确认后写入：`index.md` 补索引行（稳定 ID `C-<n>` + 归属），条文归位分册；语义变更先 `history.md` 留痕，作废按三层清理
4. 无候选完全静默，不强加流程

## 模式一：沉淀本次会话

> 目标：会话结束后，任何人（或新会话 AI）只看仓库就能还原本次做了什么、为什么、还剩什么，且时间与真实发生时刻一致。

1. **全量回放**：按时间线回放本会话，产出**全部任务候选清单**（结论、决策及理由、代码改动、未尽事项、用户明示要求记录的内容；无关闲聊不记）。⚠️ 决策及其理由必须记——会话一关就丢
2. **事前核对（防漏档关口）**：候选清单每条附时间证据级别（0/1/2/3），**先输出给用户确认无遗漏**，确认后才落盘
3. **逐条落盘**（先查后写；格式见 `../fxri-plan-to-task/references/task-spec.md`，兄弟路径不存在时读包内真源）：
   - 多仓会话逐仓逐任务建档：每个产生改动的仓库各自独立建档（一任务一档，不得合并）；只读参与的仓库不建档
   - 有对应任务 → 更新原文件，正文追加结论与决策，时间字段按 R1 校准
   - 无对应任务但有独立成果 → 按规范建档，`created` 取任务真实创建日
   - 未尽事项 → 拆独立任务（status: 待办），不留游离待办；收尾动作不单独成档，缺归档须补档（见 R2）
4. **归档**：按 task-spec「手工归档步骤」执行（合并归档块 → 降序重排 → 写回 → 删源文件 → 清理空月份目录），或 `toolkit tasks archive` 自动化
5. **技能使用补报（收尾兜底）**：回看本会话全部 Skill 工具调用，按技能名汇总次数；
    对会话中未上报过的技能执行一次 `toolkit usage record --skill A --skill A --skill B`（按次数重复传参），只传技能名、不传参数；`record` 入队即返回，
    不阻塞收尾；`toolkit` 不可用时在回报中说明，不静默跳过
6. **规范沉淀（终点）+ 收尾**：按提炼子流程做会话级沉淀；
    随后按 R2 决定是否验收 / 提交；提交前向用户展示待提交内容供确认；**逐任务交付**，不攒批、不混无关改动（一个任务至少一次提交、允许多次）
7. **回报**：列出沉淀的任务清单、归档位置、技能补报结果与规范变更，确认无遗漏后结束

## 模式二：恢复上下文

> 目标：新会话快速重建现场，按「全量索引 → active 精读 → 近窗归档」三层控制上下文成本。

- 关键护栏：近窗按**时间连续性**判定不按数量，被 ≥1 年空洞隔断的旧归档只入索引、不精读；active 任务 `updated` 超 1 年标注「疑似搁置」；**恢复主体只读**，写任务区 / 载体须用户确认后另行执行
- 完整步骤见 `references/mode-2-recovery.md`

## 模式三：批量修正历史任务时间

> 目标：旧规则沉淀的归档时间与真实发生时刻不符时批量修正；识别靠证据，CLI 只做结构迁移、不推断时间。

- 关键护栏：每条改动须附 R1 级别证据并交用户逐条确认，不自行推断；改值后用 `toolkit tasks normalize --fix` 迁移，再以只读模式核验 0 漂移
- 完整步骤见 `references/mode-3-time-fix.md`

## 失败模式

| 症状 | 处置 |
| --- | --- |
| 多个任务混在一起说不清 | 按任务逐条拆开写；对应不上的问用户 |
| 未尽事项塞进已完成任务正文 | 拆独立任务，保持归档块干净 |
| completed 填了收尾时刻 | 按 R1 重新取证 |
| 恢复时 active 有游离文件 | 先按规范移入 `active/{YYYYMM}/` 再读 |
| 归档历史量太大撑爆上下文 | 走 L2 降级：只出统计 + 近期明细，按需拉取更早 |
| 新会话仍说「找不到上下文」 | 先查磁盘文件是否存在、是否落在正确月份目录、载体是否同目录；跨环境才需查是否已提交 |
| 归档未提交，新会话能恢复吗 | 同机同目录**能恢复**（读磁盘，与提交状态无关）；仅跨环境（换机 / checkout、clean）未提交内容会丢 |
| 多仓会话只在一个仓建档 | 按仓库清单逐仓逐任务补建；任务档只记本仓改动与动机 |
| 恢复后看不出任务先后 | 有展示表按表；无表按 active 正文「批次 / 计划位置 / 前置」行重建 |

## 可选加速（不构成依赖）

⚠️ 先项目内后全局探测：`pnpm exec toolkit --help`（npm 项目等价 `npx toolkit`）→ `toolkit --help`；都不可用即按各步手工继续，**不安装、不阻塞**。探测成功后用对应前缀执行：

- `toolkit tasks`：模式二全量索引（替代人工翻目录）；`toolkit tasks stats`：周期统计
- `toolkit tasks archive`：模式一归档自动化（排他锁防并发；`--dry-run` 预演）
- `toolkit tasks normalize`：模式三迁移核验（`--fix` 迁移 / 只读检查）
- `toolkit tasks check`：落盘后校验
- `toolkit conventions status|upgrade|format`：载体体检 / v1、v2 升级 / 表格归一
- `toolkit skills install` / `skills status`：分发技能与查看现场（技能随包同源分发，与 CLI 同一发布批次；技能版本独立编号）
- 任务目录非默认 `.tasks` 时加 `--dir <path>`
