# 会话归档、上下文恢复与历史修正

> 本技能版本 1.6.0（随 @fxri/toolkit 同批分发）。被问版本时即报此值（不读磁盘、不跑 CLI）；与 `toolkit skills status` 的磁盘值不一致即说明会话上下文已过期，开新会话即可。

## 何时使用

- **沉淀模式（模式一）**：会话接近尾声，用户表达收尾意图（如「今天先到这 / 收个尾 / 把结论记下来 / 归档本次会话」）
- **恢复模式（模式二）**：新会话开场，用户表达接续意图（如「恢复上下文 / 继续上次 / 上次做到哪了」）
- **修正模式（模式三）**：用户发现历史任务时间不准，要批量修正
- ⚠️ 触发识别靠语义不靠字面（完整触发词见 frontmatter `description`）：用户说「收个尾」可能指收尾工作也可能指会话收尾，需结合上下文判断；无法判断时向用户确认，不猜

**何时不使用**：会话中途的常规方案建档与归档（fxri-plan-to-task）；对某段代码的技术总结（与会话交接无关，不落 .tasks）；日常对话。

## 能力边界

- 所有 agent 的共性约束：新会话读不到其他会话的内部上下文，对话记录本身不可跨会话传递
- 本技能解法是把记忆**沉淀进仓库文件**（`.tasks/`）；个别 agent 可直读历史会话转录，属非通用高级路径，不依赖
- 本技能**不直接执行 git 提交**：提交/推送/发版由用户全局规则决定（见 R2）

## 核心规则（先读这段）

### R1 四级时间源（沉淀一切时间字段的唯一口径）

「会话当时的真实时间」不可凭空估算。任何时间字段（created/completed/updated）按以下优先级取证：

| 级 | 时间源 | 取证 | 适用 |
| --- | --- | --- | --- |
| 0 | 任务完成当场打点 | 任务完成时立即执行命令取时间（Windows `Get-Date -Format "yyyy-MM-dd HH:mm"`，macOS/Linux `date "+%Y-%m-%d %H:%M"`） | 会话内即时归档（首选，源头消灭补记） |
| 1 | 聊天记录可见的准确时间戳 | 用户贴过的日志/终端输出时间戳、用户口述的确定时刻 | 收尾补档且上下文有可信时间 |
| 2 | 任务改动的 git 提交时间 | `git log --format="%h %ci" <file>` 按提交时间取证 | 任务有对应提交 |
| 3 | 系统当前时间兜底 | 当场执行命令取时，**正文标注「时间为收尾补记」** | 前三级皆不可得 |

规则：
- 第 3 级是兜底不是默认——能用前三级必须用；用第 3 级必须显式标注，避免「看似精确实则编造」的时间
- 归档块完成时间可以早于归档动作时间，这是特性不是异常（补档/历史修正场景）
- 完成时间晚于当前系统时间或恰为零点整会被 CLI 告警，说明时间源取错，需重新取证（前者含跨时区容差：晚于当前时刻 14 小时以上才告警）

### R2 统一收尾链路（能力终点 = 沉淀）

```
任务终结 → 归档 → 规范沉淀（硬终点） → 验收 → 提交/发版/推送（可选，需用户确认）
```

- 归档是中间步骤，**规范沉淀才是流程终点**；沉淀时机固定：归档完成后、任何收尾动作（验收 / 提交 / 发版 / 推送）前，规范与归档文件同批落盘
- ⚠️ **验收须晚于归档**：归档会改写 `.tasks/`，且归档本身不做阻断式校验——早于归档跑验收就覆盖不到终态，归档产物等于无人校验；归档块「完成情况」只记改动事实与所用验证命令，不逐条抄写验收输出
- 提交、发版、推送**不是必经步骤**，是否执行取决于用户全局/个人/项目规则；若提交代码：先归档、后跑项目验收命令、再提交，归档文件与代码变更落在同一 git 提交
- **动作不算、改动才算**：收尾动作（提交、发版、推送、部署）本身及其固有产物（版本号、更新日志、标签）不构成任务、不单独建档；其所依据的改动须有归档记录，缺则补档
- **跨仓库会话各自归档**：整场会话涉及多个仓库时，各仓的改动在**各自仓库**里建档归档（任务档是仓库自述，只记本仓的改动与动机）；不因「同一次会话」而把另一仓的工作痕迹合并进本仓记录，`scope` 只标本仓内的端 / 面

### R3 规范落点：`.tasks/conventions/` 载体（两级沉淀同一载体）

- 唯一落点 `.tasks/conventions/`（纯 Markdown 随 git 走）：`index.md` 唯一入口（形态标记 + 端清单 + 活跃索引表，首列稳定 ID `C-<n>`），`history.md` 语义演进（独立文件、仅追加），`retired.md` 退休台账（条目作废迁入、冻结语义，按需创建），`common.md` 通用条文，`<端名>.md`（或分类标签分册）端专属条文；每条规范带来源任务与日期，可审计
- **任务级**（fxri-plan-to-task 归档时）：单任务产出可升格规范才追加，无则完全静默；**会话级**（本技能收尾时）：聚合全会话候选，与已有规范**合并去重**——跨任务重复模式在此补，用户明示规则兜底
- **归属判定**：先问「是否**所有端都适用**」→ 是则归 `common`；否则逐端确认后写入命中的端分册。⚠️ 禁止跨端合并归属（真全端才升 `common`，只适用几端则各端各记一条）；`common` 的语义是「所有端」不是「不确定归哪端」的暂存区
- **端名**：与任务 frontmatter `scope` 取值**逐字一致**（任务写 `scope: web+server` → 读 `web.md` + `server.md`，无论命中与否**恒叠加 `common.md`**；`scope` 中非端值且存在同名分册者按分类标签分册加载）；`index.md` 顶部「端清单」是端的**唯一权威**，不扫目录
- 写前**必须用户确认**；同义规范不重复记录，只补差异或合并增强
- **表格形态**：载体与任务区表格一律**紧凑形态**（单元格间只留一个空格，不做列对齐填充）；手工写表不为对齐补空格，已有填充用 `toolkit conventions format` 归一（幂等、跳过代码块、不改语义），源头由 `toolkit init` 托管的 `.prettierignore` 排除任务区
- 一次性决策留在任务正文，不进规范（升格标准：重复出现 ≥2 次，或用户明示「以后都要这样」）
- **内容修订 vs 形态迁移**：语义变更走「`history.md` 追加留痕 + index 行更新」；条目作废走**迁出 + 三层清理**（索引行删除并迁入 `retired.md` 冻结语义、物理删除分册内该条小节、外部单一事实源同步删改，不留「已废弃」占位）；发现旧单文件 `conventions.md`、载体为 v1 / v2，或已成 v3 却残留 v2 独有列 / 表头首格非 `ID` 的**形态残留**时，一律按 `conventions-migration.md` 的迁移与升级链路处置（可中断不丢内容）
- ⚠️ 兼容读：先找 `conventions/index.md`，不存在再看旧单文件 `conventions.md`（提示可迁移）；两者并存时以目录形态为准
- 完整细则（三分区结构、形态标记与稳定 ID、表列定义、分层读写判定、修订与迁移步骤、自查清单）见 `../fxri-plan-to-task/references/conventions-spec.md`；形态判据、迁移与升级步骤见同目录 `conventions-migration.md`，文风模板见 `conventions-templates.md`；兄弟路径不存在时改读包内真源——`toolkit skills status` 打印的「技能源」目录下同名文件

### 规范提炼子流程（三模式共用）

1. 对照 conventions 载体收集候选：会话中用户明示的规则、与已有规范重复印证的决策、跨任务重复模式
2. 输出候选清单（每条含来源任务、建议归属与理由），交用户确认
3. 用户确认后写入载体：`index.md` 补索引行（首列稳定 ID `C-<n>` / 归属），条文归位到 `common.md` 或命中的端分册 / 分类标签分册；语义变更先在 `history.md` 追加一行留痕，条目作废按三层清理迁入 `retired.md`
4. 无候选时完全静默，不强加流程

## 模式一：沉淀本次会话

> 目标：会话结束后，任何人（或新会话 AI）只看仓库就能还原本次做了什么、为什么、还剩什么，且时间与会话真实发生时刻一致。

1. **全量回放**：按时间线完整回放本会话，产出**全部任务候选清单**（含结论、决策及理由、代码改动、未尽事项、用户明示要求记录的内容；与工作产出无关的闲聊不记）。⚠️ 决策及其理由必须记——决策散在对话里，会话一关就丢
2. **事前核对（新增，防漏档的关口）**：把任务候选清单（每条附时间证据来源：0/1/2/3 级）**先输出给用户确认无遗漏**，确认后才开始落盘——用户切会话漏档的痛点在结构上解决
3. **逐条落盘**（先查后写；格式与目录规范见 `../fxri-plan-to-task/references/task-spec.md`；fxri-plan-to-task 未一并安装、该兄弟路径不存在时，改读包内真源——`toolkit skills status` 打印的「技能源」目录下 `fxri-plan-to-task/references/task-spec.md`）：
   - **多仓会话逐仓逐任务建档**：会话涉及多个仓库时，每个产生改动的仓库按任务清单各自独立建档（一任务一档，不得把同仓多个任务合并为一档）；只读参与的仓库不建档
   - 会话工作有对应任务 → 更新原文件：正文追加结论与决策，时间字段按 R1 校准
   - 无对应任务但有独立成果 → 按 fxri-plan-to-task 规范建档，created 取任务真实创建日
   - 未尽事项 → 拆独立任务文件（status: 待办），不在正文留游离待办
   - 收尾动作及其固有产物不单独成档，所依据改动缺归档时须补档（见 R2）
4. **归档**：终结态任务按 task-spec「手工归档步骤」执行（合并归档块 → 降序重排 → 写回 → 删源文件 → 清理空月份目录），或 `toolkit tasks archive` 自动化
5. **规范沉淀（终点）**：按「规范提炼子流程」执行会话级提炼，写入 conventions 载体
6. **收尾边界**：沉淀即本技能流程终点，提交、发版、推送按用户规则决定（见 R2）；⚠️ 验收须晚于归档；**逐任务交付**——一个任务至少一次提交、允许多次，不得把多个任务攒成一个提交，也不得为凑一次提交塞入无关改动；提交前向用户展示待提交内容供确认
7. **回报**：向用户列出本次沉淀的任务清单、归档位置与规范变更，确认无遗漏后再结束

## 模式二：恢复上下文

> 目标：新会话快速重建现场，按「全量索引 → active 精读 → 近窗归档」三层控制上下文成本。

- 关键护栏：近窗按**时间连续性**判定不按数量，被 ≥1 年空洞隔断的旧归档只入索引、不精读；active 任务 `updated` 超 1 年标注「疑似搁置」；**恢复主体只读**，写任务区 / 载体须用户确认后另行执行
- 完整步骤见 `references/mode-2-recovery.md`

## 模式三：批量修正历史任务时间

> 目标：旧规则沉淀的归档时间与真实发生时刻不符时批量修正；识别靠证据，CLI 只做结构迁移、不推断时间。

- 关键护栏：每条改动须附 R1 级别证据并交用户逐条确认，不自行推断；改值后用 `toolkit tasks normalize --fix` 迁移，再以只读模式核验 0 漂移
- 完整步骤见 `references/mode-3-time-fix.md`

## 失败模式

| 症状 | 处置 |
| --- | --- |
| 会话收尾时多个任务混在一起说不清 | 按任务逐条对应拆开写；对应不上的问用户 |
| 未尽事项塞进已完成任务正文 | 必须拆独立任务，保持已完成任务归档块干净 |
| completed 填了收尾时刻而非真实完成时刻 | 按 R1 四级时间源重新取证（git log / 聊天记录时间戳） |
| 恢复时 active 有游离文件（不在月份目录） | 先按规范移入 `active/{YYYYMM}/` 再读 |
| 归档历史量太大撑爆上下文 | 走 L2 降级：只出统计 + 近期明细，按需拉取更早 |
| 新会话仍说「找不到上下文」 | 先查磁盘文件是否存在、是否落在正确月份目录、conventions 载体是否同目录；跨环境场景（换机 / 工作区被 git 清理）才需查是否已 git 提交 |
| 归档未提交，新会话能恢复吗 | 同机同目录**能恢复**（恢复读磁盘 `.tasks/` 文件，与提交状态无关）；仅跨环境（换机 / checkout、clean 清掉工作区）时未提交内容会丢，恢复才依赖提交 |
| 多仓会话只在一个仓建档 | 按仓库清单逐仓逐任务补建；任务档只记本仓的改动与动机 |
| 恢复后看不出任务先后 | 有展示型计划表则按表；无表时按各 active 任务正文的「批次 / 计划位置 / 前置」行重建顺序 |

## 可选加速（不构成依赖）

⚠️ 工具探测顺序（先项目内、后全局）：先 `pnpm exec toolkit --help`（项目 devDependency，npm 项目等价 `npx toolkit`），失败再 `toolkit --help`（全局安装）；两者都不可用即工具未安装，按各步手工继续，**不安装、不阻塞**。探测成功后用对应前缀执行下列命令：

- `toolkit tasks`：模式二 L0 全量索引（替代人工翻目录）
- `toolkit tasks stats`：模式二周期统计
- `toolkit tasks archive`：模式一第 4 步自动化（含排他锁防并发；可 `--dry-run` 预演）
- `toolkit tasks normalize`：模式三迁移核验（`--fix` 迁移 / 只读检查）
- `toolkit tasks check`：落盘后校验
- 任务目录非默认 `.tasks` 时加 `--dir <path>`
- `toolkit skills install` / `toolkit skills status`：把本包 fxri-* 技能分发到目标技能目录（`--scope` 缺省按 CLI 安装位置自动判定全局面 / 项目面；项目面真源落 `<仓库根>/.agents/skills/`、其余候选目录落入口薄壳，随仓库入库后队友 clone 即用）/ 查看链接、副本与项目面现场（技能随包同源分发，与 CLI 同一发布批次；技能内容版本独立编号，`skills status` 会打印各技能真源版本）
