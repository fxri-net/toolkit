# 多任务冲突体检

> 由 `../SKILL.md` 第 1 步（动手前置）按需加载。触发判据与处置纪律在主文件，本文件承载维度、分级与输出模板；其他技能引用本文件，不复述细则。

## 一、触发

判据是**进入执行态**（授权判据齐备：执行指向 + 范围唯一 + 已定稿），不是措辞或落档动作：

- 顺序：进入执行态后先体检，再 `toolkit task init` / 建档，最后才改仓库文件；阻断时两者均未写入
- 同一执行轮内不重复；批量执行在批首跑一次，不按任务重复
- 用户点名复检优先于「同一轮不重复」：视为复检，但不重置轮次计数
- 中断恢复、搁置唤醒、会话恢复：各按新一轮执行态跑一次（现场可能已变）
- 定稿后计划被实质修改：退回规划态不触发，再次进入执行态时自然重检
- 单任务方案不触发

不触发：讨论 / 方案 / 定稿三态的一切动作，包括落档、追加任务、调整顺序、列计划表、复核。
这些动作可与「继续评估」同句出现，不是流程终态。

## 二、检查维度

| 维度 | 判据 | 常见冲突 |
| --- | --- | --- |
| 文件争用 | 两任务是否改同一文件、同一区块 | 同一模块的不同函数分属两任务 |
| 顺序依赖 | 后置任务改的接口 / 结构，前置任务是否依赖其现状 | B 改返回值，A 仍按旧返回值实现 |
| 契约一致 | 字段名、信封、schema、命令名是否同口径 | 两任务各起一个字段名；一处改 `code`、一处仍写 `ok` |
| 术语与版本 | 同一能力是否被叫成两个名字；版本括注是否冲突 | 一处叫「迁移」、一处叫「升级」；同一版本号被两任务分别递增 |
| 文档争用 | 是否改同一页面、同一节 | 两任务都改 `docs/guide.md` 同一小节 |
| 变更集粒度 | 同一对象是否被拆到多个任务各建变更集 | 信封改造拆成两条 minor，发版出现重复条目 |
| 跨仓耦合 | 是否依赖另一仓未完成的交付 | 本仓文档声称能力已可用，但配套仓未合入 |
| 授权互斥 | 是否都需要发版 / 推送 / 全局安装 | 两任务各自要求 publish，实际需串行并合并授权 |
| 共享现场 | 是否争用同一端口、临时目录、测试 fixture | 两个测试同时写同一个固定临时路径 |

## 三、分级

- **阻断**：同文件同区块、契约字段不一致、跨仓依赖未交付、同一对象上的不可逆动作、共享现场必然互斥
- **提示**：同文件不同区块、同页不同节、可通过调序或拆分解决、资源可错峰使用

## 四、处置

体检只负责检测，不自动改写计划：

- **提示**：不打断，随开工汇报一行带过
- **阻断（含仅需调序）**：停在体检阶段、不写文件，同时给出处理方案——仅调序写明「把谁前置、范围不变」，
  需拆分 / 合并 / 改范围 / 改契约 / 等他仓时给出改好的计划表
- **恢复按闸门词表，不引入新词**：仅调序不改变计划语义，属「开工被打断」，用户说「继续」即按 P→A 三联恢复；
  改范围等于计划变更、退回 U，须重新满足授权判据再执行
- 体检在建档之前，阻断时无任务档可写锚点，暂停原因与待执行范围只在对话回显；已有任务档的恢复场景才按 P 写进度锚点

依据：授权覆盖「按这份计划执行」，不含「改计划」；自动动作须可证明在授权意图内且可逆，故调序也由用户拍板。

## 五、输出模板

无冲突：

```
冲突体检：无
```

有冲突：

| 任务对 | 冲突点 | 分级 | 处理方案 |
| --- | --- | --- | --- |
| 1 → 2 | 都改 `docs/guide.md` 同一节 | 阻断 | 把 2 并入 1，或按 1→2 顺序重分章节 |
| 2 → 3 | 2 改信封字段，3 的示例仍按旧字段 | 阻断 | 3 排到 2 之后，示例随 2 的口径更新 |
| 1、2 | 都升同一依赖的不同版本 | 阻断 | 合并为一次依赖升级，或明确先后 |

- 结论只在对话里输出，不写入任务档；只有因此调整顺序时才更新计划表
- 无冲突不输出空表，只回一行，避免占用上下文

## 六、与其他技能的边界

- `fxri-plan-task` 主文件只留触发判据与处置纪律；维度、分级与模板以本文件为单一真源
- `fxri-plan-review` 的「冲突」复核轴只检查「最近一轮执行态是否体检过、阻断是否经授权」，不重复本文件
- 本检查不替代 `C-17` 的测试质量要求，也不替代发版前的人工净变更审计
